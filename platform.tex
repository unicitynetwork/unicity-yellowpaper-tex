\chapter{Unicity Certificate Framework}

\section{Sharding Schemes}\label{sec:sharding}

\emph{Sharding scheme}\index{shard!$\mathcal{SH}$ (sharding scheme)} $\mathcal{SH}$ of type $\mathbb{SH}$ is an irreducible prefix-free code (Appendix~\ref{app:ordering}).

If $\mathcal{SH} = \{\emptystr\}$, then there is a single shard.

In the description of a sharding scheme, the shard identifiers are listed in the topological order $\sigma_1 \prec \sigma_2 \prec \ldots \prec \sigma_n$ (Appendix~\ref{app:ordering}).

Every sharding scheme $\mathcal{SH}$ induces a sharding function $f_\mathcal{SH}\colon \idtype\to \mathcal{SH}$. The shard $f_\mathcal{SH}(\mathsf{sid})$ responsible for recording a token state with identifier $\mathsf{sid}$ is the shard whose identifier $\sigma_i$ is a prefix of $\mathsf{sid}$. With $\mathcal{SH}$ an irreducible prefix-free code, there is exactly one such $\sigma_i$.

\section{Networks}\label{sec:networks}

In practice, there may be several instances of Unicity networks, each consisting of its own Consensus Layer and its own set of partitions. Each such network will have an identifier $\alpha$\index{$\alpha$ (network identifier)}:

\begin{itemize}
\item $\alpha = 1$ is the public mainnet instance;
\item $\alpha = 2$ is the public testnet instance;
\item $\alpha = 3$ is a local development instance;
\item the identifiers $4 \ldots 8$ are reserved for future extensions;
\item any additional instances of Unicity networks should use identifiers starting from $9$.
\end{itemize}

To reduce the risk of confusion, it is recommended for each major deployment to use a unique identifier. However, there is no central registry to enforce this constraint.

It is strongly recommended to avoid using the identifier $0$, so that an uninitialized identifier (which defaults to $0$ in many programming languages) would not match any actual network.

\section{Partitions and Shards}\label{sec:partitions-shards}

Unicity network's aggregation layer consists of multiple \emph{partitions}\index{partition}. Each partition is identified by a partition identifier $\beta \in \mathbb{C}$\index{$\beta$ (partition identifier)}\index{$\mathbb{C}$ (partition identifier type)}. Each partition runs an unicity proving service instance (Unicity Service), or some other utility service instance\footnote{Roughly, this is similar to Layer 1, Layer 2 division of Ethereum type blockchains}.

A partition may be divided into one or more \emph{shards}\index{shard} according to a sharding scheme (Sec.~\ref{sec:sharding}). Each shard is implemented by one or more \emph{aggregation layer nodes}\index{aggregation layer node} that maintain the SMT for their portion of the key space, with the invariant $\forall$ leaves $(k,\cdot)$ in shard $\sigma$'s SMT, $f_\mathcal{SH}(k) = \sigma$.

\section{Partition Type and Partition Type Descriptor}

Every partition in the Unicity Framework with partition identifier $\beta$ has a type that is either:
\begin{enumerate}
\item a \emph{standard type} (SMT), or
\item a \emph{defined type} that is described as a data structure of type $\mathbb{SD}$.
\end{enumerate}

\subsection{Partition Type Descriptor}

A \emph{partition type descriptor} is a tuple $\mathcal{SD} = (\mathsf{hf}, \mathbb{CP}, V_{CP}, \gamma_{CP}) \in \mathbb{SD}$, where:
\begin{itemize}
\item $\mathsf{hf}$ -- hash function identifier (e.g., SHA-256)  % or version number
%\item $\mathsf{enc}$ -- encoding scheme identifier (e.g., CBOR for SMT serialization)
\item $\mathbb{CP}$ -- consistency proof type
\item $V_{CP} \colon \mathbb{IR} \to \mathbb{CP}$ -- consistency proof computation function
\item $\gamma_{CP} \colon \mathbb{IR} \times \mathbb{CP} \to \bool$ -- consistency proof verification predicate
\end{itemize}

For the SMT-based aggregation, the partition maintains a sparse Merkle tree mapping state identifiers to transaction hashes. The hash function $\mathsf{hf}$ is used for all cryptographic operations, and the encoding scheme $\mathsf{enc}$ specifies how data structures are serialized before hashing (see Sec.~\ref{sec:smt} for SMT structure).

The \emph{consistency proof}\index{consistency proof} is a data structure that allows BFT Core nodes to verify that aggregation layer shard nodes performed the SMT manipulations correctly during the round. The actual mechanism and content of consistency proofs will be defined separately for each partition type.

\subsection{Standard Partition Types}

\textbf{Unicity SMT} ($\mathsf{st} = 1$) -- Sparse Merkle Tree based unicity prover

\textbf{EVM} ($\mathsf{st} = 8$) -- Enshrined EVM runtime

\subsection{Partition Description Record}

A \emph{partition description record}\index{$\mathcal{CD}$ (partition description)}\index{partition description} is a tuple $\mathcal{CD} = (\alpha, \beta, \mathsf{st}, \mathcal{SD}, \mathcal{SH}) \in \mathbb{CD}$, where:
\begin{itemize}
\item $\alpha \in \mathbb{A}$ is the network identifier;
\item $\beta \in \mathbb{C}$ is the partition identifier;
\item $\mathsf{st} \in \mathbb{ST}$ is the system type identifier (for standard types, $\mathsf{st} > 0$);
\item $\mathcal{SD} \in \mathbb{SD}\opt$ is the system type descriptor (exists if $\mathsf{st} = 0$);
\item $\mathcal{SH} \in \mathbb{SH}$ is the sharding scheme.
\end{itemize}

Instead of $\mathcal{CD}.\mathcal{SD}.x$ (where $x$ is any field of $\mathcal{SD}$), we use the shorthand notation $\mathcal{CD}.x$.
For standard type partitions, the field $\mathcal{CD}.\mathcal{SD}$ does not exist. In this case, the notation $\mathcal{CD}.x$ will mean the constant value of $x$ of the standard type $\mathsf{st}$.

\section{Shard Split}\label{sec:shard-split-lifecycle}

A shard $\sigma$ of partition $\beta$ may be split into two sub-shards $\sigma \| 0$ and $\sigma \| 1$ for scaling reasons. The split affects (i) the sharding scheme recorded in the partition description, (ii) the per-shard SMTs maintained by aggregation layer nodes, and (iii) the per-shard state tracked by the BFT Core in $\mathcal{SI}$. The underlying tree operation is $\textsc{rsmt\_shard\_split}$ (Appendix~\ref{sec:rsmt-shard-split-fn}).

\paragraph{Partition description update.} Replacing $\sigma$ by $\sigma\|0,\sigma\|1$ changes the sharding scheme $\mathcal{SH}$ and thus $H(\mathcal{CD}[\beta])$, which appears as $\mathsf{dhash}$ in the Unicity Tree Certificate (Sec.~\ref{se:unicity-tree-certificate}). A split is configuration change executed at epoch change: a new partition description $\mathcal{CD}[\beta]'$ with the updated $\mathcal{SH}'$ is activated at an epoch boundary, and the split takes effect in the first round of the new epoch. Old unicity certificates remain verifiable against the $\mathcal{CD}[\beta]$ that was in force at the time of their issuance; verifiers must select the partition description record corresponding to $UC.C^\mathsf{r}.e_r$ (or, alternatively, authenticate it by its $\mathsf{dhash}$).

\paragraph{Aggregator state handover.} At the epoch boundary of the split, the aggregation layer nodes serving the new shard $\sigma\|b$ initialize their SMT by applying
\[
T_{\sigma\|b} \gets \textsc{rsmt\_shard\_split}(T_\sigma,\, |\sigma|,\, b)
\]
to the last pre-split tree $T_\sigma$ (whose root was $\mathcal{SI}[\beta,\sigma].h_-$). Let $\rho_{\sigma\|b}$ denote the root hash of $T_{\sigma\|b}$; if the retained subtree is empty, $\rho_{\sigma\|b} = \zerohash$. No rehashing is required for the retained subtree (Appendix~\ref{sec:rsmt-shard-split}).

\paragraph{BFT Core state handover.} At the same epoch boundary, the BFT Core replaces $\mathcal{SI}[\beta,\sigma]$ with two fresh entries $\mathcal{SI}[\beta,\sigma\|0]$ and $\mathcal{SI}[\beta,\sigma\|1]$. For each $b\in\{0,1\}$:
\begin{itemize}
	\item $\mathcal{SI}[\beta,\sigma\|b].n \gets \mathcal{SI}[\beta,\sigma].n$ and $\mathcal{SI}[\beta,\sigma\|b].e \gets \mathcal{SI}[\beta,\sigma].e + 1$;
	\item $\mathcal{SI}[\beta,\sigma\|b].h_- \gets \rho_{\sigma\|b}$, i.e.\ the root hash of the retained sub-shard SMT derived deterministically from the parent's last-certified root;
	\item $\mathcal{SI}[\beta,\sigma\|b].UC_- \gets \mathcal{SI}[\beta,\sigma].UC_-$ (the parent's last certificate remains the authenticated pre-state reference);
	\item the statistical records are reset as at any epoch change, and the validator set and leader for each sub-shard are assigned by the orchestration mechanism.
\end{itemize}

\paragraph{First post-split round.} The first certification request issued by $\sigma\|b$ after the split must satisfy the usual round chaining invariants of Sec.~\ref{sec:request-validation} with respect to the seeded values above. Specifically:
\[
\mathsf{CR}.\mathcal{IR}.h' = \rho_{\sigma\|b} = \mathcal{SI}[\beta,\sigma\|b].h_-,
\]
and if no new leaves are inserted during that round then $\mathsf{CR}.\mathcal{IR}.h = \rho_{\sigma\|b}$ and the batch $B$ is empty. The consistency proof $\pi_{CP}$ for this bridging round is therefore the empty-batch proof (accepted by $\textsc{rsmt\_verify\_consistency}$ when $B = \langle\rangle$, $\pi_{CP} = \langle\rangle$ and $h' = h$, Appendix~\ref{sec:rsmt-verify-consistency}). Subsequent rounds proceed normally. The correctness of the $\rho_{\sigma\|b}$ seeding is not proved on-chain by the child shard; it follows deterministically from the parent's last-certified root by Appendix~\ref{sec:rsmt-shard-split-fn}, which any validator can recompute.

\section{Unicity Service Request}

A \emph{Unicity Service Request}\index{$Q$ (unicity service request)} is a request to the Unicity Service for state transition certification. It is a tuple $Q = (\predi, \sthash, \txhash, u)$, where:
\begin{itemize}
	\item $\predi$ -- current owner's spending predicate (Sec.~\ref{sec:predicates})
	\item $\sthash \in \hashtype$ -- current state hash
	\item $\txhash \in \hashtype$ -- transaction data hash
	\item $u$ -- unlocking argument satisfying $\predi$
\end{itemize}

The Unicity Service processes the request by:
\begin{enumerate}
	\item Evaluating the predicate: $\predi(\tau, H(\sthash, \txhash), u) = 1$
	\item Computing the state identifier: $\mathsf{sid} = H(\predi, \sthash)$
	\item Checking uniqueness: the state has not been spent before (i.e., $\mathsf{sid}$ does not already exist in the SMT)
	\item If all checks pass: setting the SMT leaf $(\mathsf{sid}, \txhash)$ in the tree
\end{enumerate}

The request is accepted without returning a synchronous response. The detailed validation algorithm will be specified in Sec.~\ref{sec:request-validation}.

\section{Unicity Service Request Validation}\label{sec:request-validation}

The aggregation layer nodes process Unicity Service Requests by validating them and, if valid, updating their SMT. Each shard maintains an SMT for its portion of the key space.

\subsection{Validation and Processing Algorithm}

Given a Unicity Service Request $Q = (\predi, \sthash, \txhash, u)$, the aggregation layer node performs the following checks:

\begin{enumerate}
	\item \textbf{Right shard check}: Compute the state identifier
	\[
	\mathsf{sid} = H(\predi, \sthash)
	\]
	and verify that the current shard $\sigma$ satisfies
	\[
	f_{\mathcal{CD}[\beta].\mathcal{SH}}(\mathsf{sid}) = \sigma .
	\]
	If this check fails, the request was sent to the wrong shard and must be rejected (or forwarded to the correct shard).

	\item \textbf{Predicate evaluation}: Verify that the unlocking argument satisfies the predicate:
	\[
	\predi(\tau, H(\sthash, \txhash), u) = 1
	\]

	\item \textbf{Uniqueness check}: Verify that the SMT does not contain a leaf with key $\mathsf{sid}$ (i.e., the state has not been spent before).
\end{enumerate}

If all checks are satisfied, the request is accepted and the aggregation layer node sets the SMT leaf:
\[
\text{Set SMT leaf: } (\mathsf{sid}, \txhash)
\]
This updates the SMT by inserting the new leaf.

If either check fails, the request is rejected:
\begin{itemize}
	\item If predicate evaluation fails: the request is invalid and must be rejected
	\item If uniqueness check fails (leaf with key $\mathsf{sid}$ already exists): the state has already been spent (double-spend attempt) and the request must be rejected
\end{itemize}

After processing a batch of requests, the aggregation layer nodes compute the new SMT root hash $h$ and send a certification request to the BFT Core. The BFT Core verifies the consistency proof $\pi_{CP}$ and that last state is extended correctly and certifies the new root hash $h$ via the Unicity Certificate.

\subsection{Sparse Merkle Tree}\label{sec:smt}

\index{sparse merkle tree}\index{SMT}\index{RSMT}
The aggregation layer maintains a \emph{(Radix) Sparse Merkle Tree} (SMT), a path-compressed authenticated map from 256-bit state identifiers to transaction hashes. Leaves are anchored by full keys, and internal nodes commit to their absolute branching depth and to the key prefix (\emph{region}) addressing them, which both routes lookups and pins every node to its position in the key space. The SMT supports batch insertion, inclusion certificates, non-inclusion certificates and consistency proofs. Exact formats and algorithms are given in Appendix~\ref{app:rsmt}.


\subsubsection{SMT Leaf Structure}

An SMT leaf contains a key-value pair:
\begin{itemize}
	\item \textbf{Key}: State identifier $\mathsf{sid} = H(\predi, \sthash)$ where:
	\begin{itemize}
		\item $\predi$ -- spending predicate of the token owner (Sec.~\ref{sec:predicates})
		\item $\sthash$ -- state hash representing the current state of a token
	\end{itemize}
	\item \textbf{Value}: Transaction data hash $\txhash$.
\end{itemize}

The SMT effectively maintains a mapping $\mathsf{sid} \mapsto \txhash$ that proves a state transition from state identifier $\mathsf{sid}$ was authorized via transaction with hash $\txhash$. This prevents double-spending: once a state identifier is registered in the SMT with a transaction hash, that state cannot be spent again.

\subsubsection{SMT Certificates and Updates}\label{InclusionCert}

\index{$C^\mathsf{inc}$ (Inclusion Certificate)}\index{Inclusion Certificate}\index{$C^\mathsf{exc}$ (Non-Inclusion Certificate)}\index{Non-Inclusion Certificate}
The SMT exposes the following functionalities and authenticated objects:
\begin{itemize}
	\item \textbf{Batch insertion}: inserts a batch of new leaves into the tree and updates the root hash.
	\item \textbf{Inclusion Certificate} $C^\mathsf{inc}$: authenticates that a leaf $(\mathsf{sid}, \txhash)$ is present under a given SMT root.
	\item \textbf{Non-Inclusion Certificate} $C^\mathsf{exc}$: authenticates that a state identifier $\mathsf{sid}$ is absent from the tree.
	\item \textbf{Consistency proof} $\pi_{CP}$: authenticates that a new SMT root extends a previous root by a batch insertion.
\end{itemize}

Appendix~\ref{app:rsmt} defines the corresponding wire formats and verification procedures.

\subsubsection{Re-presentation of Certified Leaves}\label{sec:leaf-representation}

\index{SMT!re-presentation}\index{inclusion proof!re-presentation}
The SMT is append-only: a certified insertion adds leaves and modifies none (Sec.~\ref{sec:consistency-proof}). A leaf $(\mathsf{sid}, \txhash)$ first certified in round $n$ is therefore still present under the root certified in any later round $n' > n$, and the shard can issue an inclusion certificate for it against that later root. A holder who needs certification evidence for an old transition does not have to keep, or re-obtain, the Unicity Certificate issued at the time; it is sufficient to ask the shard for a fresh certificate.

Two properties of the aggregation layer are load-bearing for this and are therefore normative rather than incidental. A shard MUST NOT remove or rewrite a certified leaf, which the single-spend rule already requires (Sec.~\ref{sec:request-validation}) and which re-presentation now also depends on. And a successor of a shard split MUST retain the leaves of the parent that route to it under $f_\mathcal{SH}$, as specified in Appendix~\ref{sec:rsmt-shard-split}, so that a pre-split leaf remains provable after the split.

Re-presentation against a recent round also removes the need for historical auxiliary data at verification: the partition description authenticated by $C^\mathsf{uni}.\mathsf{dhash}$ and used for the right-shard binding of $\mathsf{VerifyInclusionProof}$ is the one currently in force, not the one in force when the transition was certified.

Shards expose the query
\[
\Call{GetInclusionMulti}{\langle \mathsf{sid}_1, \ldots, \mathsf{sid}_k\rangle},
\]
which returns one inclusion certificate covering all $k$ keys against the shard's last certified SMT root, together with the $UC$ that certified it. The keys are all in the responding shard's key range. A single certificate for $k$ keys shares the internal nodes their paths have in common, which is the saving over $k$ separate certificates. The shard answers against $\mathcal{SI}[\beta,\sigma].UC_-$, the version it already retains in order to serve ordinary inclusion proofs, so no versioned tree state beyond current practice is required.

Each shard answers at whatever round it last certified, and no attempt is made to bring the shards into step. The spread is bounded without one: the BFT Core issues a repeat certification after a shard's \texttt{t2} timeout (Sec.~\ref{sec:bft-functional}, step~8), so a shard's latest $UC$ is at most \texttt{t2} behind the current round however long that shard has been idle. A client collecting proofs from several shards therefore obtains certificates spanning at most the rounds within one \texttt{t2}, and reconciles them against a single anchor with one batched root history proof over that span (Sec.~\ref{sec:root-history-service}). This makes \texttt{t2} the parameter that sets both the size of the round table and the minimum retention a node needs in order to serve the leaf path.

\subsection{Shard Tree Certificate}\label{se:shard-tree-cert}

\emph{Shard Tree Certificate}\index{$C^\mathsf{shard}$ (shard tree certificate)}\index{shard tree certificate} connects a shard's certified input hash to the partition's shard-tree root, from which the Unicity Tree certificate continues to the global root of trust. It is a tuple $C^\mathsf{shard} = (\sigma; h^s_1, \ldots, h^s_{|\sigma|})$, where:
\begin{enumerate}
	\item $\sigma=\sigma_1\sigma_2\ldots \sigma_{|\sigma|}$ is a shard identifier of type $\{0,1\}^\ast$
	\item $h^s_1, \ldots, h^s_{|\sigma|}$ -- sibling hashes of type $\hashtype$
\end{enumerate}

For the single shard case, the sharding scheme is $\{\emptystr\}$ and the certificate is $(\emptystr, \bot)$.

\subsubsection{Sharded SMT Structure}
In a sharded setting, each shard maintains the SMT for its portion of the key space and produces a certified shard input record $(IR, h_t)$. The Consensus Layer then deterministically builds the shard tree from the authenticated shard inputs of all shards in the partition (see Sec.~\ref{se:shard-tree} and Algorithm~\ref{alg:uc-gen}).

\subsubsection{Creation: $\mathsf{CreateShardTreeCert}$}\label{se:create-shard-tree-cert}

\textbf{Input}:\index{functions!CreateShardTreeCert}
\begin{enumerate}
	\item $\sigma$ -- shard identifier
	\item $\chi$ -- shard tree of type $\chi \colon \overline{\mathcal{SH}}\to \hashtype$
\end{enumerate}

\textbf{Output}: shard tree certificate $C^\mathsf{shard}=(\sigma; h^s_1, \ldots , h^s_{|\sigma|})$

\textbf{Computation}:
\begin{algorithmic}
	\State $C \gets ()$
	\For{$i \gets  |\sigma|$ downto $1$}
		\State $C \gets C \mathbin{\|} \chi(\sigma_1\sigma_2\ldots\sigma_{i-1}\overline{\sigma_i})$
	\EndFor
	\State \Return $(\sigma; C)$
\end{algorithmic}

where $\sigma_1\sigma_2\ldots\sigma_m$ is the binary representation of $\sigma$, and $\overline{\sigma_i}$ is the binary complement of $\sigma_i$.

For the single shard case, the shard certificate is $(\emptystr,\bot)$.

\subsubsection{Computation: $\mathsf{CompShardTreeCert}$}\index{functions!CompShardTreeCert}

\textbf{Input}:
\begin{enumerate}
	\item $(\sigma;h^s_1, \ldots, h^s_{|\sigma|})$ -- shard tree certificate, where $\sigma=\sigma_1\sigma_2\ldots \sigma_{|\sigma|}$ is a shard identifier
	\item $IR$ -- Shard Input Record
	\item $h_t$ -- hash value of type $\hashtype$
\end{enumerate}
\textbf{Output}: Root hash $r$ of type $\hashtype$

\textbf{Computation}:

\begin{algorithmic}[0]
	\State $r \gets H(IR \mathbin{\|} h_t)$
	\For {$i \gets |\sigma|$ downto $1$ }
		\State \textbf{if} $\sigma_i = 0$ \textbf{then} $r \gets  H(r, h^s_i)$
		\State \textbf{if} $\sigma_i = 1$ \textbf{then} $r \gets  H(h^s_i, r)$
	\EndFor
	\State \Return $r$
\end{algorithmic}

For the single shard case, $\mathsf{CompShardTreeCert}((\emptystr, \bot), IR, h_t)$ returns $H(IR \mathbin{\|} h_t)$.

\subsection{Unicity Tree Certificate}\label{se:unicity-tree-certificate}

\emph{Unicity Tree Certificate}\index{$C^\mathsf{uni}$ (unicity tree certificate)}\index{unicity tree certificate} (Fig.~\ref{fi:uc}) is a tuple $C^\mathsf{uni} = (\beta, \mathsf{dhash}; (\beta_2, h_2), \ldots, (\beta_\ell, h_\ell))$, where:
\begin{enumerate}
	\item $\beta$ -- partition identifier of type $\mathbb{C}$
	\item $\mathsf{dhash}$ -- partition description hash of type $\hashtype$
	\item $(\beta_2, h_2), \ldots, (\beta_\ell, h_\ell)$ -- a sequence of partition identifier and sibling hash pairs
\end{enumerate}

\subsubsection{Creation: $\mathsf{CreateUnicityTreeCert}$}\label{se:create-unicity-tree-cert}\index{functions!CreateUnicityTreeCert}

\textbf{Input}:
\begin{enumerate}
	\item $\beta$ -- partition identifier of type $\mathbb{C}$
	\item $\mathcal{C}$ -- set of partition identifiers of type $\mathbb{C}$
	\item $\mathcal{CD}$ -- partition description of type $\mathbb{CD}[\mathcal{C}]$
	\item $\mathcal{IH}$ -- input hashes of type $\hashtype[\mathcal{C}]$
\end{enumerate}

\textbf{Output}: unicity tree certificate $(\beta, \mathsf{dhash}; (\beta_2, h_2), \ldots, (\beta_\ell, h_\ell))$

\textbf{Computation}:
\begin{algorithmic}
	\State $n \gets \len{\mathcal{C}}$ \Comment{Number of partitions}
	\State $C \gets \mathsf{sorted}(\mathcal{C})$ \Comment{Sorted list}
	\For{$i \gets 1 \ldots n$}
		\State $x_i \gets H(\mathcal{IH}[C_i] \mathbin{\|} H(\mathcal{CD}[C_i]))$
	\EndFor
	\State $\langle (\beta_1, h_1), (\beta_2, h_2), \ldots, (\beta_\ell, h_\ell) \rangle \gets \Call{\textsc{index\_tree\_chain}}{(C_1, x_1), (C_2, x_2), \ldots, (C_n, x_n), \beta}$ %\Comment{Sec.~\ref{sec:index-tree-chain}}
	\State \Return $(\beta, H(\mathcal{CD}[\beta]); (\beta_2, h_2), \ldots, (\beta_\ell, h_\ell))$ \Comment{Drop redundant first hash step}
\end{algorithmic}

\subsubsection{Computation: $\mathsf{CompUnicityTreeCert}$}
\index{unicity tree certificate!computation}
\textbf{Input}:
\begin{enumerate}
	\item $(\beta, \mathsf{dhash}; (\beta_2, h_2), \ldots, (\beta_\ell, h_\ell))$ -- unicity tree certificate
	\item $x$ -- input hash (output of the $\mathsf{CompShardTreeCert}$ function)
\end{enumerate}
\textbf{Output}: Root hash $r$ of type $\hashtype$

\textbf{Computation}:
\begin{algorithmic}[0]
	\State $L \gets \langle (\beta, H(x, \mathsf{dhash})), (\beta_2, h_2), \ldots, (\beta_\ell, h_\ell) \rangle$ \Comment{Restore the first hash step}
	\State \Return $\Call{\textsc{index\_tree\_output}}{L; \beta}$ \Comment{Sec.~\ref{sec:index-tree-output}}
\end{algorithmic}


\subsection{Unicity Seal}

\emph{Unicity Seal}\index{$C^\mathsf{r}$ (unicity seal)}\index{unicity seal} is a tuple $C^\mathsf{r} = (\alpha, n_r, e_r, t_r, r, a_r; s)$, where:
\begin{enumerate}
	\item $\alpha$ -- Network identifier
	\item $n_r$ -- BFT Core's Round number
	\item $e_r$ -- BFT Core's Epoch number
	\item $t_r$ -- Round creation time (wall clock value specified and verified by the BFT Core), with one-second precision. See Appendix~\ref{app:encodings} for encoding
	\item $r$ -- Root hash of the Unicity Tree (denoted as $r^{\text{root}}$ if necessary for clarity)
	\item $a_r$ -- Root history accumulator, committing every Unicity Tree root up to and including $r$ (Sec.~\ref{sec:root-history})
	\item $s$ -- Signature, computed by the BFT Core over preceding fields ($s = \mathsf{Sign}_{\mathsf{sk}_r}(n_r, e_r, t_r, r, a_r)$). The formulation of signature field depends on underlying consensus mechanism and its parameters. Here we assume an opaque data structure which can be verified based on the Unicity Trust Base, i.e., there is an implementation of an abstract function $\mathsf{Verify}_{\mathcal{T}}((n_r, e_r, t_r, r, a_r), s)$, encapsulated into the implementation of $\mathsf{VerifyUnicitySeal}$.
\end{enumerate}

$\mathsf{VerifyUnicitySeal}$ -- unicity seal verification function of type $\hashtype \times \mathbb{US} \times \mathbb{UB} \to \bool$\;. This function also verifies, if Unicity Seal's network identifier matches with the Unicity Trust Base.

\subsubsection{Root History Accumulator}\label{sec:root-history}

\index{root history accumulator}\index{$a_r$ (root history accumulator)}
$a_r$ is the seal's chain-linking field: it commits the whole sequence of Unicity Tree roots the network has certified, so any historical root is provable against the \emph{current} seal in $O(\log n_r)$.

\paragraph{Sequence and size.} BFT Core round numbers start at $0$ and increase by one per round (Sec.~\ref{sec:distributed-bft-core}), so the seal of round $n_r$ is the $(n_r{+}1)$-th. The accumulator of that seal commits the roots of rounds $0, \ldots, n_r$, and its \emph{size} is $N = n_r + 1$.

$N$ is derived from the signed $n_r$, and is therefore authenticated by the same signature. The operations below use $N$ to derive the shape of the MMR accumulator.

\paragraph{Leaves.} The accumulator leaf for round $n$ is
\[
\ell_n \;:=\; H(\mathsf{ROOT\_LEAF},\; n,\; r_n),
\]
with $\mathsf{ROOT\_LEAF}$ the ASCII byte string \texttt{"UNICITY\_ROOT\_LEAF"}.
% The domain separator distinguishes leaves from interior nodes, which $\textsc{plain\_tree\_root}$ does not provide. Binding $n$ into the leaf makes the index unforgeable and ensures that at most one root verifies at each index.

\paragraph{Structure and modification.} The accumulator over $\langle \ell_0, \ldots, \ell_{N-1}\rangle$ is a list of MMR peaks: the roots of complete binary trees of strictly decreasing size, one for each $1$-bit of $N$, built with $\textsc{plain\_tree\_root}$. The append operation $\Call{AccAppend}{P, N, n, r}$ forms $\ell_n$, adds it as a singleton peak, repeatedly merges the two smallest equal-sized peaks, and returns the new peak list and $N+1$. The accumulator value is $a_r = \Call{plain\_tree\_root}{P}$ over the resulting list.

The retained state is the list of peaks: one hash per $1$-bit of $N$.
% Per-round cost is $O(1)$ amortized for the merge step but $O(\operatorname{popcount} N) = O(\log N)$ for re-bagging the peaks into $a_r$, which must be done every round; the per-round cost is therefore $O(\log N)$, not $O(1)$. In absolute terms this is a few dozen hashes per round and is negligible beside the round's other work, but it is not constant.

\paragraph{Membership.} A \emph{root history proof} $\varpi$ for a root $r_n$ at index $n$ against $(a_r, N)$ is the sibling path of $\ell_n$ within its peak, followed by the other peaks in canonical order. $\Call{VerifyRootHistory}{a_r, N, n, r_n, \varpi} = 1$ iff $n < N$, the path length matches the height of the peak that index $n$ falls in under the decomposition of $N$, and recomputation from $\ell_n = H(\mathsf{ROOT\_LEAF}, n, r_n)$ yields $a_r$.

\paragraph{Batched membership.} Roots at $d$ distinct indices are proved together by a \emph{batched} root history proof, which supplies each distinct interior node once instead of once per index. Its size is $O(d\log(N/d) + \log N)$ rather than $O(d\log N)$, since paths converge as they approach the peaks and the peak list is shared.
Verifiers and aggregators MUST implement the batched form. $d = 1$ is a special case.

\paragraph{Prefix consistency.} A \emph{root history consistency proof} $\psi$ shows that an earlier accumulator value is the accumulator over a prefix of the same sequence: $\Call{VerifyRootHistoryPrefix}{a_M, M, a_N, N, \psi} = 1$, for $M \le N$, iff $\psi$ exhibits the peaks of the size-$M$ accumulator together with the siblings needed to recompute the peaks of the size-$N$ accumulator from them, yielding $a_M$ and $a_N$ respectively under the decompositions of $M$ and $N$. This is the ordinary append-only log consistency check.

% Both proofs must exist for the accumulator to be usable. An accumulator value that is merely asserted --- claimed to be some round's, but not shown to extend to the current one --- authenticates nothing: an accumulator authorizes arbitrary historical roots, so an unauthenticated accumulator authorizes arbitrary fabricated roots. Wherever an earlier accumulator value is accepted, it MUST be tied to a verified one by $\Call{VerifyRootHistoryPrefix}{}$; Sec.~\ref{sec:compression-relation} is the case in point.

\paragraph{Consensus state.} The accumulator is deterministically computable consensus state. The peak list and $N$ are part of the State of the BFT Core; the append is a deterministic function of the round's own Unicity Tree root, so every correct validator computes the same $a_r$; and the post-round value is committed by the state authenticator that validators vote on. A proposal carrying a wrong $a_r$ cannot reach a quorum. A recovering or newly joining validator obtains the peak list and $N$ from a peer and accepts them only if they reproduce the authenticator of the highest known Quorum Certificate. The accumulator persists across epoch and trust base changes.

\paragraph{Genesis.} The accumulator is initialized at round $0$, with round-$0$ root being the 1st entry.

\paragraph{Consequences.} A relying party that verifies a single \emph{recent} seal under its current trust base gains the ability to authenticate every earlier Unicity Tree root and every earlier accumulator value. Because $a_r$ is signed, an aggregator or archival node can serve $\varpi$ and $\psi$ trustlessly.

\subsection{Root History Proofs and Their Service}\label{sec:root-history-service}

\index{root history accumulator!service}\index{aggregation layer node!root history service}
The accumulator is maintained by the BFT Core, which retains only the frontier and exposes no public interface. Root history proofs are served by aggregators and by archive nodes, as an optional service. The root history is network-global, verifiable public data and is not shard-specific.

The service answers queries of two kinds, and they differ sharply in the retention they need. Reconciling the certificates a client has just collected from several shards spans at most one \texttt{t2} of rounds (Sec.~\ref{sec:leaf-representation}), so any node that has been running for that long can answer. Relating an \emph{older} accumulator value to a current one, as folding an existing token attestation requires (Sec.~\ref{sec:compression-relation}, check~5), spans the age of the attestation, and only a node retaining that far back can answer. No party is obliged to retain any particular depth; Sec.~\ref{sec:compression-relation} specifies the alternative available to a prover when no node retains the range it needs.

\subsubsection{Seal Distribution}\label{sec:seal-distribution}

A node that maintains root history needs $r_n$ for every round $n$ within its retained range, without gaps. A Certification Response (Sec.~\ref{certification-response}) reaches a shard only in rounds where its input changed or a repeat certification was induced, so it is not a gapless source. The BFT Core MUST therefore publish each round's Unicity Seal to the aggregation layer in every round, independently of whether any shard's input changed (Sec.~\ref{sec:bft-functional}, step~8). Other nodes obtain seals from any peer, a seal being self-authenticating against the Unicity Trust Base, so a recovering node can use whichever peer answers first.

\subsubsection{Retention and Pruning}\label{sec:root-history-pruning}

\index{root history accumulator!pruning}
A node serves root history over a range of its own choosing. Retaining the range $[M_0, N)$ requires the roots $r_{M_0}, \ldots, r_{N-1}$ at 32 bytes each --- approximately 1\,GB per year at one round per second --- together with the \emph{seam frontier} $P_{M_0}$, the accumulator peak list at size $M_0$, which is one hash per $1$-bit of $M_0$.

The smallest configuration that serves the leaf path retains only the frontier and the roots of the last \texttt{t2} worth of rounds, since that is the widest span a set of freshly collected shard certificates can cover (Sec.~\ref{sec:leaf-representation}). At one round per second and a \texttt{t2} of a few seconds this is a handful of hashes beside the $O(\log N)$ frontier, and it grows with \texttt{t2} rather than with the age of the network. Aggregation layer nodes SHOULD retain at least this much, updating the frontier once per round from the seal they already receive, so that a client compressing a token can obtain its round table without reaching an archive.

The seam frontier is sufficient because an MMR append only ever merges a new right subtree into an existing peak. Every node ever formed over a range beginning below $M_0$ is therefore a merge of a suffix of the peaks of $P_{M_0}$ with nodes over ranges at or above $M_0$, and the latter are computable from the retained roots. A node holding $(P_{M_0}, M_0)$ and the retained roots can consequently produce $\varpi$ for any $n \in [M_0, N)$ and $\psi$ for any $M \in [M_0, N]$. Queries below $M_0$ fail, which is the intended effect of pruning.

Bootstrapping is one small transfer and requires no trust in the peer. A node starting at $M_0$ obtains $P_{M_0}$ from any peer and accepts it only if $\Call{plain\_tree\_root}{P_{M_0}} = C^\mathsf{r}.a_r$ for a seal of round $M_0 - 1$ that it has verified under its own trust base. Thereafter it advances by appending each round's root as the seal arrives, requiring $\Call{plain\_tree\_root}{P'} = C^\mathsf{r}.a_r$ where $(P', N') = \Call{AccAppend}{P, N, n, C^\mathsf{r}.r}$, and recovering from a peer on any mismatch or gap. A node may raise $M_0$ at any time by discarding older roots and adopting the corresponding frontier, which it computes from material it already holds.

The depth a deployment chooses bounds the age of an attestation that can be folded by prefix consistency rather than by the fallback of Sec.~\ref{sec:compression-relation}. Retaining from round $0$ is permitted but is not required of any node.

\subsubsection{Queries}

\begin{longtable}{lp{9.4cm}}
\textbf{Query} & \textbf{Response} \\
\hline
\endhead
$\Call{GetSeal}{n}$ & the Unicity Seal of round $n$; the latest if $n$ is not provided \\
$\Call{GetRootHistory}{n, N^*}$ & $\varpi$, the membership path of $r_n$ against the accumulator of size $N^*$ \\

\subsubsection{Data Flows}

\begin{description}
	\item[Ingestion] BFT Core $\rightarrow$ aggregators, once per round. Continuous and independent of any client.
	\item[Replication] p2p batched protocol.
	\item[Proofs] A holder compressing a token collects fresh inclusion proofs from the shards holding its state identifiers (Sec.~\ref{sec:leaf-representation}), takes the newest of the returned seals as the anchor, and requests one $\Call{GetRootHistoryBatch}{\langle n_1, \ldots, n_d\rangle, N^*}$ over the rounds those proofs came from --- a span of at most one \texttt{t2}. A holder folding an existing attestation additionally requests one $\Call{GetRootHistoryPrefix}{}$, from a node whose retained range covers the attestation's anchor.
	\item[Verification] Tokens are self-contained, thus, no query.
\end{description}

The serving node is trustless and can be replicated without coordination, cached, placed behind ordinary content-distribution infrastructure, or run privately by a semi-offline third party.

\subsection{Consistency Proof}\label{sec:consistency-proof}

\index{consistency proof}\index{$\pi_{CP}$ (consistency proof)}
A \emph{Consistency Proof} (in earlier documents also called a \emph{non-deletion proof}; we use \emph{consistency proof} throughout) is a cryptographic construction that validates one round of operation of the append-only SMT maintained by aggregation layer nodes. It proves that the state transition from previous SMT root hash $h'$ to current SMT root hash $h$ was performed correctly: only new leaves were added, each at the position determined by its key, and no pre-existing leaves were removed or modified. For a round with inserted batch
\[
B = \langle (\mathsf{sid}_1, h_{\mathsf{tx},1}), \ldots, (\mathsf{sid}_j, h_{\mathsf{tx},j}) \rangle,
\]
the security objective is to prove that the map committed by $h$ is obtained from the map committed by $h'$ by extending it with exactly the leaves in $B$.

The consistency proof enables the BFT Core to verify the integrity of the Aggregation Layer's SMT manipulation with respect to the authenticated prior root and the declared round batch.

For a batch of state transitions processed in a single round, the consistency proof $\pi_{CP}$ is the post-order opcode stream defined in Appendix~\ref{sec:rsmt-consistency-proof}.

\subsubsection{Security Model}

The aggregation layer node that computes $\pi_{CP}$ may be Byzantine: it may maintain an arbitrary internal tree representation, claim an arbitrary post-state root $h$, and send an arbitrary proof stream. The verifier trusts only the following inputs:
\begin{enumerate}
	\item the previously certified root hash $h'$;
	\item the batch $B$ determined by the validated requests of the round;
	\item the claimed post-state root hash $h$ in the shard input record; and
	\item the collision resistance of the hash function $H$.
\end{enumerate}

The consistency proof authenticates only the append-only SMT update from $h'$ to $h$. It does not, by itself, prove that an element of $B$ was semantically admissible for insertion; this is established separately by request validation (Sec.~\ref{sec:request-validation}) and public audit of append only logs of Aggregation nodes.

\subsubsection{Verification Function}\label{VerifyConsistencyProof}\index{functions!VerifyConsistencyProof}

$\mathsf{VerifyConsistencyProof}$ -- consistency proof verification function of type $\mathbb{CP} \times (\bytes{32} \times \hashtype)^\ast \times \hashtype\opt \times \hashtype\opt \to \bool$

\textbf{Input}:
\begin{enumerate}
	\item $\pi_{CP}$ -- consistency proof (opcode stream)
	\item $B = \langle (\mathsf{sid}_1, h_{\mathsf{tx},1}), \ldots, (\mathsf{sid}_j, h_{\mathsf{tx},j}) \rangle$ -- batch of inserted leaves
	\item $h'$ -- previous SMT root hash (before the round)
	\item $h$ -- current SMT root hash (after the round)
\end{enumerate}

\textbf{Output}: \TRUE or \FALSE

The verification algorithm ($\textsc{rsmt\_verify\_consistency}$) is defined in Appendix~\ref{sec:rsmt-verify-consistency}.

The proof system must enforce \emph{append-only consistency}\index{append-only consistency}, which combines the following two properties. Let $M_0, M_1 \colon \bytes{32} \to \hashtype\opt$ denote the partial maps committed by $h'$ and $h$, respectively (a binding is committed exactly when an inclusion certificate for it verifies against the root).

\begin{itemize}
	\item \textbf{Prior-state preservation}: If $\mathsf{VerifyConsistencyProof}(\pi_{CP}, B, h', h) = \TRUE$, then
	\[
		\forall\, \mathsf{sid} \in \bytes{32}\colon\; M_0(\mathsf{sid}) \ne \bot \Rightarrow M_1(\mathsf{sid}) = M_0(\mathsf{sid}).
	\]
	That is, no previously committed SMT leaf can be deleted or modified.
	\item \textbf{Coherent placement}: every leaf inserted in the round is placed at the position determined by its key; together with the above, $M_1$ extends $M_0$ by exactly the bindings of $B$, whose keys must be fresh---no accepting proof exists for a batch that re-records an already-present key.
\end{itemize}

Append-only consistency is required to avoid potential double-spending with the help of malicious operators. Coherent placement cannot be omitted: a single misplaced junction above a preserved subtree makes every binding in that subtree unprovable under the new root, and allows the freed key positions to be re-recorded with different values in later rounds---an equivocation that passes every purely structural check. Applied round by round from the empty genesis tree, append-only consistency also guarantees that every certified tree is the unique canonical tree of its key set.

The security model where an untrusted Aggregator machine generates (non-)inclusion proofs, anchored by committed root hashes, allows us to avoid stronger guarantees like \emph{completeness} (censoring a request is denial of service at worst), \emph{batch incorporation} (failure to insert some leaves results in denial of service at worst), \emph{batch binding} (inclusion proofs do it better), and \emph{no phantom insertions} (free recording service at worst; phantom entries carry fresh keys, since coherent placement forbids re-recording).

For the hash-based instantiation of the consistency proof in this model, the batch $B$ (the sorted list of inserted $(\mathsf{sid}, h_\mathsf{tx})$ pairs) accompanies the opcode stream on the wire, since the BFT Core does not otherwise possess it; the check $|B| = \mathsf{CR}.\ell_B$ cross-links it to the certification request. Supplying $B$ from the untrusted aggregator is safe in this model: append-only consistency holds for whatever batch is declared, and batch contents beyond that are covered by the scoping argument above. The ZK-compressed instantiation (Appendix~\ref{app:zk-consistency-proof}) keeps the batch private and exposes only the two roots.

\subsection{Shard Input Record}\label{shard-input-record}

\begin{enumerate}
	\item $n$ -- shard's round number of type $\uint{64}$
	\item $e$ -- shard's epoch number of type $\uint{64}$
	\item $h'$ -- previous round's SMT root hash of type $\hashtype$

	\item $t$ -- reference time for request validation of type $\uint{64}$

\subsection{Statistical Record}\label{statistical-record}

Statistical record of type $\mathbb{SR}$ is a tuple $\mathsf{SR}=(n_e, \overline{\ell}_B, \overline{\ell}_S, \hat{\ell}_B, \hat{\ell}_S)$, where:\index{statistical record ($\mathsf{SR}$)}
\begin{enumerate}
	\item $n_e$ -- number of non-empty rounds (adding at least one new leaf), of type $\uint{64}$
	\item $\overline{\ell}_B$ -- cumulative number of new SMT leaves added during the epoch's rounds, of type $\uint{64}$
	\item $\overline{\ell}_S$ -- cumulative sum of the per-round SMT memory usage in bytes (for computing epoch averages), of type $\uint{64}$
	\item $\hat{\ell}_B$ -- maximum number of SMT additions processed during a round, of type $\uint{64}$
	\item $\hat{\ell}_S$ -- maximum SMT memory usage in bytes observed during a round, of type $\uint{64}$
\end{enumerate}

The record may be extended with other accounting data (fees, etc.).

There is one Statistical Record of current epoch where the values are being updated, reflecting the current state since the beginning of the epoch; and one invariant Statistical Record of the preceding epoch of every shard of every public partition.

\subsection{Technical Record}\label{technical-record}

Technical record\index{technical record ($\mathbb{TE}$)} of type $\mathbb{TE}$ is a tuple $\mathsf{TE}=(n_r, e_r, \nu_\ell, h_\mathsf{sr})$, where:
\begin{enumerate}
	\item $n_r$ -- suggested next round number of type $\uint{64}$
	\item $e_r$ -- suggested next epoch number of type $\uint{64}$
	\item $\nu_\ell$ -- suggested leader identifier of type $\{0,1\}^\ast$
	\item $h_\mathsf{sr}$ -- hash of statistical records; type $\hashtype$
\end{enumerate}

Technical record is delivered with an Unicity Certificate. When a shard is extending the Unicity Certificate with a next round certification attempt, then it must use the suggested values provided in Technical Record.

There is one Technical Record for every shard of every partition, providing synchronization for the next round.

\subsection{Shard Info}

\emph{Shard info}\index{shard!shard info} of type $\mathbb{SI}$ is a tuple $(n, e, h_-, \mathsf{SR}_-, \mathsf{SR}, \mathcal{V}, \nu_\ell, UC_-)$, where:
\begin{enumerate}
	\item $n$ -- shard's round number of type $\uint{64}$
	\item $e$ -- shard's epoch number of type $\uint{64}$
	\item $h_-$ -- last-certified root hash
	\item $\mathsf{SR}_-$ -- statistical record of the previous epoch
	\item $\mathsf{SR}$ -- statistical record of the current epoch, initially (at each epoch) $(0,0,0,0,0)$
	\item $\mathcal{V}$ -- validators of the shard, a set of identifiers, each of type $\{0,1\}^\ast$
	\item $\nu_\ell$ --  leader identifier of type $\{0,1\}^\ast$ (it is assumed that $\nu_\ell\in \mathcal{V}$)
	\item $UC_-$ -- last created unicity certificate

\subsection{Shard Tree}\label{se:shard-tree}

For a partition $\beta$, let $\mathcal{SH}_\beta = \mathcal{CD}[\beta].\mathcal{SH}$, and
$\mathcal{IRT}_\beta$ be of type $(\mathbb{IR},\hashtype)[\mathcal{SH}_\beta]$, i.e. for
every $\beta\in\mathcal{C}$ and $\sigma\in\mathcal{SH}_\beta$, $\mathcal{IRT}_\beta[\sigma]=(\mathcal{IR},h_t)$ (for some $\mathcal{IR}$ and $h_t$).

If there is no input from a shard to certify then $\mathcal{IRT}_\beta[\sigma] = \mathcal{IRT}_\beta[\sigma]_-$, that is, the value from the previously built Shard Tree is used. If there is no previous value then $\mathcal{IRT}_\beta[\sigma] = \zerohash$.

Shard tree\index{shard tree} for a partition $\beta$ is a function $\chi_\beta \colon \overline{\mathcal{SH}_\beta} \to \hashtype$ such that:
\begin{enumerate}
	\item If $\sigma\in\mathcal{SH}_\beta$, then $\chi_\beta(\sigma) = H(\mathcal{IRT}_\beta[\sigma]) =H(\mathcal{IRT}_\beta[\sigma].\mathcal{IR} \mathbin{\|} \mathcal{IRT}_\beta[\sigma].h_t)$.
	\item If $\sigma\in \overline{\mathcal{SH}_\beta}\backslash\mathcal{SH}_\beta$, then
		$\chi_\beta(\sigma) = H(\chi_\beta(\sigma\| 0)\, \mathbin{\|} \,\chi_\beta(\sigma\| 1))$.
\end{enumerate}
The value $\chi_\beta(\lfloor\!\rfloor)$ is called the root hash of the shard tree.

\emph{Shard tree certificate} for a shard $\sigma\in \mathcal{SH}_\beta$ is a sequence $h^s_1, \ldots, h^s_m$ of sibling hash values of type $\hashtype$, where $m=|\sigma|$ (the number of bits in $\sigma$); see Sec.~\ref{se:shard-tree-cert}.

\subsubsection{Shard Tree Creation: $\mathsf{CreateShardTree}$}\label{se:create-shard-tree}\index{functions!CreateShardTree}

\textbf{Input}:
\begin{enumerate}
	\item $\mathcal{SH}$ -- sharding scheme of type $\mathbb{SH}$
	\item $\mathcal{IRT}$ -- shard-specific data of type $(\mathbb{IR},\hashtype)[\mathbb{SH}]$
\end{enumerate}
\textbf{Output}: $\chi$ -- shard tree of type $\overline{\mathcal{SH}}\to \hashtype$

\textbf{Computation}:
$\chi\gets \bot$, $\mathsf{genST}(\emptystr)$

where $\mathsf{genST}$ is the following recursive function of type $\bitstr\to \hashtype$ with side effects:
\medskip

$\mathsf{genST}(\sigma)$:
\begin{enumerate}
	\item \textbf{if} $\sigma\in \mathcal{SH}$, \textbf{then store}  $\chi(\sigma) \gets H(\mathcal{IRT}[\sigma])$ and \textbf{return} $\chi(\sigma)$.
	\item\textbf{if} $\sigma\in \overline{\mathcal{SH}}\backslash\mathcal{SH}$, \textbf{then store}
		$\chi(\sigma) \gets H(\mathsf{genST}(\sigma\| 0) \mathbin{\|} \mathsf{genST}(\sigma\| 1))$ and \textbf{return} $\chi(\sigma)$
\end{enumerate}

For the single shard case, the shard tree is $\{(\emptystr, H(\mathcal{IRT}[\sigma]))\}$, i.e. it only has a single record for the root hash $\chi(\emptystr)=H(\mathcal{IRT}[\sigma])$.

\subsection{Unicity Tree}\index{Unicity Tree}

Unicity Tree is an indexed Merkle tree that aggregates the state of all partitions in the network.

\subsubsection{Creation: $\mathsf{CreateUnicityTree}$}\label{se:create-unicity-tree}\index{functions!CreateUnicityTree}

\textbf{Input}:
\begin{enumerate}
	\item $\mathcal{C}$ -- set of partition identifiers of type $\mathbb{C}$
	\item $\mathcal{CD}$ -- partition description of type $\mathbb{CD}[\mathcal{C}]$
	\item $\mathcal{IH}$ -- input hashes of type $\hashtype[\mathcal{C}]$
\end{enumerate}
\textbf{Output}: $r$ -- unicity tree root hash of type $\hashtype$

\textbf{Computation}:
\begin{algorithmic}
	\State $n \gets \len{\mathcal{C}}$ \Comment{Number of partitions}
	\State $C \gets \mathsf{sorted}(\mathcal{C})$ \Comment{Sorted list}
	\For{$i \gets 1 \ldots n$}
		\State $x_i \gets H(\mathcal{IH}[C_i] \mathbin{\|} H(\mathcal{CD}[C_i]))$
	\EndFor
	\State \Return $\Call{\textsc{index\_tree\_root}}{(C_1, x_1), (C_2, x_2), \ldots, (C_n, x_n)}$ \Comment{Sec.~\ref{sec:index-tree-root}}
\end{algorithmic}

\section{State of the BFT Core}\label{sec:bft-state}

\emph{State of the BFT Core}\index{BFT Core!BFT Core state} is a tuple $(\alpha, n, e, P, N, \mathcal{T}, \mathcal{C}, \mathcal{CD}, \mathcal{SI})$, where:
\begin{enumerate}
	\item $\alpha$ -- network identifier of type $\mathbb{A}$
	\item $n$ -- BFT Core's round number of type $\uint{64}$
	\item $e$ -- BFT Core's epoch number of type $\uint{64}$
	\item $P$ -- root history accumulator peak list, of type $\hashtype^\ast$, with one entry per $1$-bit of $N$ (Sec.~\ref{sec:root-history})
	\item $N$ -- root history accumulator size of type $\uint{64}$, equal to $n$ at the start of a round and to $n+1$ after that round's root has been appended
	\item $\mathcal{T}$ -- unicity trust base of type $\mathbb{UB}$
	\item $\mathcal{C}$ -- set of partition identifiers, with elements of type $\mathbb{C}$
	\item $\mathcal{CD}$ -- partition descriptions of type $\mathbb{CD}[\mathbb{C}]$
	\item $\mathcal{SI}$ -- shard info of type $\mathbb{SI}[\mathbb{C},\{0,1\}^\ast]$
\end{enumerate}

Epoch number\index{$e$ (epoch number)} can be interpreted as the version number of some shard's or BFT Core's configuration. It is used by supporting layers like orchestration and consensus. On static configuration, the epoch is $0$.

\section{Messages of the BFT Core}

\subsection{Certification Request}\label{certification-request}

\emph{Certification Request} (CR)\index{certification request (CR)} of a shard is a message $\langle \alpha, \beta, \sigma, \nu; \mathcal{IR}, \ell_B, \ell_S, [\pi_{CP}]; s \rangle$, where:
\begin{enumerate}
	\item $\alpha$ -- network identifier of type $\mathbb{A}$
	\item $\beta$ -- partition identifier of type $\mathbb{C}$
	\item $\sigma$ -- shard identifier of type $\mathbb{SH}$
	\item $\nu$ -- validator identifier (aggregation layer node identifier) of type $\{0,1\}^\ast$
	\item $\mathcal{IR}$ -- shard input record of type $\mathbb{IR}$
	\item $\ell_B$ -- number of added new SMT leaves during the round, type $\uint{64}$
	\item $\ell_S$ -- SMT memory usage in bytes of type $\uint{64}$
	\item $\pi_{CP} \lor \bot$ -- consistency proof of type $\mathbb{CP}$ (Sec.~\ref{sec:consistency-proof})
	\item $s$ -- signature authenticating the message
\end{enumerate}

Certification requests are sent to the BFT Core by the aggregation layer nodes (validators) implementing the shards.

\subsection{Certification Response}\label{certification-response}

\emph{Certification Response} (CReS)\index{certification response (CReS)} of a shard is a message $\langle \alpha, \beta, \sigma, \mathsf{TE}; UC \rangle$, where:
\begin{enumerate}
	\item $\alpha$ -- network identifier of type $\mathbb{A}$
	\item $\beta$ -- partition identifier of type $\mathbb{C}$
	\item $\sigma$ -- shard identifier of type $\mathbb{SH}$
	\item $\mathsf{TE}$ -- technical record of type $\mathbb{TE}$
	\item $UC$ -- certified unicity certificate
\end{enumerate}

Certification response is sent by the BFT Core to the nodes of an aggregation layer nodes as a response to a certification request message. This is an asynchronous message: response is not immediate, and there can be multiple subsequent responses.

\section{Functional Description of the BFT Core}\label{sec:bft-functional}

\index{BFT Core!functional description}
During every round, the BFT Core receives certification requests from the shards of partitions
$\beta \in \mathcal{C}$.

The BFT Core certifies the SMT root hashes provided by the aggregation layer nodes. Each shard maintains an SMT for its portion of the key space. When aggregation layer nodes process Unicity Service Requests (as specified in Sec.~\ref{sec:request-validation}), they update their SMTs by setting leaves. The BFT Core certifies these updates by:
\begin{enumerate}
	\item Receiving certification requests containing the new SMT root hash $h$ and previous root hash $h'$
	\item Verifying the consistency proof $\pi_{CP}$ that proves correct SMT manipulation
	\item Certifying the new root hash via the Unicity Certificate
\end{enumerate}

As every shard $\sigma$ of a partition $\beta$ is implemented by a redundant distributed system with certain number $m=|\mathcal{SI}[\beta,\sigma].\mathcal{V}|$ of validator machines, it is possible that several certification requests $\mathsf{CR}_{\beta,\sigma}$ with the same $\mathsf{CR}_{\beta,\sigma}.\mathcal{IR}.h'$ but different $\mathsf{CR}_{\beta,\sigma}.\mathcal{IR}.h$ are received. This is solved by a majority voting mechanism requiring that
%\begin{enumerate}
%	\item
	a required majority, at least $\lfloor m/2\rfloor + 1$ of the dedicated validators, send $\mathsf{CR}_{\beta,\sigma}$ with an identical value of $\mathsf{CR}_{\beta,\sigma}.\mathcal{IR}.h$.
%	\item The leader $\mathcal{SI}[\beta,\sigma].\nu_\ell$ is in the majority
%\end{enumerate}
It is possible that not every shard sends its shard input record to the BFT Core during the round, and the majority voting may fail (see the Consensus specification for details).


For every incoming certificate request $\mathsf{CR}=\langle \alpha, \beta, \sigma, \nu; \mathcal{IR}, \ell_B, \ell_S, [\pi_{CP}]; s \rangle$ (Sec.~\ref{certification-request}) the following checks are made
(if any of them fails, $\mathsf{CR}$ is discarded):
\begin{enumerate}
\item $\mathsf{CR}.\alpha = \alpha$ -- request came from the same network instance
\item $\mathsf{CR}.\beta\in \mathcal{C}$ and $\sigma\in \mathcal{CD}[\mathsf{CR}.\beta].\mathcal{SH}$ -- request came from a legitimate shard of a registered partition
\item $\mathsf{CR}.\nu\in \mathcal{SI}[\mathsf{CR}.\beta, \mathsf{CR}.\sigma].\mathcal{V}$ -- request came from an authorized aggregation layer node
\item $\mathsf{CR}.\mathcal{IR}.n=\mathcal{SI}[\beta,\sigma].n + 1$ -- round number is correctly incremented
\item $\mathsf{CR}.\mathcal{IR}.e=\mathcal{SI}[\beta,\sigma].e$ -- epoch number matches
\item $\mathsf{CR}.\mathcal{IR}.h'=\mathcal{SI}[\beta,\sigma].h_-$ -- previous round's SMT root hash in IR matches the recorded one
	\item $\mathcal{CD}[\beta].\gamma_{CP}(\mathsf{CR}.\mathcal{IR}, \mathsf{CR}.\pi_{CP})$ -- consistency proof verification (Sec.~\ref{sec:consistency-proof}) succeeds: verify $\mathsf{VerifyConsistencyProof}(\mathsf{CR}.\pi_{CP}, B, \mathsf{CR}.\mathcal{IR}.h', \mathsf{CR}.\mathcal{IR}.h) = \TRUE$ and $|B| = \mathsf{CR}.\ell_B$ (batch size matches).
\item $\mathsf{CR}.\mathcal{IR}.t = \mathcal{SI}[\beta, \sigma].UC_-.C^\mathsf{r}.t$ -- time reference is equal to the time field of the previous unicity seal
\end{enumerate}
Only one (majority-voted) certificate request (denoted by $\mathsf{CR}_{\beta,\sigma}$) is accepted from every shard.

When the BFT Core's round $n$ is completed, then:
\begin{enumerate}
	\item For every $\beta\in\mathcal{C}$, and $\sigma\in \mathcal{SH}_\beta$ with accepted certificate request \footnote{Please refer to the Consensus chapter for details; notably a ``request'' may be induced for technical reasons}:
	\begin{enumerate}
		\item $\mathcal{SI}[\beta, \sigma].n \gets \mathsf{CR}.\mathcal{IR}.n$
		\item $\mathcal{SI}[\beta, \sigma].h_- \gets \mathsf{CR}.\mathcal{IR}.h$
		\item $\mathcal{SI}[\beta, \sigma].\mathsf{SR}.n_e \gets \mathcal{SI}[\beta, \sigma].\mathsf{SR}.n_e + 1$
		\item $\mathcal{SI}[\beta, \sigma].\mathsf{SR}.\overline{\ell}_B \gets \mathcal{SI}[\beta, \sigma].\mathsf{SR}.\overline{\ell}_B + \mathsf{CR}.\ell_B$
		\item $\mathcal{SI}[\beta, \sigma].\mathsf{SR}.\overline{\ell}_S \gets \mathcal{SI}[\beta, \sigma].\mathsf{SR}.\overline{\ell}_S + \mathsf{CR}.\ell_S$
		\item $\mathcal{SI}[\beta, \sigma].\mathsf{SR}.\hat{\ell}_B \gets \max\{\mathcal{SI}[\beta, \sigma].\mathsf{SR}.\hat{\ell}_B, \mathsf{CR}.\ell_B\}$
		\item $\mathcal{SI}[\beta, \sigma].\mathsf{SR}.\hat{\ell}_S \gets \max\{\mathcal{SI}[\beta, \sigma].\mathsf{SR}.\hat{\ell}_S, \mathsf{CR}.\ell_S\}$
		\item The leader for next round: \\
			$\mathcal{SI}[\beta, \sigma].\nu_\ell \gets \Call{leaderfunc}{UC_-, \mathcal{SI}[\beta, \sigma].\mathcal{V}}$
		\item Technical record: \\
			$\mathcal{TE}_{\beta,\sigma} \gets (\mathcal{SI}[\beta,\sigma].n+1, \mathcal{SI}[\beta,\sigma].e, \mathcal{SI}[\beta,\sigma].\nu_\ell, h_\mathsf{sr})$ \;, \\
			where $h_\mathsf{sr}=H(\mathcal{SI}[\beta,\sigma].\mathsf{SR}_-, \mathcal{SI}[\beta,\sigma].\mathsf{SR})$
	\end{enumerate}

	\item For every registered partition $\beta\in\mathcal{C}$, the collected certification requests $\mathsf{CR}_{\beta,\sigma}$ are converted to a temporary data structure $\mathcal{IRT}_\beta$ of type $(\mathbb{IR},\hashtype)[\mathcal{SH}_\beta]$, where $\mathcal{SH}_\beta=\mathcal{CD}[\beta].\mathcal{SH}$,
	and $\mathcal{IRT}_\beta[\sigma]=(\mathsf{CR}_{\beta,\sigma}.\mathcal{IR}, H(\mathcal{TE}_{\beta,\sigma}))$; \\
	if there is no request then respective leaf repeats its previous value. If there is no previous value, the leaf is initialized to $\zerohash$.
	\item For every $\beta\in\mathcal{C}$, the shard tree $\chi_\beta$  (Sec.~\ref{se:shard-tree}) is created by the function call $\chi_\beta\gets\mathsf{CreateShardTree}(\mathcal{SH}_\beta,\mathcal{IRT}_\beta)$ (Sec.~\ref{se:create-shard-tree}).
	\item A temporary data structure $\mathcal{IH}$ of type $\hashtype[\mathcal{C}]$ is created such that $\mathcal{IH}[\beta]\gets \chi_\beta(\emptystr)$ for every $\beta\in\mathcal{C}$, i.e. $\mathcal{IH}$ contains the root hashes of the shard trees.
	\item The root of unicity tree is computed as $r \gets \mathsf{CreateUnicityTree}(\mathcal{C}, \mathcal{CD}, \mathcal{IH})$ (Sec.~\ref{se:create-unicity-tree})
	\item Unicity seal $C^\mathsf{r}=(\alpha, n, e, t, r, a; s )$ is created, where $t\gets\mathsf{time}()$ is the current time, $a$ is the root history accumulator after appending $r$ (Sec.~\ref{sec:root-history}), and $s$ is a "signature" on all other fields. The form of $s$ depends on the used consensus mechanism.
	\item For every $\beta\in\mathcal{C}$, the unicity tree certificate $C^\mathsf{uni}_\beta$ is created by the function call $C^\mathsf{uni}_\beta\gets \mathsf{CreateUnicityTreeCert}(\beta, \mathcal{C}, \mathcal{CD}, \mathcal{IH})$ (Sec.~\ref{se:create-unicity-tree-cert})
	\item For every $\beta\in\mathcal{C}$, and $\sigma\in \mathcal{SH}_\beta$:
	\begin{enumerate}
		\item The shard tree certificate $C^\mathsf{shard}_{\beta,\sigma}$ (Sec.~\ref{se:shard-tree-cert}) is created by the function call $C^\mathsf{shard}_{\beta,\sigma}\gets \mathsf{CreateShardTreeCert}(\sigma,\chi_\beta)$ (Sec.~\ref{se:create-shard-tree-cert})
		\item The unicity certificate $UC_{\beta,\sigma}=(\mathcal{IRT}_\beta[\sigma].\mathcal{IR},\mathcal{IRT}_\beta[\sigma].h_t, C^\mathsf{shard}_{\beta,\sigma}, C^\mathsf{uni}_\beta, C^\mathsf{r})$ (Sec.~\ref{se:unicity-certificate}) and the certification response $\mathsf{CReS}_{\beta,\sigma}=\langle \alpha,\beta,\sigma; UC_{\beta,\sigma}, \mathcal{TE}_{\beta,\sigma}\rangle$ are composed (if the shard input have changed, including the induced change of a repeat certification after the shard's \texttt{t2} timeout)
		\item Independently of $changes$, the seal $C^\mathsf{r}$ itself is published to the aggregation layer, so that the sequence of Unicity Tree roots reaches it without gaps (Sec.~\ref{sec:root-history-service})
		\item The last unicity certificate field is updated by $\mathcal{SI}[\beta,\sigma] UC_-\gets UC$ (if the shard input have changed).
	\end{enumerate}
	\item The round number is updated by $n\gets n+1$; the accumulator frontier was advanced when $a$ was computed.
\end{enumerate}

When a shard's (identified by $\beta$, $\sigma$) epoch with at least one non-empty round ends, the following assignments are executed:
\begin{enumerate}
	\item $\mathcal{SI}[\beta,\sigma].\mathsf{SR}_- \gets \mathcal{SI}[\beta,\sigma].\mathsf{SR}$
	\item $\mathcal{SI}[\beta,\sigma].\mathsf{SR} \gets (0,0,0,0,0)$
	\item $\mathcal{SI}[\beta,\sigma].e \gets \mathcal{SI}[\beta,\sigma].e + 1$
	\item The new validator set $\mathcal{SI}[\beta,\sigma].\mathcal{V}$ is chosen
\end{enumerate}
