\chapter{Encodings}\label{app:encodings}

\section{CBOR}

Most data structures on the Unicity platform are serialized in the Concise Binary Object Representation (CBOR), as defined in the IETF~RFC~8949\footnote{\url{https://www.rfc-editor.org/rfc/rfc8949}}.

For data to be hashed or signed, the deterministic encoding rules (as defined in Sec.~4.2 of the RFC~8949) must be used.

\section{Tuples}

Tuples are encoded as CBOR arrays in the natural way: a tuple $T$ consisting of $n$ elements, denoted $(T_1, T_2, \ldots, T_n)$ or $\langle T_1, T_2, \ldots, T_n \rangle$ in the specification, is encoded as $n$-element CBOR array with $T_1$ the first elment, $T_2$ the second element, and so on.

Within a fixed tuple shape, an optional element with no value, denoted $\bot$ in the specification, is not omitted from the array, but encoded as the CBOR simple value \texttt{null}. Each version of a structure therefore has exactly one tuple shape and one element count, and an optional element occupies its position whether or not it carries a value.

\section{Bit-strings}

Bit-strings are not directly supported in CBOR. On the Unicity platform, a bit-string is encoded as follows:
\begin{enumerate}
\item First, one $1$-bit followed by zero to seven $0$-bits are appended to the original bit-string so that the total number of bits is a multiple of $8$.
\item Then, the padded result is encoded as a CBOR byte-string in the left-to-right, highest-to-lowest order.
\end{enumerate}

For example, the 12-bit string '0101\,1010\,1111' is first padded to the 16-bit string '0101\,1010\,1111\,1000', which is then encoded as the 3-byte sequence 0x425af8: \
\begin{tabular}{ll}
	\quad 0x42 & byte-string, length 2 \\
	\quad\quad 0x5a & the bits '0101\,1010' \\
	\quad\quad 0xf8 & the bits '1111' and the padding '1000'
\end{tabular}

\section{Hash Values}

Hash values, although frequently defined as general bit-strings in cryptographic theory, in practice always have bit-lengths divisible by 8 and are encoded as simple CBOR byte-strings with no padding.

\section{Unit Identifiers}

Unit identifiers are encoded as CBOR byte-strings.

\section{Time}

Time is expressed as the number of seconds since 1970-01-01 00:00:00 UTC and encoded as an unsigned integer. All days are considered to be exactly 86\,400 seconds long; leap seconds are ignored. Protocol decisions use certified time values and do not depend on a participant's local clock.

\section{Identifiers}

\textbf{Identifiers of Nodes} (validators) are expressed as hashes of compressed ECDSA public keys;
respective private key is controlled by the Node.

\textbf{Identifiers of Transaction Systems} are expressed as integers.

\section{Cryptographic Algorithms}

``ECDSA'' denotes the Elliptic Curve Digital Signature Algorithm using secp256k1 curve

``SHA-256'' denotes the SHA-2 hash algorithm with 256-bit output and ``SHA-512'' denotes the SHA-2 hash algorithm with 512-bit output; both are specified by NIST FIPS 180-4.

The list is non-exhaustive.


\section{BFT Records}\label{sec:bft-encoding}

The abstract records in the body have the following native encodings. Tags and versions are part of the bytes hashed. An input record is CBOR tag 39002 applied to
\[
[1,n,e,h',h,v,t,h_B,f,h_E].
\]
The byte-string fields $h',h,v,h_B,h_E$ preserve \texttt{null} separately from an empty byte string. A noninitial input record requires a present summary value and a nonzero timestamp. The whole input record cannot be \texttt{null}.

A technical record is the untagged array
\[
[n_r,e_r,\nu_\ell,h_\mathsf{sr},h_\mathsf{fee}].
\]
Its hash includes both accounting commitments. The native statistical record is the array of block count, cumulative fees, cumulative block size, cumulative state size, maximum block fee, maximum block size and maximum state size, in that order. The abstract statistical counters omit the two fee counters; their values must still be preserved when hashing the native record. A fee record is a map from validator identifiers to earned fees. Each accounting commitment hashes the deterministic encodings of the previous record followed by the current record.


The unicity certificate is tag 39001 over
\[
[1,IR,h_t,h_c,C^\mathsf{shard},C^\mathsf{uni},C^\mathsf{r}].
\]
The shard certificate is tag 39003 over $[1,\sigma,[h^s_1,\ldots,h^s_{|\sigma|}]]$; siblings are in leaf-to-root order and their count equals the shard identifier's bit length. The empty shard has an empty sibling array. The unicity-tree certificate is tag 39004 over $[1,\beta,[[\beta_2,h_2],\ldots,[\beta_\ell,h_\ell]]]$.

A shard leaf hashes, in sequence, the tagged input record, the technical-record hash byte string and the shard-configuration hash byte string. A shard internal node hashes the two child hash byte strings in left-to-right order. The value passed to the indexed tree for partition $\beta$ is the hash of the byte-string encoding of its shard-tree root; there is no additional partition-description hash in that value or in the unicity-tree certificate.


\subsection{Unicity Seal}\label{sec:seal-encoding}

A seal is CBOR tag 39005 over $[1,\alpha,n_r,e_r,t_r,r_-,r,s]$, where $s$ is a map from validator identifiers to signature byte strings. The signing preimage is the deterministic encoding of the same tagged array with $s=\texttt{null}$. The signature slot is not removed. Full seal bytes retain the entire signature map.

In the distributed implementation, the field named \texttt{PreviousHash}, denoted $r_-$, is the hash of the QC's \texttt{VoteInfo}. QC verification recomputes that hash before checking the signatures. It is not the previous unicity-tree root.

\subsection{Recoverable Signatures}\label{sec:recoverable-signatures}

The seal and standard predicate signature profile is exactly 65 bytes $R\|S\|V$, with big-endian 32-byte scalars. For secp256k1 group order $q$, require $1\le R<q$, $1\le S\le\lfloor q/2\rfloor$ and $V\in\{0,1,2,3\}$. Verification must recover the independently expected public key using $V$. Values 27/28, chain-ID conversions and compact 64-byte signatures are not accepted by this profile. A signature failing these checks contributes no vote to a seal quorum.


\section{Inclusion Proof Encoding}\label{sec:inclusion-encoding}

An inclusion proof is tag 39033 over
\[
[1,Q,\tau,\mathsf{bstr}(C^\mathsf{inc}),UC],
\]
where $Q$ is the tagged certification data, $\tau$ is the original leaf reference time, and the certificate byte string is specified in Appendix~\ref{app:rsmt}. The state identifier and $\lambda(Q,\tau)=\mathsf{SHA256}(\mathsf{CBOR}([\txhash,\tau]))$ are derived verification inputs, not additional array elements. A later UC does not change $\tau$.


\section{Empty Roots and Structural Validation}\label{sec:empty-root-encoding}

The empty aggregation state root $\bot$ is encoded as CBOR \texttt{null} in the input record. A 32-byte all-zero digest is an ordinary root, not the empty-tree sentinel; an empty byte-string root is invalid. The UC and input record remain present. An empty non-inclusion certificate is a zero-length byte string and is admissible only for that authenticated empty root.

Decoders and path evaluators reject absent required records, null path entries, malformed identifiers and inconsistent path lengths before dereferencing or hashing them. These requirements do not prohibit the nullable input-record fields or the valid zero-length shard path.
