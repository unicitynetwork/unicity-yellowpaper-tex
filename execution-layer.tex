\chapter{Execution Layer}

The execution layer handles off-chain transaction processing and business logic. Tokens are self-contained digital assets transferred peer-to-peer between users. Only cryptographic commitments to state transitions are submitted to the Aggregation Layer for double-spending prevention. Transaction execution and verification are performed by the interested parties (recipients), not by consensus participants. This design moves computational overhead off-chain while maintaining trustless guarantees against double-spending.

\section{Execution Model}

In the Unicity execution model, digital assets called \emph{tokens}\index{token} are bearer instruments: whoever holds the token data and can satisfy the spending condition is the owner. Transactions occur directly between parties using any communication channel, with the Unicity Service consulted only to prevent double-spending.

The model relies on three key principles:
\begin{enumerate}
	\item \textbf{Off-chain execution}: Transaction creation, validation, and verification happen between sender and recipient without consensus participation.
	\item \textbf{On-chain uniqueness}: The Unicity Service maintains an append-only registry of spent token states, ensuring each state can be spent at most once.
	\item \textbf{Recipient verification}: The recipient (relying party) independently verifies the complete token history before accepting a transfer.
\end{enumerate}

\subsection{Token Lifecycle}\label{sec:token-lifecycle}

A token progresses through the following stages:
\begin{description}
\item[Minting]\index{mint transaction} Creates a new token with an initial state. Minting uses a publicly known minting key pair $(\mathsf{sk}_\mathsf{mint}, \mathsf{pk}_\mathsf{mint})$ which MAY be network specific.
\item[Transfer]\index{transfer transaction} Changes ownership by spending the current state and creating a new state with a new owner predicate.
\item[Compression]\index{token compression} Compacts the token by replacing a prefix of its transfer history, and the ancestor tokens its genesis names, with a succinct proof of validity. Unlike the other stages, compression is a change of \emph{representation} rather than a transaction: no state is spent, no state is created, the token identifier is unchanged and the Unicity Service is not involved. See Sec.~\ref{sec:token-compression}.
\item[Split]\index{split transaction} (Fungible tokens only.) Burns the original token and mints new tokens, with a cryptographic value conservation proof ensuring no value is created or destroyed. See Sec.~\ref{sec:token-splitting}.
\item[Burn]\index{burn transaction} Permanently locks a token by transferring it to a burn predicate that cannot be unlocked. See Sec.~\ref{sec:burn-transaction}.
\end{description}

\subsection{Token State}\label{sec:token-state}

\index{token!state}
A \emph{token state} is a pair $(\predi, \sthash)$, where:
\begin{itemize}
	\item $\predi$ -- the spending predicate (defines who can spend the token); see Sec.~\ref{sec:predicates}
	\item $\sthash \in \hashtype$ -- the state hash, linking the token's transaction history
\end{itemize}

The \emph{state identifier}\index{state identifier}\index{$\mathsf{sid}$ (state identifier)} is the key used in the Unicity Service registry:
\[
\mathsf{sid} = H(\predi, \sthash)
\]

When a transaction with random value $x \gets \{0,1\}^\ell$ is executed, the next state hash is computed as:
\[
\sthash' = H(\sthash, x)
\]

The randomness of \emph{state mask}\index{state mask} $x$ ensures that the next state identifier $H(\predi', \sthash')$ is unpredictable, preventing the Unicity Service from linking consecutive states of the same token.

The state mask $x$ MUST be sampled with at least 128 bits of min-entropy.

\subsection{Token Structure}\label{sec:token-structure}

A \emph{token}\index{token!structure} is a self-contained data structure carrying its complete provenance. Any party can independently verify the entire history without consulting external state. Formally, a token is a sequence:
\[
\mathcal{L} = (T_0^\mathsf{cert}, T_1^\mathsf{cert}, \ldots, T_n^\mathsf{cert})
\]
where $T_0^\mathsf{cert}$ is a certified mint transaction and $T_i^\mathsf{cert}$ for $i > 0$ are certified transfer transactions.

A token has two compressible dimensions, both treated in Sec.~\ref{sec:token-compression} and neither of which alters a certified transaction: its own transfer sequence, a prefix of which MAY be replaced by a \emph{token attestation} $\mathcal{K}$; and its \emph{provenance}, the ancestor tokens its genesis reason names, which MAY be supplied as attestations instead of in full. Either result denotes the same token in the same state, is verified by the same function $\Call{VerifyToken}{}$, and is spent by an ordinary transfer.

\subsubsection{Mint Transaction}\label{sec:mint-tx}

\index{mint transaction!structure}
A \emph{certified mint transaction} is a tuple $(T_0, \pi_0)$, where $T_0 = (\sthash, D_\mathsf{mint})$ and
\[
D_\mathsf{mint} = (\alpha, \predi', \mathsf{salt}, \mathsf{ty}, \mathsf{reason}, \auxd') .
\]
\begin{itemize}
	\item $\sthash = H(\mathsf{id}, \mathsf{MINT\_SUFFIX})$ -- source state hash, for state identifier derivation
	\item $D_\mathsf{mint}$ -- mint transaction data, containing in this order:
	\begin{itemize}
		\item $\alpha \in \mathbb{A}$ -- network identifier, binding the token to a specific Unicity network instance
		\item $\predi'$ -- spending predicate of the first owner
		\item $\mathsf{salt} \in \{0,1\}^{256}$ -- token identifier salt, chosen by the minter and required to be unique among the minter's salt choices (e.g.\ by uniform random sampling or by a local counter); $\mathsf{salt}$ has no masking role and need not be high-entropy
		\item $\mathsf{ty}$ -- token type, classifying the token category, defining its mandatory validation rules
		\item $\mathsf{reason}$ -- mint reason; content depends on the token type. Justifies minting this token, e.g., by proving minting authority
		\item $\auxd'$ -- auxiliary payload (application-specific; e.g. asset value for fungible tokens)
	\end{itemize}
	\item $\pi_0$ -- inclusion proof from the Unicity Service
\end{itemize}

The reason is part of the certified transaction data and therefore fixed forever by $\txhash$. Every reason format that depends on other tokens accordingly states that dependency \emph{by identifier} rather than by embedding the tokens, so that the evidence for them travels beside the token and may be re-encoded; this is the \emph{reference form} of Sec.~\ref{sec:token-evidence}, and it is what makes a token's provenance compressible.

The \emph{token identifier}\index{token!identifier} is derived as
\[
\mathsf{id} \;:=\; H(\mathsf{salt}, \alpha) \;\in\; \idtype \;.
\]
This ensures that two tokens minted on different networks cannot induce colliding state identifiers.

$\mathsf{MINT\_SUFFIX}$\index{MINT\_SUFFIX} is a fixed domain separator constant. The minting key pair $(\mathsf{sk}_\mathsf{mint}, \mathsf{pk}_\mathsf{mint})$ is a public constant; it serves only to provide a uniform request interface with the Unicity Service. Values: Appendix~\ref{app:el-constants}.

\paragraph{Certifying a mint transaction} $T_0 = (\sthash, D_\mathsf{mint})$:
\begin{enumerate}
	\item $\txhash \gets H(D_\mathsf{mint})$
	\item $h_T \gets H(\sthash, \txhash)$
	\item $\sigma \gets \mathsf{Sign}(\mathsf{sk}_\mathsf{mint}, h_T)$
	\item $Q \gets (\mathsf{pk}_\mathsf{mint}, \sthash, \txhash, \sigma)$
	\item $\pi_0 \gets \unisrv(Q)$
\end{enumerate}

\paragraph{Verifying a certified mint transaction} $(T_0, \pi_0)$ against trust base $\mathcal{T}$, using known, fixed mint keys:
\begin{enumerate}
	\item require $T_0.D_\mathsf{mint}.\alpha = \pi_0.UC.C^\mathsf{r}.\alpha = \mathcal{T}.\alpha$
	\item derive $\mathsf{id} \gets H(T_0.D_\mathsf{mint}.\mathsf{salt}, T_0.D_\mathsf{mint}.\alpha)$;\; require $T_0.\sthash = H(\mathsf{id}, \mathsf{MINT\_SUFFIX})$
	\item $\txhash \gets H(D_\mathsf{mint})$;\; require $\txhash = \pi_0.\txhash$
	\item $\mathcal{V}(H(\mathsf{pk}_\mathsf{mint}, \sthash), \txhash, \pi_0, \mathcal{CD}_\beta, \mathcal{T}) = 1$
	\item Mint authorization check on $\mathsf{ty}$, $\mathsf{reason}$ and $\auxd'$: mint reason validity and auxiliary payload format and semantics, dispatched by token type (Sec.~\ref{sec:mint-authorization}, Alg.~\ref{alg:mint-auth})
\end{enumerate}

Correctness of the token id derivation is enforced implicitly by step~2: $\sthash$ is bound to $\mathsf{id}$ by the source-state-hash check, and $\mathsf{id}$ is recomputed from $(\mathsf{salt}, \alpha)$.


\subsubsection{Transfer Transaction}\label{sec:transfer-tx}

\index{transfer transaction!structure}
A \emph{certified transfer transaction} is a tuple $(T, u, \pi)$, where $T = (\sthash, D)$:
\begin{itemize}
	\item $D = (\predi', x, \auxd')$ -- transaction data:
	\begin{itemize}
		\item $\predi'$ -- spending predicate of the next owner
		\item $x \gets \{0,1\}^\ell$ -- random value for state hash derivation
		\item $\auxd'$ -- auxiliary data for the next state
	\end{itemize}
	\item $u$ -- unlocking argument satisfying the current predicate $\predi$
	\item $\pi$ -- inclusion proof from the Unicity Service
\end{itemize}

\paragraph{Certifying a transfer transaction} $T = (\sthash, D)$ in the current state $(\predi, h)$:
\begin{enumerate}
	\item $\txhash \gets H(D)$
	\item $h_T \gets H(\sthash, \txhash)$
	\item Create $u$ such that $\predi(\tau_\mathsf{exp}, h_T, u) = 1$ for an expected system time $\tau_\mathsf{exp}$
	\item $Q \gets (\predi, \sthash, \txhash, u)$
	\item $\pi \gets \unisrv(Q)$
\end{enumerate}

\paragraph{Verifying a certified transfer transaction} $(T, u, \pi)$ in state $(\predi, h)$:
\begin{enumerate}
	\item $T.\sthash = h$ \quad (state hash matches expected)
	\item $\pi.UC.C^\mathsf{r}.\alpha = \mathcal{T}.\alpha$ \quad (inclusion proof is from the same network as the trust base)
	\item $\txhash \gets H(T.D)$;\; require $\txhash = \pi.\txhash$ \quad (transaction data binds to the certified SMT leaf)
	\item $\predi(\mathsf{time}(\pi), H(\sthash, \txhash), u) = 1$ \quad (predicate satisfied)
	\item $\mathcal{V}(H(\predi, T.\sthash), \txhash, \pi, \mathcal{CD}_\beta, \mathcal{T}) = 1$ \quad (inclusion proof valid and certified by the correct shard)
	\item Additional token type-specific checks (Sec.~\ref{sec:token-types})
\end{enumerate}

\subsection{Token Verification}\label{sec:token-verification}

\index{token!verification}\index{functions!VerifyToken}
$\mathsf{VerifyToken}$ -- token verification function of type $\mathbb{L} \times \mathbb{UB} \to \bool$

\textbf{Input}:
\begin{enumerate}
	\item $\mathcal{L} = (G, [\mathcal{K}], T_{m+1}^\mathsf{cert}, \ldots, T_n^\mathsf{cert})$ -- token, where the optional attestation $\mathcal{K}$ stands for transfers $1 \ldots m$ (Sec.~\ref{sec:token-compression}); an uncompressed token omits $\mathcal{K}$ and has $m = 0$. The genesis $G$ is the certified mint transaction $T_0^\mathsf{cert}$, or, when $\mathcal{K}$ is present and anchors it, the bare mint data $D_\mathsf{mint}$. The watermark $m$ is implicit in the representation, not a stored field
	\item $\mathcal{T}$ -- trust base
\end{enumerate}

\textbf{Output}: \TRUE or \FALSE

\textbf{Computation}:
\begin{algorithmic}[0]
	\State $D_\mathsf{mint} \gets$ the mint data of $G$
	\If {$D_\mathsf{mint}.\alpha \ne \mathcal{T}.\alpha$} \Return \FALSE \EndIf
	\If {$\mathcal{K}$ present}
		\If {$\Call{VerifyAttestation}{\mathcal{K}, \mathcal{T}, \Gamma} = \bot$} \Return \FALSE \EndIf
		\If {$\mathcal{K}$ does not bind to $D_\mathsf{mint}$ as in Sec.~\ref{sec:attestation}} \Return \FALSE \EndIf
		\State $\predi^{m} \gets \decpred(\mathcal{K}.e)$;\quad $h^{m} \gets \mathcal{K}.h$ \Comment{carry restored from the proof}
	\Else
		\State \Parse $G$ \textbf{as} $(T_0, \pi_0)$
		\If {$\neg \Call{VerifyMintTransaction}{T_0, \pi_0, \mathcal{T}}$} \Return \FALSE \EndIf
		\State $\predi^0 \gets D_\mathsf{mint}.\predi'$
		\State $h^0 \gets H(H(D_\mathsf{mint}.\mathsf{salt}, D_\mathsf{mint}.\alpha), \mathsf{MINT\_SUFFIX})$
	\EndIf
	\For {$i \gets m+1 \ldots n$}
		\State \Parse $T_i^\mathsf{cert}$ \textbf{as} $(T_i, u_i, \pi_i)$
		\If {$\neg \Call{VerifyTransferTransaction}{T_i, u_i, \pi_i, \predi^{i-1}, h^{i-1}, \mathcal{T}}$} \Return \FALSE \EndIf
		\State $\predi^{i} \gets T_i.D.\predi'$
		\State $h^{i} \gets H(h^{i-1}, T_i.D.x)$
	\EndFor
	\State \Return \TRUE
\end{algorithmic}

$\Call{VerifyMintTransaction}{}$ and $\Call{VerifyTransferTransaction}{}$ are defined by verification steps in chapters \ref{sec:mint-tx}, \ref{sec:transfer-tx}; $\Call{VerifyAttestation}{}$ in Sec.~\ref{sec:attestation}.

Mint reasons name the source tokens they depend on. These are resolved from the evidence set accompanying the token and verified under the same trust base, verifier registry and cumulative resource limits as the outer token (Secs.~\ref{sec:token-evidence}, \ref{sec:nested-verification}).

\section{Programmable Spending Conditions}\label{sec:predicates}

Instead of restricting ownership to a single public key, the Unicity execution layer generalizes ownership to \emph{predicates}\index{predicate} -- programmable boolean functions that define the conditions under which a token state can be spent. This enables smart-contract-like functionality executed off-chain by relying parties rather than by consensus participants.

\subsection{Predicate Framework}\label{sec:predicate-framework}

\index{predicate!framework}
A \emph{predicate} $\predi_\mathsf{name}(\mathsf{par}; \cdot)$ is a boolean function with:
\begin{itemize}
	\item \textbf{Name} $\mathsf{name}$ -- identifies the predicate type
	\item \textbf{Parameters} $\mathsf{par}$ -- type-dependent configuration (e.g. a public key)
	\item \textbf{Arguments} $(\tau, m, u)$:
	\begin{itemize}
		\item $\tau \in \mathbb{T}$ -- system time, extracted from the Unicity Seal timestamp $C^\mathsf{r}.t_r$
		\item $m \in \hashtype$ -- message hash $H(\sthash, \txhash)$
		\item $u$ -- unlocking argument, structure depends on predicate type
	\end{itemize}
\end{itemize}

The predicate evaluates to $\predi_\mathsf{name}(\mathsf{par}; \tau, m, u) \in \{0, 1\}$.


\subsubsection{Time Reference}\label{sec:time-extraction}

\index{$\tau$}\index{time extraction}
Predicate evaluation must be deterministic and transparent: the Unicity Service (at certification time) and any later verifier (re-validating from an inclusion proof) must agree on the exact value of $\tau$ used. The system therefore fixes $\tau$ per Aggregator round, with the value coming through BFT Core consensus.

\paragraph{Per-round fixed reference time.}
The BFT Core's Unicity Seal carries a wall-clock round-creation timestamp $C^\mathsf{r}.t_r$ (Sec.~\ref{se:unicity-certificate}), with one-second precision, agreed by BFT Core consensus. When Aggregator assembles a certification request for its round $n{+}1$, it copies the timestamp from the Unicity Seal of the \emph{previous} UC it is extending into the Shard Input Record field $\mathcal{IR}.t$ (Sec.~\ref{shard-input-record}):
\[
	\mathsf{CR}.\mathcal{IR}.t \;\gets\; UC_-.C^\mathsf{r}.t_r
\]
where $UC_-$ is the last valid Unicity Certificate of that shard (which the Aggregator is \emph{extending}). This is the \emph{reference time for request validation} of the round being validated. All predicates evaluated against Unicity Service requests in that round use this single value as $\tau$.

Because the BFT Core issues a repeat certification after a shard's \texttt{t2} timeout (Sec.~\ref{sec:bft-functional}), $UC_-$ is at most \texttt{t2} old. The reference time is therefore stale by at most \texttt{t2}, irrespective of how long that shard has been idle.

\paragraph{BFT Core enforcement.}
The BFT Core verifies the Aggregator's choice of reference time as part of request admission (Sec.~\ref{certification-request}, check $\mathsf{CR}.\mathcal{IR}.t = \mathcal{SI}[\beta,\sigma].UC_-.C^\mathsf{r}.t_r$).

\paragraph{Extraction from inclusion proofs.}
Given an inclusion proof $\pi^\mathsf{inc} = (\mathsf{sid}, \txhash, C^\mathsf{inc}, UC)$, the \emph{system time} used for predicate evaluation is extracted as
\[
	\mathsf{time}(\pi^\mathsf{inc}) \;=\; UC.\mathcal{IR}.t
\]
This is the same value the Aggregator used when admitting the request -- the previous seal's $t_r$, copied into $\mathcal{IR}.t$ and BFT-verified. Re-validation by any later verifier is therefore deterministic and yields the identical predicate evaluation outcome.

Note that $UC.\mathcal{IR}.t \ne UC.C^\mathsf{r}.t_r$ in general: $\mathcal{IR}.t$ is the reference time of the round \emph{being} certified (taken from the prior seal), whereas $C^\mathsf{r}.t_r$ is the wall-clock time at which the new seal itself was produced. Predicate evaluation uses $\mathcal{IR}.t$.

\subsection{Standard Predicates}\label{sec:standard-predicates}

\subsubsection{Signature Predicate}

\index{predicate!signature ($\predi_\mathsf{sig}$)}
The \emph{signature predicate} $\predi_\mathsf{sig}(\mathsf{pk};\cdot)$ with a single public key $\mathsf{pk}$ as parameter is equivalent to digital signature verification. This is the basic ``pay to public key'' ownership model.

\begin{itemize}
	\item \textbf{Parameters}: $\mathsf{pk}$ (public key)
	\item \textbf{Unlocking argument}: $u = \sigma$ (digital signature)
	\item \textbf{Definition}: $\predi_\mathsf{sig}(\mathsf{pk}; \tau, m, \sigma) = 1$ iff $\mathsf{Verify}(\mathsf{pk}, m, \sigma) = 1$
\end{itemize}

\subsubsection{P2PKH Predicate}

\index{predicate!P2PKH ($\predi_\mathsf{p2pkh}$)}
The \emph{Pay-to-Public-Key-Hash} predicate $\predi_\mathsf{p2pkh}(h_\mathsf{pk};\cdot)$ stores only the hash of the public key, requiring the spender to reveal the full public key alongside the signature.

\begin{itemize}
	\item \textbf{Parameters}: $h_\mathsf{pk} \in \hashtype$ (public key hash)
	\item \textbf{Unlocking argument}: $u = (\mathsf{pk}, \sigma)$
	\item \textbf{Definition}: $\predi_\mathsf{p2pkh}(h_\mathsf{pk}; \tau, m, (\mathsf{pk}, \sigma)) = 1$ iff $H(\mathsf{pk}) = h_\mathsf{pk} \;\land\; \mathsf{Verify}(\mathsf{pk}, m, \sigma) = 1$
\end{itemize}

\subsubsection{P2SH Predicate}\label{sec:p2sh}

\index{predicate!P2SH ($\predi_\mathsf{p2sh}$)}
The \emph{Pay-to-Script-Hash} predicate $\predi_\mathsf{p2sh}(h_\predi;\cdot)$ generalizes P2PKH by storing the hash of an arbitrary predicate rather than just a public key hash. The recipient is identified by $h_\predi = H(\mathsf{CBOR}(\predi'))$, which provides a uniform-size recipient field regardless of predicate complexity and preserves privacy by hiding the predicate type until the token is spent.

\begin{itemize}
	\item \textbf{Parameters}: $h_\predi \in \hashtype$ (predicate hash)
	\item \textbf{Unlocking argument}: $u = (\predi', u')$ where $\predi'$ is the full predicate and $u'$ is its unlocking argument
	\item \textbf{Definition}: $\predi_\mathsf{p2sh}(h_\predi; \tau, m, (\predi', u')) = 1$ iff $H(\mathsf{CBOR}(\predi')) = h_\predi \;\land\; \predi'(\tau, m, u') = 1$
\end{itemize}

When spending, the full predicate $\predi'$ is revealed in the lock script field of the transfer transaction, and verifiers check that $H(\mathsf{CBOR}(\predi'))$ matches the recipient hash from the previous transaction.

\subsubsection{Multi-Signature Predicate}

\index{predicate!multi-signature ($\predi_\mathsf{msig}$)}
The \emph{multi-signature predicate} $\predi_\mathsf{msig}(\mathsf{pk}_1, \ldots, \mathsf{pk}_n;\cdot)$ requires $n$ valid signatures from $n$ specified public keys (all-of-$n$).

\begin{itemize}
	\item \textbf{Parameters}: $(\mathsf{pk}_1, \ldots, \mathsf{pk}_n)$
	\item \textbf{Unlocking argument}: $u = (\sigma_1, \ldots, \sigma_n)$
	\item \textbf{Definition}: $\predi_\mathsf{msig}(\mathsf{pk}_1, \ldots, \mathsf{pk}_n; \tau, m, u) = 1$ iff $\mathsf{Verify}(\mathsf{pk}_i, m, \sigma_i) = 1$ for every $i \in \{1, \ldots, n\}$
\end{itemize}


\subsubsection{Threshold-Signature Predicate}

\index{predicate!threshold-signature ($\predi_\mathsf{tsig}$)}
The \emph{threshold-signature predicate} $\predi_\mathsf{tsig}(k, \mathsf{pk}_1, \ldots, \mathsf{pk}_n;\cdot)$ requires $k$-of-$n$ valid signatures from distinct public keys.

\begin{itemize}
	\item \textbf{Parameters}: $(k, \mathsf{pk}_1, \ldots, \mathsf{pk}_n)$ where $k \in \{1, \ldots, n\}$
	\item \textbf{Unlocking argument}: $u = ((\sigma_1, j_1), \ldots, (\sigma_k, j_k))$ where $j_i$ is the index of the public key used for $\sigma_i$
	\item \textbf{Definition}: $\predi_\mathsf{tsig}(k, \mathsf{pk}_1, \ldots, \mathsf{pk}_n; \tau, m, u) = 1$ iff:
	\begin{enumerate}
		\item $\mathsf{Verify}(\mathsf{pk}_{j_i}, m, \sigma_i) = 1$ for every $i \in \{1, \ldots, k\}$
		\item All indices $j_i$ are distinct: $j_i = j_{i'}$ implies $i = i'$
	\end{enumerate}
\end{itemize}

The distinctness requirement prevents satisfying the predicate by presenting $k$ copies of the same signature.


\subsubsection{Burn Predicate}\label{sec:burn-predicate}

\index{predicate!burn ($\predi_\mathsf{burn}$)}
The \emph{burn predicate} $\predi_\mathsf{burn}(h_\mathsf{reason})$ cannot be unlocked. A token transferred to a burn predicate is permanently spent.

\begin{itemize}
	\item \textbf{Parameters}: $h_\mathsf{reason} \in \hashtype$ (reason hash, linking the burn to its purpose)
	\item \textbf{Unlocking argument}: none
	\item \textbf{Definition}: $\predi_\mathsf{burn}(h_\mathsf{reason}; \tau, m, u) = 0$ for all arguments
\end{itemize}

The burn predicate is used in token splitting (Sec.~\ref{sec:token-splitting}), where the reason hash is $\mathsf{SHA\text{-}256}(b_\mathcal{M})$ for the complete canonical split-manifest encoding $b_\mathcal{M}$.


\subsubsection{Open Predicate}\label{sec:open-predicate}

\index{predicate!open ($\predi_\mathsf{open}$)}
The \emph{open predicate} $\predi_\mathsf{open}$ is satisfied by any argument --- the dual of the burn predicate.

\begin{itemize}
	\item \textbf{Parameters}: none
	\item \textbf{Unlocking argument}: ignored
	\item \textbf{Definition}: $\predi_\mathsf{open}(\tau, m, u) = 1$ for all arguments
\end{itemize}

On its own, an open-owned state is spendable by anyone and holds no value. Its purpose is \emph{protocol-owned} tokens: combined with type-defined per-transfer checks (Sec.~\ref{sec:mint-authorization}), spending is constrained by validation rules instead of keys --- any party may advance the token's state, but only along transitions its type permits (e.g.\ autonomous pools, Appendix~\ref{app:autonomous-pools}).


\subsubsection{Timelock Predicate}

\index{predicate!timelock ($\predi_\mathsf{tlock}$)}
The \emph{timelock predicate} $\predi_\mathsf{tlock}(\mathsf{pk}, \tau_\mathsf{min};\cdot)$ prevents spending until the system time reaches a specified threshold. This is used to implement e.g. vesting schedules and lock-up periods for tokens.

\begin{itemize}
	\item \textbf{Parameters}: $(\mathsf{pk}, \tau_\mathsf{min})$ where $\mathsf{pk}$ is a public key and $\tau_\mathsf{min} \in \mathbb{T}$ is the unlock time
	\item \textbf{Unlocking argument}: $u = \sigma$ (digital signature)
	\item \textbf{Definition}: $\predi_\mathsf{tlock}(\mathsf{pk}, \tau_\mathsf{min}; \tau, m, \sigma) = 1$ iff $\tau \ge \tau_\mathsf{min} \;\land\; \mathsf{Verify}(\mathsf{pk}, m, \sigma) = 1$
\end{itemize}

The token remains locked until system time $\tau \ge \tau_\mathsf{min}$, after which it can be spent by producing a valid signature under $\mathsf{pk}$ and forming a witness unlocking the predicate and appending a spending transaction to the token ledger.


\subsubsection{Hashed Timelock Predicate}

\index{predicate!hashed timelock ($\predi_\mathsf{htlc}$)}
The \emph{hashed timelock predicate} $\predi_\mathsf{htlc}(\mathsf{pk}, \mathsf{pk}', y, \tau_\mathsf{max};\cdot)$ combines hash-locked and time-locked spending paths. The parameter $\mathsf{pk}$ is the refund key (original sender), $\mathsf{pk}'$ is the claim key (intended recipient), $y \in \hashtype$ is a hash lock, and $\tau_\mathsf{max} \in \mathbb{T}$ is a timeout.

\begin{itemize}
	\item \textbf{Parameters}: $(\mathsf{pk}, \mathsf{pk}', y, \tau_\mathsf{max})$
	\item \textbf{Unlocking argument}: $u = (x, \sigma)$ where $x$ is a preimage candidate and $\sigma$ is a digital signature
	\item \textbf{Definition}: $\predi_\mathsf{htlc}(\mathsf{pk}, \mathsf{pk}', y, \tau_\mathsf{max}; \tau, m, (x, \sigma)) = 1$ iff (a) or (b):
	\begin{itemize}
		\item[(a)] \emph{Claim path}: $\mathsf{Verify}(\mathsf{pk}', m, \sigma) = 1 \;\land\; y = H(x) \;\land\; \tau \le \tau_\mathsf{max}$
		\item[(b)] \emph{Refund path}: $\mathsf{Verify}(\mathsf{pk}, m, \sigma) = 1 \;\land\; \tau > \tau_\mathsf{max}$
	\end{itemize}
\end{itemize}

Clause~(a) allows the recipient to claim the token before the timeout by revealing the $H$-preimage $x$ of $y$ and signing with $\mathsf{pk}'$. Clause~(b) allows the sender to reclaim the token after the timeout by signing with $\mathsf{pk}$.

Example use-case is atomic swap, where two HTLC predicates on different ledgers/partitions share the same hash lock $y$; claiming on one ledger reveals $x$, enabling the counterparty to claim on the other. Note that this assumes ledgers to be public, which is not always the case on p2p networks.


\section{Interaction with Unicity Service}\label{sec:el-us-interaction}

\index{Unicity Service!execution layer interaction}
This section describes how the execution layer interacts with the Unicity Service (Sec.~\ref{sec:request-validation}) for state transition certification.

\subsection{Certification Request}

A certification request from the execution layer is a tuple $Q = (\predi, \sthash, \txhash, u)$, where:
\begin{itemize}
	\item $\predi$ -- spending predicate of the current owner
	\item $\sthash$ -- current state hash
	\item $\txhash$ -- transaction data hash
	\item $u$ -- unlocking argument satisfying $\predi$
\end{itemize}

\subsection{Processing}

The Unicity Service processes the request as follows:
\begin{enumerate}
	\item Compute state identifier: $\mathsf{sid} \gets H(\predi, \sthash)$
	\item Compute message hash: $m \gets H(\sthash, \txhash)$
	\item Evaluate predicate: verify $\predi(\tau, m, u) = 1$
	\item Check uniqueness: verify $R[\mathsf{sid}] = \bot$
	\item If both checks pass: $R[\mathsf{sid}] \gets \txhash$\footnote{The current SDK implementation stores $H(\mathsf{CBOR}(\predi, \sthash, \txhash, u))$ as the leaf value instead of $\txhash$, because of backward compatibility with the legacy SDK.}
\end{enumerate}

If the request is accepted, the Unicity Service returns an inclusion proof $\pinc$. If the state has already been spent (uniqueness check fails) or the predicate evaluation fails, the request is rejected.

\section{Token Types and Mint Authorization}\label{sec:token-types}

\index{token!type}\index{mint reason}\index{mint authorization}
Minting on the Unicity platform is technically permissionless: the minting key pair is a public constant (Sec.~\ref{sec:mint-tx}, Appendix~\ref{app:el-constants}), so a certified mint transaction proves only that the token identifier is fresh --- it conveys no issuance authority by itself. All authority to mint is carried by data inside the genesis and is re-verified by every subsequent recipient of the token. Two genesis fields implement this:
\begin{itemize}
	\item $\mathsf{ty}$ -- the \emph{token type}, classifying the token and selecting the validation rules that govern it for its entire lifetime;
	\item $\mathsf{reason}$ -- the \emph{mint reason}, an abstract payload that justifies the act of minting under the rules of type $\mathsf{ty}$: an issuer's authorization signature, a value-conservation proof of a split, a proof of external backing, or a zero-knowledge proof of an arbitrary type-defined statement.
\end{itemize}

This section specifies the generic verification flow that checks mint authorization --- the expansion of step~5 of mint-transaction verification (Sec.~\ref{sec:mint-tx}) and of step~6 of transfer verification (Sec.~\ref{sec:transfer-tx}). Concrete reason formats and standard token types are provided in Appendix~\ref{app:token-registry}.

\subsection{Token Type}\label{sec:token-type}

\index{token type}
A token type is an opaque byte string $\mathsf{ty} \in \bytestr$ with $1 \le \len{\mathsf{ty}} \le 64$ (typically 32 bytes), compared by byte equality. The type is fixed by the mint transaction and is immutable: no transfer, split (Sec.~\ref{sec:split-verification}, check~6), or any other operation may change it.

The identifier itself carries no meaning; it binds the token to a \emph{token type definition}
\[
\mathcal{D}_\mathsf{ty} = (\mathsf{ty},\; \mathsf{RT},\; \Call{ParseAux}{},\; \Call{VerifyIssuance}{},\; \mathsf{meta}),
\]
where
\begin{itemize}
	\item $\mathsf{RT}$ -- the set of admissible mint-reason formats, given as CBOR semantic tags (Appendix~\ref{app:cbor-tags}); the set MAY include $\bot$, admitting an absent reason;
	\item $\Call{ParseAux}{\mathsf{ty}, \auxd'}$ -- the deterministic decoder and validator of the token's genesis payload; for fungible types this is the function $\Call{Assets}{}$ of Sec.~\ref{sec:token-splitting};
	\item $\Call{VerifyIssuance}{}$ -- the type's issuance policy: a boolean function over the certified genesis, run in addition to the format-level reason verifier (e.g.\ pinning the expected issuer key, a bridge configuration, or a proof-system verification key);
	\item $\mathsf{meta}$ -- external, non-consensus metadata (display name, symbol, decimals, icons; Appendix~\ref{app:asset-metadata}).
\end{itemize}

A published definition MUST be frozen: every verifier of every recipient must apply byte-identical parsing and verification rules indefinitely, or tokens of that type would verify for some recipients and fail for others.

\paragraph{Type identifier derivation.} A type identifier MAY be an arbitrary (e.g.\ random) value, bound to its definition by the token type registry (Appendix~\ref{app:type-registry}). For new types it is RECOMMENDED to derive the identifier from the definition itself,
\[
\mathsf{ty} := H(\mathsf{TYPE\_DEF},\; b_\mathcal{D}),
\]
where $b_\mathcal{D}$ is the canonical CBOR encoding of the frozen definition manifest (Appendix~\ref{app:type-registry}) and $\mathsf{TYPE\_DEF}$ a fixed domain separator. This makes the binding between identifier and rules self-authenticating.

\subsection{Mint Reason}\label{sec:mint-justification}

\index{mint justification}\index{mint reason}
The mint reason is either absent ($\bot$) or a byte string containing a single tagged deterministic CBOR item. The semantic tag $t$ identifies the \emph{reason format}: the parsing rules and the verification algorithm of the reason body. Reason formats are format-level building blocks, decoupled from token types: one format (e.g.\ the split reason, Sec.~\ref{sec:token-splitting}) serves many token types, and one type may admit several formats for its issuance events. The type definition's admissible set $\mathsf{RT}$ makes the coupling explicit.

The fields should be interpreted as follows:

\begin{description}
	\item[reason] authorizes the mint
	\item[aux'] describes the minted token, a message to the next (') verifier or a transaction meta-data field in general.
\end{description}

A reason verifier receives the complete mint-transaction data and validates the binding between the two --- e.g.\ that the value declared in $\auxd'$ equals the value the reason actually authorizes.

\subsection{Verifier Registry}\label{sec:verifier-registry}

\index{verifier registry}
A relying party's verification capability is described by a \emph{verifier registry}
\[
\Gamma = (\mathcal{RV},\; \mathcal{TD},\; \Lambda),
\]
where
\begin{itemize}
	\item $\mathcal{RV}$ -- a partial map from reason-format tags to \emph{reason verifiers}; $\mathcal{RV}[t]$ is the verification function of format $t$, of the form $V_t(T_0, \pi_0, \Gamma, \mathcal{E}, \mathsf{collect}) \in \{0,1\}$, where $\mathcal{E}$ is the evidence set accompanying the token (Sec.~\ref{sec:token-evidence});
	\item $\mathcal{TD}$ -- a partial map from token type identifiers to token type definitions $\mathcal{D}_\mathsf{ty}$;
	\item $\Lambda$ -- cumulative resource budgets (bytes, items, nesting depth, proof steps, embedded tokens; cf.\ Appendix~\ref{app:split-proof-encoding}) shared by an entire verification run; when this budget is exhausted, verification fails deterministically with a resource-limit error.
\end{itemize}

The contents of $\mathcal{RV}$ and $\mathcal{TD}$ are an application-level trust decision (e.g., a wallet is designed to handle a specific set of token types, sufficient for its business goals). An implementation ships built-in verifiers for the standard formats and types (Appendix~\ref{app:token-registry}) and accepts application-supplied plug-ins for others. The registry is shared by the whole verification of a token: e.g., tokens named by mint reasons and resolved from the evidence set (Sec.~\ref{sec:nested-verification}) are verified under the same $\Gamma$, the same trust base $\mathcal{T}$, and the remaining budget $\Lambda$ as the outer token (cf.\ Sec.~\ref{sec:split-verification}, check~3).

\subsection{Mint Authorization Check}\label{sec:mint-authorization}

Algorithm~\ref{alg:mint-auth} defines the mint authorization check, run as step~5 of mint-transaction verification (Sec.~\ref{sec:mint-tx}) after the generic certification checks (steps~1--4) have passed. Every $\mathsf{ensure}$ failure, decoding error or exhausted budget rejects the transaction. $\mathsf{collect}$ is the nested-token collector of Sec.~\ref{sec:nested-verification}.

\begin{algorithm}[!htb]
\caption{Mint Authorization Verification}\label{alg:mint-auth}
\begin{algorithmic}[]
\Function{VerifyMintAuthorization}{$T_0, \pi_0, \Gamma, \mathsf{collect}$}
	\State $D \gets T_0.D_\mathsf{mint}$
	\State $\mathcal{D}_\mathsf{ty} \gets \Gamma.\mathcal{TD}[D.\mathsf{ty}]$
	\If{$\mathcal{D}_\mathsf{ty} = \bot$} \Return \FALSE \Comment{fail-shut: unsupported token type} \EndIf
	\If{$D.\mathsf{reason} = \bot$}
		\State ensure($\bot \in \mathcal{D}_\mathsf{ty}.\mathsf{RT}$) \Comment{type admits absent reason}
	\Else
		\State $t \gets$ CBOR semantic tag of $D.\mathsf{reason}$ \Comment{malformed CBOR rejects}
		\State ensure($t \in \mathcal{D}_\mathsf{ty}.\mathsf{RT}$) \Comment{type admits this reason format}
		\State $V \gets \Gamma.\mathcal{RV}[t]$
		\If{$V = \bot$} \Return \FALSE \Comment{fail-shut: unsupported reason format} \EndIf
		\State ensure($V(T_0, \pi_0, \Gamma, \mathcal{E}, \mathsf{collect}) = 1$) \Comment{format-specific verification}
	\EndIf
	\State ensure($\mathcal{D}_\mathsf{ty}.\Call{ParseAux}{D.\mathsf{ty}, D.\auxd'} \ne \bot$) \Comment{payload well-formed for this type}
	\State ensure($\mathcal{D}_\mathsf{ty}.\Call{VerifyIssuance}{T_0, \pi_0} = 1$) \Comment{type-specific issuance policy}
	\State \Return \TRUE
\EndFunction
\end{algorithmic}
\end{algorithm}

A reason verifier $V_t$ obtains the tokens a reason names from the \emph{evidence set} $\mathcal{E}$ accompanying the token (Sec.~\ref{sec:token-evidence}). Each is supplied either as a complete token, handed to $\mathsf{collect}$ for worklist verification (Sec.~\ref{sec:nested-verification}), or as a token attestation, verified inline by $\Call{VerifyAttestation}{}$ (Sec.~\ref{sec:attestation}). In both cases the verifier obtains $(\mathsf{id}, \mathsf{ty}, \mathcal{A}, h, e)$ and proceeds identically; values taken from a token routed to $\mathsf{collect}$ are provisional until the worklist drains, and the whole verification fails if it does not.

Reason bodies and payloads are decoded under the strict deterministic-CBOR discipline of Appendix~\ref{app:split-proof-encoding}: wrong or unknown tags, non-minimal encodings, wrong field counts or types, trailing bytes, and exhausted budgets are all rejected.

Type-specific validation is not limited to the genesis: step~6 of transfer verification (Sec.~\ref{sec:transfer-tx}) runs the per-transfer checks of $\mathcal{D}_\mathsf{ty}$, where the type defines any. For most types there are none --- the authoritative type-governed payload is the genesis payload $\auxd'_0$, and transfer-level auxiliary data is free-form transport (e.g.\ ephemeral keys of Sec.~\ref{sec:private-transactions}) unless the type states otherwise.

\paragraph{Fail-shut policy.}\index{fail-shut policy}
On the Unicity Mainnet ($\alpha = 1$), token acceptance MUST be \emph{fail-shut}: a relying party accepting a token MUST reject any token whose type has no entry in $\mathcal{TD}$, whose reason format has no entry in $\mathcal{RV}$, or whose reason tag lies outside the type's admissible set --- each with a distinct diagnostic error. A permissive mode that skips authorization checks for unregistered types MAY exist in testnet for diagnostic, archival or explorer tooling, but MUST NOT gate acceptance of value.

\subsection{Nested Tokens and Resource Limits}\label{sec:nested-verification}

\index{nested token verification}
Several reason formats depend on other tokens: the burned source of a split, and in general any format whose authorization derives from the prior existence of another certified token. A reason verifier MUST NOT verify a resolved token by recursive invocation of $\mathsf{VerifyToken}$; instead it validates the reason's own structure and bindings, and emits each token it resolved from $\mathcal{E}$ to the collector $\mathsf{collect}$. The driver maintains a worklist seeded with the outer token: it pops a token, verifies it (which may collect further ancestors), and repeats until the worklist is empty or the budget $\Lambda$ is exhausted. An identifier already verified in this run is not re-verified: the worklist is keyed by identifier, so an ancestor reachable by several paths through the provenance graph costs one verification.

All components of $\Lambda$ are cumulative across the entire worklist, and cover the evidence set as decoded bytes, each attestation verification, and each opaque genesis an attestation carries. A maliciously deep or wide provenance graph (e.g.\ repeated splits of splits) therefore exhausts the budget and is rejected as invalid, rather than exhausting the verifier's memory or time. Budget limits are part of the network's validation policy: two verifiers with the same $\Gamma$ accept exactly the same tokens, making the validation deterministic.

\section{Fungible Token Payload}\label{sec:fungible-tokens}

For fungible tokens (e.g. digital currency), the execution layer defines additional structure within the token's auxiliary data to support money-like operations: value tracking, splitting, and value conservation proofs.

\subsection{Asset Structure}\label{sec:asset-structure}

\index{asset}
An \emph{asset} is a pair $(\mathsf{aid}, v)$, where:
\begin{itemize}
	\item $\mathsf{aid}$ -- asset identifier, specifying the asset type (e.g. currency)
	\item $v \in \mathbb{N}$ -- asset value (non-negative integer amount)
\end{itemize}

A token may carry multiple assets, represented as a collection:
\[
\mathcal{A} = \{(\mathsf{aid}_1, v_1), \ldots, (\mathsf{aid}_m, v_m)\}
\]
where all asset identifiers $\mathsf{aid}_i$ are distinct.

\subsection{Token Splitting}\label{sec:token-splitting}

\index{token!splitting}
Splitting allows a fungible token to be divided into multiple new tokens while preserving the amount of every enclosed asset independently.  The protocol uses one \emph{Radix Sparse Merkle Sum Tree}\index{Radix Sparse Merkle Sum Tree} (RSMST) per asset identifier.  An RSMST reuses the radix sparse Merkle tree structure with sums committed next to every child hash, so verification of any output proves that its amount is included in a committed allocation whose total equals the source amount.

Each fractional token names its source by identifier and carries only its own allocation proofs in the mint reason; the source itself, and the burn that spent it, travel beside the token in the evidence set (Sec.~\ref{sec:token-evidence}). One source presentation therefore serves all $k$ outputs of a split, and it may be replaced by a token attestation at any later time without touching the certified genesis.

\subsubsection{Split Protocol}

Let $\Call{Assets}{\mathsf{ty},\auxd'}$ denote the token-type-specific, deterministic decoding and validation of a fungible payload.  Asset identifiers in the resulting collection are non-empty, distinct and placed in canonical bytewise order, and every amount is positive.  A payload containing a zero-valued entry is rejected rather than normalized.  Given a valid token $\mathcal{L}$ on network $\alpha$ carrying
\[
\mathcal{A}=\Call{Assets}{\mathsf{ty},\auxd'},
\]
the owner prepares $k \geq 1$ output mint transactions on the same network and with exactly the same token type $\mathsf{ty}$, with canonical asset collections $\mathcal{A}_1,\ldots,\mathcal{A}_k$.  Splitting is not a token-type conversion mechanism.  For every source asset identifier $\mathsf{aid}$ the allocations must satisfy
\[
\sum_{j=1}^{k} v_j(\mathsf{aid}) = v(\mathsf{aid})
\]
where a missing entry has value zero.  No output may introduce an asset identifier absent from $\mathcal{A}$.  Amounts of different asset identifiers are never added to or substituted for one another.

For output $j$, let $D_{\mathsf{out},j}$ consist of the source token identifier and all output mint fields except the mint reason.  Its commitment
\[
d_j = H(\mathsf{SPLIT\_OUTPUT},D_{\mathsf{out},j})
\]
binds the allocation to the source token, network, recipient predicate, salt and resulting token identifier, token type, and the complete canonical auxiliary payload.  In particular, a proof prepared for one recipient or token type cannot authorize a mint to another, even though the standard minting key is public.

The split proceeds as follows:
\begin{enumerate}
	\item Verify $\mathcal{L}$ completely, including its fungible payload, mint reason and issuer policy, before submitting any irreversible burn request.  Derive pairwise distinct output token identifiers $\mathsf{id}_j=H(\mathsf{salt}_j,\alpha)$ and the corresponding commitments $d_j$.
	\item For every source asset $\mathsf{aid}_i$ in canonical order, construct an RSMST $\mathcal{S}_i$.  For each output carrying that asset, insert the leaf
	\[
	(\mathsf{id}_j,d_j,v_j(\mathsf{aid}_i)).
	\]
	Require the RSMST root sum to equal $v(\mathsf{aid}_i)$.  Let $r_i$ be its root hash.
	\item Construct the \emph{split manifest}
	\[
	\mathcal{M}=\langle r_1,\ldots,r_m\rangle,
	\]
	where the roots are positionally aligned with the canonical source asset collection.  The manifest contains no repeated source identifier, asset identifiers or amounts: all are already authenticated by the burned token.  Its precise encoding $b_\mathcal{M}$ is defined in Appendix~\ref{app:split-proof-encoding}.  Extract and durably store every output's RSMST proofs and mint fields, together with the manifest and complete burn-transfer fields, before proceeding.
	\item Burn the source by creating and certifying a transfer whose auxiliary data is exactly $b_\mathcal{M}$ and whose recipient is $\predi_\mathsf{burn}(\mathsf{SHA\text{-}256}(b_\mathcal{M}))$.  The resulting certified burned token is denoted $\mathcal{L}_\mathsf{burn}$.
	\item Mint each output token $j$ with the exact fields committed by $d_j$.  Its mint reason contains the source identifier $\mathsf{id}_\mathsf{src}$ and, in canonical output-asset order, one RSMST inclusion proof for every asset it carries.  The proof contains only leaf-to-root sibling entries $(\delta,s,w)$ with explicit bifurcation depth, sibling hash and sibling sum; it omits the asset identifier, output identifier, output commitment, leaf amount and root hash because the verifier derives them respectively from the output payload, mint transaction, and split manifest.
	\item Assemble the evidence set for each output: the entry for $\mathsf{id}_\mathsf{src}$, as $\mathcal{L}_\mathsf{burn}$ in full or as an attestation of the pre-burn state together with the certified burn transaction, plus transitively the entries that entry itself names.
\end{enumerate}

The burn is evidence rather than part of the reason, and does not need to be committed by it. Given the source's pre-burn state $(\predi, h)$ the state identifier $\mathsf{sid} = H(\encpred(\predi), h)$ is determined, and the Unicity Service certifies at most one transaction per state identifier (Sec.~\ref{sec:request-validation}); the burn spending that state, and hence the manifest $b_\mathcal{M}$ it carries and the allocation roots read from it, are therefore unique. A substituted burn is not a certified one.


\subsubsection{Split Verification}\label{sec:split-verification}

Given a token whose mint reason claims split origin, the verifier must perform all of the following checks.  Failure of any check rejects the token.
\begin{enumerate}
	\item Decode the mint reason, manifest, payloads and proofs using deterministic CBOR.  Reject wrong or unknown tags, non-canonical integers or byte strings, duplicate or unordered asset identifiers, invalid field counts or types, trailing bytes, arithmetic overflow and any input exceeding the protocol's decoding and verification limits.
	\item Verify the output mint transaction and its Unicity Certificate.  Decode and validate its auxiliary payload according to its token type; the payload must contain a non-empty canonical collection of distinct, positive-valued assets.
	\item Resolve $\mathsf{id}_\mathsf{src}$ in the evidence set $\mathcal{E}$ (Sec.~\ref{sec:token-evidence}); a missing entry rejects.  A complete token is verified in full --- every Unicity Certificate, transaction, named ancestor, fungible payload and token type specific issuance policy --- by handing it to $\mathsf{collect}$; an attestation is verified by $\Call{VerifyAttestation}{}$, which must not return $\bot$.  Either way take $(\mathsf{id}, \mathsf{ty}_\mathsf{src}, \mathcal{A}_\mathsf{src}, h, e)$ from the result, under the same trust base $\mathcal{T}$, verifier registry and cumulative resource limits used for the output.  Require $\mathsf{id} = \mathsf{id}_\mathsf{src}$; both tokens must have network identifier $\mathcal{T}.\alpha$.
	\item Require $\mathcal{E}$ to supply, for that source, a certified transfer out of the state $(\decpred(e), h)$, verified as an ordinary transfer (Sec.~\ref{sec:transfer-tx}), whose auxiliary data is a canonical split-manifest encoding $b_\mathcal{M}$ and whose recipient predicate is exactly $\predi_\mathsf{burn}(\mathsf{SHA\text{-}256}(b_\mathcal{M}))$.  When the source was supplied as a complete token this is its final transfer.
	\item Place the distinct asset identifiers of $\mathcal{A}_\mathsf{src}$ in canonical order, and require the manifest to contain exactly one root hash for each source asset in that order.
	\item Require the output token type to be byte-identical to $\mathsf{ty}_\mathsf{src}$.  A split proof cannot authorize minting under any other token type, even if that type would decode the same asset identifiers and amounts.
	\item Recompute $d_j$ from the verified source identifier and the output mint fields other than $\mathsf{reason}$.  The recomputation must cover the exact canonical recipient predicate, network, salt, token identifier, token type and complete auxiliary payload.
	\item Require the proof count to equal the number of assets in the output payload.  Associate proofs with assets only by their canonical order; reject missing, duplicate or additional proofs.
	\item For every output asset $(\mathsf{aid}_i,v_j(\mathsf{aid}_i))$, require that $\mathsf{aid}_i$ occurs in $\mathcal{A}_\mathsf{src}$.  Verify its RSMST proof using key $\mathsf{id}_j$, leaf data $d_j$, leaf value $v_j(\mathsf{aid}_i)$ and expected root $r_i$ selected from the manifest.  Require both inclusion and root-hash equality.
	\item Require the root sum reconstructed by that proof to equal the source amount $v(\mathsf{aid}_i)$ read from $\mathcal{A}_\mathsf{src}$.  This equality is checked independently for every asset identifier and is the verifier-side value-conservation rule; successful construction by a wallet is not evidence of conservation.
\end{enumerate}

These checks establish that the source was authentic and irreversibly spent, the burn committed to the exact set of per-asset allocation roots, every accepted output and its ownership were fixed before the burn, and no accepted output can create value.  They establish the same facts whether the source arrived in full or as an attestation: both resolve the same identifier to the same token, and the burn --- unique for the state it spends --- fixes the manifest either way.  The protocol does not guarantee that every prepared output will subsequently be minted or delivered: failure to mint an output can destroy value but cannot transfer or inflate it.  The party performing the irreversible burn is responsible for durably retaining the manifest, output salts and proofs required to resume minting.

\subsection{Burn Transaction}\label{sec:burn-transaction}

\index{burn transaction}
A \emph{burn transaction} is a transfer transaction where the recipient predicate is $\predi_\mathsf{burn}(h_\mathsf{reason})$ (Sec.~\ref{sec:burn-predicate}). Since the burn predicate cannot be unlocked, the token is permanently spent and cannot be transferred further.

The reason hash $h_\mathsf{reason}$ links the burn to its purpose. In a split operation, it is the hash of the complete canonical split-manifest encoding $b_\mathcal{M}$, enabling verifiers of the resulting tokens to bind the source burn to the exact ordered vector of per-asset allocation roots.

\section{Token Compression}\label{sec:token-compression}

\index{token compression}
A token grows along two independent axes. It accumulates one certified transaction per transfer, so its size and verification cost grow with its own history (Sec.~\ref{sec:token-verification}); and a token minted by a split or merge depends on its source tokens, each of which depends on \emph{its} sources, back to issuance, so its size and cost also grow with the shape of its provenance. For a long-lived collectible the first term dominates; for a fungible fragment that has been split and merged many times, the second does.

\emph{Compression} replaces both with one succinct proof. A \emph{token attestation} $\mathcal{K}$ attests that a named token, of a named type and genesis payload, validly reached a named state --- carrying the evidence for its transfer history, its ancestors' transfer histories, and its ancestors' value conservation, all inside a single proof. The same object serves in two places: inside a token, standing for a prefix of its transfer sequence; and beside a token, standing for an ancestor its genesis names.

The size of an attestation is constant in the length of the token's transfer history and in the depth of the provenance it expands, and grows only with the number of geneses it leaves in the clear. Where it expands the provenance in full, those are exactly the distinct \emph{issuance events} behind the token, which remain in the clear by design and are the one thing compression does not remove (Sec.~\ref{sec:compression-scope}). A token that has only ever been transferred and split has one; a heavily merged one has as many as the independent lineages that flowed into it.

Compression is a change of representation, not a transaction. No state is spent and none is created; the token identifier, the genesis and the current state are unchanged; the Unicity Service is not involved and observes nothing. A compressed token and the uncompressed token it was derived from denote the same token in the same state: whichever representation a holder presents, spending it consumes the same state identifier, which the Unicity Service admits at most once (Sec.~\ref{sec:request-validation}). Compression therefore requires no token-type opt-in and creates no double-representation risk.

Two consequences shape the rest of this section. First, compression is \emph{discretionary} and outside the critical path of transacting: a holder compresses when it chooses --- typically as a background job --- and never as part of preparing a transaction. Second, compression is \emph{lossy and irreversible}: the proof does not yield the transfer records back. A holder that compresses and discards its records can no longer produce the uncompressed form, and can therefore no longer pay a relying party whose verifier lacks the compression verification key. Wallets SHOULD retain the raw history independently and treat the attestation as a transport representation rather than as storage.

\subsection{Design Constraints}\label{sec:compression-constraints}

Three properties are imposed on the construction. None of them is a concession to proving cost; each is about who is trusted with what, and about what can change later without invalidating proofs already issued. All three would be imposed even if proving were free.

\begin{description}
	\item[Issuance is never proven, only checked] Every mint transaction whose reason is an act of \emph{issuance} --- an issuer signature, a slot claim, a bridge backing, an arbitrary type-defined proof --- remains present in full and is verified by the ordinary verifier under its own registry $\Gamma$ (Sec.~\ref{sec:mint-authorization}). The relation expands only the value-conserving formats, whose rules are network-wide and type-independent. It therefore contains no issuer keys, no slot commitments, no bridge configuration and no nested verification keys, and a new issuance format can be registered without touching it.
	\item[No BFT signature verification inside the relation] The one Unicity Seal an attestation depends on is verified by the relying party's normal $\mathsf{VerifyUnicitySeal}$ path against its own trust base $\mathcal{T}$, and enters the proof only as a certified scalar. This keeps trust-base evolution --- validator sets, epochs, and any future change of consensus signature scheme --- entirely outside the relation. A relation that verified seals in-circuit would have to pin a trust base as a public input, and every proof would then be verifiable only by parties holding that exact trust base.
	\item[Type-specific rules stay with the type] Payload decoding inside the relation is the generic canonical asset-collection decoding (Sec.~\ref{sec:asset-structure}), not $\mathcal{D}_\mathsf{ty}.\Call{ParseAux}{}$. The type's own decoder and issuance policy are applied by the verifier, in the clear, to the genesis payload the attestation carries and to every genesis it discharges. A type that admits a conserving reason format MUST therefore define $\Call{ParseAux}{}$ so that it agrees with the generic decoding on the assets it yields; types whose genesis payload is exactly the canonical asset collection --- every fungible standard type of Appendix~\ref{app:token-registry} --- satisfy this by construction.
\end{description}

Nothing here follows from circuit size. Under the intended realization (Appendix~\ref{app:bridging-primitives}) irregular control flow, canonical CBOR decoding and sorting are ordinary code, so the costs that matter are the number of signature verifications and the number of hash compressions, and both are counted in Sec.~\ref{sec:compression-cost}. A direct benefit of that realization is that the decoders and the transfer-verification step inside the relation are the \emph{same source} as the ones outside it, which is what the specification's repeated demand for byte-identical parsing actually requires.

\subsection{Token Evidence and Reference Form}\label{sec:token-evidence}

\index{evidence set}\index{reference form}
Compression is only possible if the thing to be compressed is not sealed into a certified transaction. A reason format that \emph{embeds} its source tokens puts them in $\mathsf{reason}$, hence in $\txhash$, hence in the certified genesis, where those exact bytes are fixed forever and can never be re-encoded.

Every conserving reason format is therefore defined in \emph{reference form}: it names its sources by token identifier. The identifier suffices. It is derived as $\mathsf{id} = H(\mathsf{salt}, \alpha)$, it is unique network-wide, and at most one certified genesis exists per identifier (Sec.~\ref{sec:request-validation}), so an identifier determines a genesis as tightly as the genesis bytes do. The \emph{state} a source had reached is not pinned by the identifier, and does not need to be: it is pinned by the source's burn, which the consuming format checks.

Accordingly, a token travels with an \emph{evidence set}
\[
\mathcal{E} = \{\, \mathsf{id} \mapsto \mathsf{ev}(\mathsf{id}) \,\},
\]
supplying, for every identifier that its reason formats name, one of:
\begin{description}
	\item[a complete token] $\mathcal{L}$ with $\mathsf{id}(\mathcal{L}) = \mathsf{id}$, ending in the certified burn that the naming format consumes, and itself possibly carrying an attestation --- the recursive, uncompressed case;
	\item[a token attestation] $\mathcal{K}$ together with the certified burn transaction spending the state it attests to.
\end{description}
$\mathcal{E}$ is one flat map carried with the outermost token and resolved transitively: an entry supplied as a complete token may name further identifiers, whose entries must be present in the same $\mathcal{E}$. It is a canonical CBOR map with strictly increasing keys; duplicate keys reject. A missing entry rejects. Entries no reason format names are ignored, and count against $\Lambda$ like any other decoded bytes.

The evidence set is neither certified nor committed by anything: it is checked, not trusted. A verifier resolving an identifier either verifies the supplied token by $\Call{VerifyToken}{}$ or verifies the supplied attestation, and in both cases obtains the same facts about the same token. Substituting one form for the other is invisible to every check that consumes it, which is exactly what makes compression a re-encoding rather than a protocol change.

Two properties follow from $\mathcal{E}$ being uncommitted, and both are improvements over embedding. Evidence is \emph{replaceable}: a recipient who receives a token without usable evidence can obtain it from anyone holding the ancestor data --- the previous holder, the issuer, an archival service --- rather than being permanently unable to verify. And evidence is \emph{deduplicated by construction}: an ancestor reachable by several paths through the provenance graph appears once in $\mathcal{E}$ and is verified once.

\subsection{Anchoring}\label{sec:compression-anchors}

\index{anchor}
All certification evidence in an attestation is discharged against a single \emph{anchor}: one Unicity Seal $C^{\mathsf{r}*}$. The public anchor value is that seal's root history accumulator and nothing else,
\[
A \;:=\; C^{\mathsf{r}*}.a_r , \qquad N^* \;:=\; C^{\mathsf{r}*}.n_r + 1 ,
\]
paired with the accumulator size $N^*$, which the verifier derives from the signed round number and which fixes the structure $A$ is checked against. Leaves are established in the two stages of Appendix~\ref{app:bridging-anchor}. A derivation declares one \emph{round table} $\mathcal{R}$ covering every round it draws leaves from, authenticated against $(A, N^*)$ by a single batched root history proof; each leaf then supplies an SMT path to its shard root, the shard-tree and unicity-tree path to its round's entry in $\mathcal{R}$, the network binding $\mathcal{CD}_\beta.\alpha = \alpha$, and the right-shard binding of $\mathsf{sid}$ to $\sigma$. Because the table is batched, root history costs scale with the number of distinct rounds a derivation touches, $O(d\log(1 + N^*/d) + \log N^*)$, rather than with its leaf count.

Appendix~\ref{app:bridging-anchor} explains why the anchor is a seal rather than a shard root, and why one seal suffices however the shards of the Aggregation Layer are progressing relative to one another. It also explains why the anchor is this one scalar rather than a root-and-accumulator pair. An accumulator authorizes arbitrary historical roots, so it is the component that must never be accepted without proof, and a construction offering a cheaper path that authenticates only the root would leave it unchecked.

\paragraph{Obtaining the certification evidence.}
A holder preparing an attestation does not reuse the Unicity Certificates the token accumulated as it was transferred. The SMT is append-only, so every leaf of the token's history is still present under each shard's last certified root and can be certified afresh (Sec.~\ref{sec:leaf-representation}). The holder issues one $\Call{GetInclusionMulti}{}$ to each shard holding any of the state identifiers in the derivation, and each shard replies with a single inclusion certificate covering all of that shard's keys, together with the $UC$ that certified it.

No attempt is made to bring the shards into step, and none is needed. Each shard answers at its own last certified round, the repeat certification timer bounds that round to within \texttt{t2} of the current one, and the holder reconciles the resulting spread by taking the newest returned seal as $C^{\mathsf{r}*}$ and requesting one batched round table over the rounds involved. The number of distinct rounds $d$ is therefore bounded by the number of shards queried and by the number of BFT Core rounds within one \texttt{t2}, whichever is smaller, rather than by the length of the token's history. The holder drops the duplicated material, keeping one unicity tree certificate per partition and one seal in total.

What re-presentation buys is the retention depth the round table demands. Reusing the token's own certificates would set $d$ to the number of distinct rounds in its history and would require a node retaining root history back to the token's oldest transition, which for an old token means an archive. Re-presenting sets $d$ small and the required range to one \texttt{t2}, which any node that has been running for a few seconds can serve. Deep retention is then needed only for folding an older attestation (Sec.~\ref{sec:compression-relation}, check~5).

Presenting a leaf at a round later than the one in which it was first certified supplies that later round's $\mathcal{IR}.t$. A transition whose predicate reads the reference time must therefore be presented at its own round, which does require a root history path for a possibly distant round and hence a node retaining it (Sec.~\ref{sec:root-history-pruning}); check~3 of the relation makes the distinction on a static property of the predicate type.

\paragraph{Anchors do not accumulate.}
$A$ is a single value derived from a single verified signature, for a history of any length and a provenance of any depth. An older attestation folded into a newer one contributes no anchor of its own: its accumulator is authenticated against $A$ and then discarded (Sec.~\ref{sec:compression-relation}, check~5). There is no anchor list, and the attestation does not grow with the number of folds.

A deployment whose seals do not carry $a_r$ can still use this construction, at the price the accumulator removes. Every distinct anchor seal must then be carried and separately verified, $A$ becomes a commitment to the sorted set of their roots, and their number grows with the number of folds and with provenance depth. That variant is the reason the root history accumulator is specified as part of the seal (Sec.~\ref{sec:root-history}) rather than as an optional service.

\subsection{The Relation $\mathfrak{R}_\mathsf{tok}$}\label{sec:compression-relation}

The relation, its proof system and its verification key $\mathsf{vk}_\mathsf{tok}$ are network-level constants, frozen and published in the registry (Appendix~\ref{app:type-registry}) before activation; every verifier pins $H(\mathsf{vk}_\mathsf{tok})$ alongside its trust base. Because the verification key is a function of the compiled program, the registry entry MUST pin a reproducible build. Upgrade is full replacement, see Sec.~\ref{sec:bridge-security}.

The proof system MUST be \emph{recursively composable}, able to verify a proof of $\mathfrak{R}_\mathsf{tok}$ within $\mathfrak{R}_\mathsf{tok}$. See Appendix~\ref{app:bridging-primitives}.

One ASCII domain separator is fixed: $\mathsf{OPAQUE\_INIT} = \texttt{"UNICITY\_OPAQUE\_INIT"}$.

\subsubsection{Public Input}

\begin{longtable}{clp{8.4cm}}
\textbf{Index} & \textbf{Field} & \textbf{Description} \\
\hline
\endhead

1 & $\alpha$ & network identifier \\

\end{longtable}

\noindent $\mathcal{I}$ is a commitment to a \emph{set}, not a sequence:
\[
\mathcal{I} := H(\mathsf{OPAQUE\_INIT},\, \txhash_1, \ldots, \txhash_R), \qquad \txhash_1 < \cdots < \txhash_R,
\]
sorted bytewise and strictly increasing. Sorting removes any prover--verifier agreement on traversal order, and deduplication is not an optimization but a correctness convenience: a provenance graph that splits a token and later merges the parts back reaches the same genesis by two paths, and that shape is what a wallet consolidating its own change produces routinely.

\subsubsection{Statement}

$\mathfrak{R}_\mathsf{tok}(x; \mathsf{w})$ holds iff both of the following hold.

First, the witness declares a round table $\mathcal{R}$ with a batched root history proof $\Psi$, and
\[
\Call{VerifyRounds}{x.A,\; x.N^*,\; \mathcal{R},\; \Psi} \;=\; 1
\]
(Appendix~\ref{app:bridging-anchor}). This is the gate through which every anchored fact below acquires its authority; an implementation MUST perform it as a relation check and MUST NOT treat the round table as trusted witness data.

Second, there is a \emph{derivation} of $(x.\mathsf{id}, x.\mathsf{ty}, x.h_\auxd, x.h, x.\hat{e})$, where a derivation of a token consists of:

\begin{enumerate}
	\item \textbf{Genesis.} A mint transaction $D_\mathsf{mint}$ with $D_\mathsf{mint}.\alpha = x.\alpha$, $H(D_\mathsf{mint}.\mathsf{salt}, x.\alpha) = \mathsf{id}$, $D_\mathsf{mint}.\mathsf{ty} = \mathsf{ty}$ and $H(D_\mathsf{mint}.\auxd') = h_\auxd$. Its leaf is $(\mathsf{sid}_0, \txhash_0)$ with
	\[
	\txhash_0 = H(D_\mathsf{mint}),\quad \sthash_0 = H(\mathsf{id}, \mathsf{MINT\_SUFFIX}),\quad \mathsf{sid}_0 = H(\mathsf{pk}_\mathsf{mint}, \sthash_0),
	\]
	and it is anchored against $\mathcal{R}$. This is checks 1--4 of mint verification (Sec.~\ref{sec:mint-tx}) with the certificate replaced by anchored inclusion.

	\item \textbf{Reason.} Dispatch on the CBOR semantic tag of $D_\mathsf{mint}.\mathsf{reason}$. A tag in the relation's fixed \emph{conserving set} --- the split reason and the merge reason (Sec.~\ref{sec:split-verification}, Appendix~\ref{app:reason-merge}) --- takes either of the first two branches, at the prover's choice; every other tag takes the third.
	\begin{itemize}
		\item \emph{Expanded.} The body is decoded and the format's checks are re-run, in the correspondence of Sec.~\ref{sec:compression-edge}: each named source is resolved to a sub-derivation whose identifier is the one named and whose type is byte-identical to $\mathsf{ty}$; its terminal burn is verified as a transfer step out of the sub-derivation's final carry, with auxiliary data $b_\mathcal{M}$ and recipient predicate $\predi_\mathsf{burn}(\mathsf{SHA\text{-}256}(b_\mathcal{M}))$; and the format's conservation arithmetic --- the allocation-root reconstruction of a split, the summation of a merge --- is applied over the sub-derivations' asset collections, decoded generically from their genesis payloads, against the asset collection of $D_\mathsf{mint}.\auxd'$. The sub-derivations' opaque sets are unioned into this derivation's, as in check~5. Any failure \emph{rejects} and does not fall through to another branch.
		\item \emph{Opaque conserving genesis.} The genesis is not expanded and $\txhash_0$ is added to the opaque set. The edge is still checked, by the verifier rather than by the relation: every opaque genesis is discharged by running its own format verifier under the relying party's registry, resolving its sources from $\mathcal{E}$ and verifying their burns ($\Call{VerifyAttestation}{}$, step~3). The choice therefore selects where the conserving edge is checked, and with it whether the provenance below travels as proof or as evidence. It is not a fallback from a failed expansion: the prover chooses the witness, so at any point where the branch is available the two are the same proof, and soundness of this branch rests on the verifier discharging the genesis in full. An attestation that expands its own root genesis is \emph{provenance-complete}.
		\item \emph{Issuance.} The genesis is not examined: $\txhash_0$ is added to the opaque set, and nothing is assumed about the reason, the payload or the type beyond what check~1 established.
	\end{itemize}
	The conserving set is fixed by the relation version. Registering a new \emph{issuance} format needs no change here; registering a new \emph{conserving} format does, and is a new relation version.

	\item \textbf{Transfers.} A chain of transitions from the genesis carry $(h^0, e^0) = (\sthash_0,\; \encpred(D_\mathsf{mint}.\predi'))$ to the derivation's final carry. Writing $\predi^{i-1} = \decpred(e)$, each step checks
	\begin{enumerate}
		\item $T_i.\sthash = h$ \quad (the chain is contiguous);
		\item $\txhash_i \gets H(T_i.D)$;\; $\mathsf{sid}_i \gets H(e, T_i.\sthash)$;
		\item $\predi^{i-1}(\tau_i, H(T_i.\sthash, \txhash_i), u_i) = 1$. Whether $\predi^{i-1}$ reads the reference time is a static property of its type (Appendix~\ref{app:predicate-encoding}). If it does, the leaf is anchored at its \emph{own} round and $\tau_i$ is the $\mathcal{IR}.t$ of that round, read off the same anchored path (Appendix~\ref{app:anchor-time}); if it does not, $\tau_i$ is unconstrained and the leaf may be anchored at any round at or after its own;
		\item the leaf $(\mathsf{sid}_i, \txhash_i)$ is anchored against the derivation's round table $\mathcal{R}$, itself authenticated against $(A, N^*)$ once for the whole derivation;
		\item $e \gets \encpred(T_i.D.\predi')$;\; $h \gets H(h, T_i.D.x)$.
	\end{enumerate}
	These are checks 1, 3, 4 and 5 of transfer verification (Sec.~\ref{sec:transfer-tx}) together with the carry update of $\Call{VerifyToken}{}$, with check~2 discharged by $x.\alpha$ and the anchor's own network identifier. Check~6, per-transfer type rules, is out of scope in version~1 (Sec.~\ref{sec:compression-scope}).

	\item \textbf{Terminal state.} For the attested token, the chain ends at $(x.h, x.\hat{e})$. For a sub-derivation consumed by a burn, it ends immediately before that burn, which the naming derivation's reason check verifies as the consuming step.

	\item \textbf{Recursion.} A sub-derivation MAY instead be discharged by an attestation, without expanding it. Verify its $\pi_\mathsf{tok}$ in-circuit under $\mathsf{vk}_\mathsf{tok}$ against a witnessed public input; require its version and $\alpha$ to match this one and its identifier and type to be what the naming reason requires; take its $(h, \hat e)$ as the state its burn spends. Every remaining component of that public input is then reconciled by the same pattern, in which the sub-proof commits a value, this derivation witnesses the preimage, and the preimage is checked against something this derivation already trusts.
	\begin{itemize}
		\item \emph{Anchor.} The sub-derivation's public $(A_\mathsf{sub}, N^*_\mathsf{sub})$ is an accumulator, and an accumulator that this derivation has not authenticated authorizes any root whatsoever. At least one of the following two reconciliations MUST succeed.
		\begin{enumerate}
			\item \emph{Prefix reconciliation.} $N^*_\mathsf{sub} \le N^*$ and $\Call{VerifyRootHistoryPrefix}{A_\mathsf{sub}, N^*_\mathsf{sub}, A, N^*, \psi} = 1$ (Sec.~\ref{sec:root-history}), establishing that $A_\mathsf{sub}$ is the accumulator over a prefix of the sequence $A$ commits. The prover obtains $\psi$ from any node whose retained range covers $N^*_\mathsf{sub}$ (Sec.~\ref{sec:root-history-pruning}).
			\item \emph{Seal reconciliation.} A Unicity Seal $C^\mathsf{r}_\mathsf{sub}$ is witnessed with $C^\mathsf{r}_\mathsf{sub}.\alpha = x.\alpha$, $A_\mathsf{sub} = C^\mathsf{r}_\mathsf{sub}.a_r$, $N^*_\mathsf{sub} = C^\mathsf{r}_\mathsf{sub}.n_r + 1$, and $\mathsf{VerifyUnicitySeal}(C^\mathsf{r}_\mathsf{sub}.r, C^\mathsf{r}_\mathsf{sub}, \mathcal{T}_\mathsf{sub}) = 1$. The trust base record $\mathcal{T}_\mathsf{sub}$ of epoch $C^\mathsf{r}_\mathsf{sub}.e_r$ is witnessed and reached from $x.h_\mathcal{T}$ by opening the previous-record hash of each intervening record (Sec.~\ref{sec:ddrc}), which requires $C^\mathsf{r}_\mathsf{sub}.e_r \le C^{\mathsf{r}*}.e_r$.
		\end{enumerate}
		Each reconciliation authenticates $A_\mathsf{sub}$ in full, and neither leaves a component of the sub-anchor resting on the prover's word. That distinguishes the choice offered here from the root-and-accumulator pair rejected in Appendix~\ref{app:anchor-level}, where the cheaper branch authenticates the root and leaves the accumulator --- the component that authorizes arbitrary historical roots --- unchecked. The choice here is between two complete proofs of the same statement, not between a complete one and an incomplete one. Either way the older anchor is discharged and discarded, not carried.
		\item \emph{Opaque geneses.} Witness the sub-derivation's opaque transaction hashes, require them to recompute $\mathcal{I}_\mathsf{sub}$, and merge them into this derivation's set. These propagate to the outermost derivation, so every genesis the provenance left unexpanded remains explicit after compression while the rest of the history does not. A sub-derivation that left a conserving genesis opaque thereby obliges the outermost verifier to discharge it, and the evidence for that genesis's sources must be present in $\mathcal{E}$ when the outermost attestation is verified.
		\item \emph{Committed preimages.} The sub-derivation publishes $h_\auxd^\mathsf{sub}$ and $\hat e_\mathsf{sub}$ as hashes of data this derivation must use --- the payload whose asset values the conservation arithmetic of check~2 decodes, and the predicate encoding the burn step needs in order to form $\mathsf{sid} = H(e, h)$. Witness each preimage and check it against its commitment before use.
	\end{itemize}

	The same rule discharges an \emph{earlier attestation of the token itself}, which is how a holder extends its own compressed history: verify the previous $\pi_\mathsf{tok}$, reconcile its accumulator by either route, and continue the transfer chain from the carry it attests to. A fold must therefore use an anchor at least as recent as every attestation it absorbs.
\end{enumerate}

\paragraph{Conservation is edge-wise.} The relation establishes no numeric relation between the attested payload and the geneses in $\mathcal{I}$. A statement of the form ``$100$ was issued, $7$ is attested, and $7 \le 100$'' is neither proved nor sufficient: it is satisfied by two disjoint tokens of $7$ each derived from the same issuance, by an output whose source was never burned, and by one source counted twice in a merge. What the relation establishes is each conserving edge separately, namely that the source reached the state it was burned out of, that the burn was certified and committed to this exact output set, and that the format's arithmetic over the sources' payloads yields this output's payload. Conservation of the derivation follows from conservation of each edge together with the single-spend property of the burns (Sec.~\ref{sec:request-validation}), and there is no shortcut that skips an edge.

Check~5 states the compositional part of the relation, and its anchor clause establishes the security of that composition. Verifying a sub-proof costs one recursive verification regardless of what the sub-proof stands for. Nothing about the sub-derivation --- not its transfer count, not its own provenance depth, not its anchor's age --- reaches the outer proof except its opaque geneses.

\paragraph{Choosing a reconciliation.} The two routes differ in what the security of an old attestation rests on, and the difference widens with its age. Prefix reconciliation ties $A_\mathsf{sub}$ to the chain the relying party is on at verification time, so a seal from an abandoned branch, or one signed by a validator set compromised after its epoch ended, cannot be substituted. Seal reconciliation rests instead on the validator set of epoch $C^\mathsf{r}_\mathsf{sub}.e_r$ and accepts any correctly signed seal of that epoch. A prover SHOULD use prefix reconciliation whenever a node retains the required range, and a deployment SHOULD set its retention depth (Sec.~\ref{sec:root-history-pruning}) to cover the attestation ages it expects. Seal reconciliation exists so that an attestation older than any retained range remains foldable, and so that no participant is obliged to operate an archival service in order for compression to work at all.

The costs also differ. Prefix reconciliation is $O(\log N^*)$ hash compressions. Seal reconciliation is one BFT quorum signature verification, plus one hash per epoch stepped over, which is small because epochs are infrequent. Neither cost accumulates: a $k$-way merge performs $k$ reconciliations at that fold and exports a single anchor, so folding the result again costs one reconciliation rather than $k + 1$. Against the one Unicity Certificate per certified transaction that an uncompressed token carries, both routes leave the number of signature verifications proportional to the number of folds rather than to the length of the history.

The reconciliation is where a recursive construction of this shape is most easily got wrong. A sub-proof's public input is not evidence of anything by itself. It is whatever value made some proof verify, and a prover is free to choose it. Every component of it must therefore be tied back to something the outer derivation already trusts, which is the accumulator of the seal the relying party will verify under the prefix route, and the trust base record committed by $x.h_\mathcal{T}$ under the seal route. Authenticating a sub-anchor only partially is equivalent to not authenticating it at all, because the unchecked component is the one carrying the authority.

\subsubsection{The Conserving Edge in Circuit}\label{sec:compression-edge}

``The format's checks are re-run'' (check~2) is stated precisely by the following correspondence. Every numbered check of split verification (Sec.~\ref{sec:split-verification}) and of merge verification (Appendix~\ref{app:reason-merge}) has exactly one disposition, and an implementation that omits or weakens any of them is not an implementation of $\mathfrak{R}_\mathsf{tok}$. Three substitutions apply throughout and are the only ones admitted: a Unicity Certificate is replaced by anchored inclusion against $\mathcal{R}$ (check~1 for a genesis leaf, check~3(d) for a transfer leaf); resolution of an identifier in $\mathcal{E}$ is replaced by resolution to a sub-derivation, itself expanded or discharged by recursion (check~5); and $\mathcal{D}_\mathsf{ty}.\Call{ParseAux}{}$ is replaced by the generic canonical asset-collection decoding, which the type definition must agree with (Sec.~\ref{sec:compression-constraints}).

\begin{longtable}{lp{9.6cm}}
\textbf{Format check} & \textbf{Disposition in $\mathfrak{R}_\mathsf{tok}$} \\
\hline
\endhead
Split 1 & Verbatim. The same deterministic CBOR rules, tag set, canonicity, ordering, field-count and overflow rejections. \\
Split 2 & Certificate substituted; payload decoded generically. The requirement that the payload be a non-empty canonical collection of distinct positive-valued assets is verbatim. \\
Split 3 & Evidence resolution substituted. The identifier equality $\mathsf{id} = \mathsf{id}_\mathsf{src}$ and both network identifiers are verbatim. \\
Split 4 & Verbatim as a transfer step, certificate substituted: the burn spends the sub-derivation's final carry, its auxiliary data is $b_\mathcal{M}$, its recipient predicate is exactly $\predi_\mathsf{burn}(\mathsf{SHA\text{-}256}(b_\mathcal{M}))$. \\
Split 5 & Verbatim. Canonical order of the source asset identifiers, one manifest root per source asset in that order. \\
Split 6 & Verbatim. Output type byte-identical to $\mathsf{ty}_\mathsf{src}$. \\
Split 7 & Verbatim. $d_j$ recomputed from the verified source identifier and every output mint field other than $\mathsf{reason}$. \\
Split 8 & Verbatim. Proof count equals output asset count; association by canonical order only. \\
Split 9 & Verbatim. Per-asset RSMST inclusion under key $\mathsf{id}_j$, leaf data $d_j$, leaf value $v_j(\mathsf{aid}_i)$, against the manifest root $r_i$; inclusion and root-hash equality both required. \\
Split 10 & Verbatim. Reconstructed root sum equals the source amount, checked independently per asset identifier. \\
\hline
Merge 1 & Verbatim, including $2 \le k \le K_\mathsf{max}$. \\
Merge 2 & Payload decoded generically; the non-empty canonical positive-amount requirement is verbatim. \\
Merge 3 & Evidence resolution substituted. Strictly increasing $\mathsf{id}_i$, byte-identical type and network identifier are verbatim. \\
Merge 4 & $d$ recomputed verbatim from the source list and the output mint fields other than $\mathsf{reason}$; each source burn verified as in Split~4. \\
Merge 5 & Verbatim. Canonical summed collection over the sources equals the output collection exactly, with overflow rejected. \\
\end{longtable}

\noindent Two things are outside the relation in every case. Mint authorization (step~5 of Sec.~\ref{sec:mint-tx}) is the verifier's, for every genesis in $\mathcal{I}$, which is what the first design constraint reserves to it. Per-transfer type rules are out of scope in version~1 (Sec.~\ref{sec:compression-scope}).

There is one relation and one $\mathsf{vk}_\mathsf{tok}$ for all token types. A type whose admissible set contains no conserving format, which is every non-fungible type of Appendix~\ref{app:token-registry}, never reaches the expanded branch: its derivations are a genesis and a transfer chain, and under the intended realization it pays nothing for machinery it does not execute. Splitting the relation for such types would buy no proving cost and would cost a second verification key to pin, audit and build reproducibly. The only variant the design admits is the one carrying per-transfer type rules, which contains type-specific code and therefore cannot share a key.

\subsection{Token Attestation}\label{sec:attestation}

\index{token attestation}
The attestation object is
\[
\mathcal{K} = (\mathsf{ver},\; \alpha,\; \mathsf{id},\; \mathsf{ty},\; \auxd'_0,\; h,\; e,\; \pi_\mathsf{tok},\; C^{\mathsf{r}*},\; \langle D_{\mathsf{mint},1}, \ldots, D_{\mathsf{mint},R}\rangle),
\]
where $\auxd'_0$ is the attested token's genesis payload in the clear, $C^{\mathsf{r}*}$ is the anchor seal, and $D_{\mathsf{mint},r}$ are the opaque geneses' mint transaction data --- \emph{bare}, without inclusion proofs or certificates. $A$, $N^*$, $h_\auxd$, $\hat e$ and $\mathcal{I}$ are recomputed by the verifier and are not carried.

Carrying the geneses bare is what makes the anchor seal the only certification signature. Check~1 of the relation anchors every genesis leaf, opaque ones included: it recomputes $\txhash_0 = H(D_\mathsf{mint})$ and $\mathsf{sid}_0 = H(\mathsf{pk}_\mathsf{mint}, H(\mathsf{id}, \mathsf{MINT\_SUFFIX}))$ and proves that leaf certified. That is precisely what steps 1--4 of mint-transaction verification (Sec.~\ref{sec:mint-tx}) establish, so re-presenting each genesis's own Unicity Certificate would re-prove what the proof has already proved --- and would drag in one historical seal, and the trust base of its epoch, per issuance event. What is \emph{not} discharged in-circuit is step~5, mint authorization, which is type-specific by design; that is what the verifier runs, on data the proof has bound.

$\Call{VerifyAttestation}{\mathcal{K}, \mathcal{T}, \Gamma}$:
\begin{enumerate}
	\item Ensure $\mathcal{K}.\mathsf{ver} = 1$ and $\mathcal{K}.\alpha = \mathcal{T}.\alpha$; decode $e$ canonically (Appendix~\ref{app:predicate-encoding}).
	\item Ensure $C^{\mathsf{r}*}.\alpha = \mathcal{T}.\alpha$ and $\mathsf{VerifyUnicitySeal}(C^{\mathsf{r}*}.r,\, C^{\mathsf{r}*},\, \mathcal{T}) = 1$; set $(A, N^*) \gets (C^{\mathsf{r}*}.a_r,\; C^{\mathsf{r}*}.n_r + 1)$ and $h_\mathcal{T} \gets H(\mathcal{T}[C^{\mathsf{r}*}.e_r])$, the digest of the verifier's own trust base record for the anchor's epoch. This is the only certification signature the \emph{verifier} performs, at any depth of recursion and for any number of issuance events. A fold that used seal reconciliation (Sec.~\ref{sec:compression-relation}, check~5) discharged its own signature inside the proof, against a trust base record the binding of $h_\mathcal{T}$ ties to the verifier's; the evidence set alongside the attestation carries its signatures separately, one per source burn left in the clear (Sec.~\ref{sec:compression-scope}).
	\item Let the \emph{discharged genesis set} be the carried $D_{\mathsf{mint},r}$, together with the attested token's own genesis data when $\mathcal{K}$ is used inside a token and the derivation left that genesis opaque (see below), which the token then supplies in place of a carried copy. For each $D_\mathsf{mint}$ in that set: ensure $D_\mathsf{mint}.\alpha = \mathcal{T}.\alpha$ and run mint authorization, Alg.~\ref{alg:mint-auth}, under the verifier's own $\Gamma$ --- its token type definition, its reason verifiers, its issuance policies, resolving any evidence it needs from $\mathcal{E}$. A conserving reason is admitted here and is discharged by the format's own verifier, which resolves its sources from $\mathcal{E}$, verifies them and verifies their burns; this is the verifier-side half of check~2, and skipping it would leave the edge unchecked on both sides. Certification is \emph{not} re-checked here: the proof established it. Ensure the hashes $H(D_\mathsf{mint})$ are pairwise distinct, sort them bytewise ascending as $\txhash_1 < \cdots < \txhash_R$, and set $\mathcal{I} \gets H(\mathsf{OPAQUE\_INIT}, \txhash_1, \ldots, \txhash_R)$.
	\item Ensure $\mathfrak{R}_\mathsf{tok}$ verifies under $\mathsf{vk}_\mathsf{tok}$ with public input $(1,\, \alpha,\, A,\, N^*,\, \mathsf{id},\, \mathsf{ty},\, H(\auxd'_0),\, h,\, H(e),\, \mathcal{I},\, h_\mathcal{T})$, in the field order of the table above.
	\item Ensure $\mathcal{D}_\mathsf{ty} \gets \Gamma.\mathcal{TD}[\mathsf{ty}]$ is defined and $\mathcal{A} \gets \mathcal{D}_\mathsf{ty}.\Call{ParseAux}{\mathsf{ty}, \auxd'_0} \ne \bot$.
	\item Return $(\mathsf{id}, \mathsf{ty}, \mathcal{A}, h, e)$; any failed check returns $\bot$ instead.
\end{enumerate}

Every failure rejects. A verifier that does not pin $\mathsf{vk}_\mathsf{tok}$ MUST reject any attestation with a distinct diagnostic error, as with an unregistered reason format (Sec.~\ref{sec:mint-authorization}); it MUST NOT fall back to accepting the token unverified.

Step~3 is where the design constraint of Sec.~\ref{sec:compression-constraints} is cashed in: mint authorization for every genesis the relation left opaque runs in ordinary, auditable code, under the relying party's own registry, exactly as it does for an uncompressed token. A capped type's slot geneses (Appendix~\ref{app:reason-slot}) are checked in the clear, so the supply cap is re-established on every verification; a bridged token's backing proof is re-checked against the verifier's own bridge configuration; a type the verifier does not know fails shut.

Resource accounting (Sec.~\ref{sec:nested-verification}) charges $\Lambda$ a fixed cost for the proof verification and the seal verification, plus the full cost of each opaque genesis, which is an ordinary mint verification and may itself resolve evidence. A provenance with more opaque geneses than the budget admits is rejected exactly as a too-deep provenance graph is (Sec.~\ref{sec:nested-verification}).

\paragraph{Use inside a token.} When $\mathcal{K}$ stands for a prefix of a token's own transfer sequence, the token already carries its genesis, and the derivation's treatment of that genesis decides what else is carried. Left opaque, it is the sole member of the discharged genesis set and the token supplies it, so $\mathcal{K}$ carries no mint data of its own and $\mathcal{K}.(\mathsf{id}, \mathsf{ty}, \auxd'_0)$ MUST agree with it; because $\mathcal{K}$ anchors the leaf, the token MAY reduce $T_0^\mathsf{cert}$ to $D_\mathsf{mint}$ and drop $\pi_0$, where an uncompressed token, having no proof to anchor it, carries the certificate as before. Mint authorization then runs on $T_0$ exactly as for an uncompressed token, resolving its own sources from $\mathcal{E}$ if its reason is a conserving format, so a token may compress its history while leaving its provenance uncompressed. Expanded, $\mathcal{I}$ names the issuance events behind the token rather than the token's own genesis, no source burns travel with it, and $T_0^\mathsf{cert}$ is redundant on the wire. The verifier distinguishes the cases by whether $\mathcal{I}$ contains $H(T_0.D_\mathsf{mint})$, before verifying anything.

\paragraph{Use as evidence.} When $\mathcal{K}$ stands for an ancestor named by a reason, $\mathcal{E}$ supplies it together with the certified burn that spends $(\decpred(e), h)$. The consuming reason verifier proceeds exactly as it would with a complete token: it verifies the burn as an ordinary certified transfer out of that state, reads $b_\mathcal{M}$ from its auxiliary data, and applies its remaining checks with $\mathcal{A}$ in place of the decoded source payload and $\mathsf{id}$ in place of the decoded source identifier. In this role no token supplies the root genesis, so a derivation that left it opaque carries it among the $D_{\mathsf{mint},r}$ like any other opaque genesis.

\paragraph{Why the genesis payload is public.} $\auxd'_0$ is carried in the clear because conservation is checked in the clear: the RSMST root sum must equal the source amount (Sec.~\ref{sec:split-verification}, check~10), and that arithmetic is the verifier's, not the prover's. This discloses nothing new --- every holder of every split output already learns the source amount from that same check --- and it is what allows one attestation to serve all $k$ outputs of a split, since it speaks about the source alone and is independent of any particular output.

\subsection{Preparation and Folding}\label{sec:compression-folding}

An attestation is about a token, not about a transaction that consumes it, so it can be produced before the consuming transaction exists. The discipline follows from that:

\begin{itemize}
	\item A holder folds in the background, at whatever cadence it chooses. The steps are to verify the previous $\pi_\mathsf{tok}$, reconcile its accumulator against a fresh anchor, append the transitions received since, and prove. Cost is one recursive verification, one reconciliation, and work proportional to the \emph{new} transitions rather than to the history carried forward. An older anchor is absorbed rather than replaced, so no re-anchoring step and no retained leaf list are required, unlike a construction with per-round or per-shard anchors.
	\item Folding frequently is cheaper than folding rarely, because the reconciliation route available depends on the gap. A holder whose previous anchor still falls within some node's retained range reconciles by prefix, for hashes only; one whose anchor has aged past every retained range reconciles by seal, for one BFT quorum verification (Sec.~\ref{sec:compression-relation}). Neither route fails, so a token left untouched for years remains foldable; the cadence affects proving cost, not availability.
	\item Folding extends a history; it does not revisit a genesis. A fold discharges the token's own earlier attestation by recursion, so checks 1 and 2 for the token's genesis are the ones that attestation already performed, and a genesis left opaque then stays opaque under every subsequent fold. Expanding it later means re-deriving from the genesis rather than folding, at the cost of the provenance the earlier attestation did not carry. A holder that intends its token to become provenance-complete SHOULD therefore expand at the first attestation.
	\item The holder of a token that will be split or merged prepares its attestation in advance, by that same background job and off the critical path.
	\item At split time no proving occurs. The splitter burns and mints as usual, and hands each of the $k$ outputs the \emph{same} attestation as evidence for their common source. One proving job serves all $k$ recipients and, through them, the entire descendant subtree.
	\item Merge composes the same way: each of the $k$ sources contributes one attestation, and the merged token's own attestation --- prepared later --- folds all $k$ into one. A party that holds all $k$ sources itself, the usual case when consolidating change, MAY instead expand them inline in a single proving job, which avoids $k$ separate proofs and $k$ recursive verifications.
\end{itemize}

There is a break-even point in size, set by the proof system's constant proof length (Appendix~\ref{app:bridging-primitives}). A recursion-oriented system pays for its composability with a large constant, so folding does not reduce size until the history or provenance it replaces exceeds that constant. A wallet SHOULD therefore treat folding as an optimization for long-lived or heavily merged tokens rather than as a default for every token.

What compression buys unconditionally is verification cost, which is constant from the first fold: one proof verification and one seal verification in place of one Unicity Certificate per certified transaction. Where the replaced material is a deep provenance graph rather than a transfer history, the size break-even also arrives quickly, since an attestation stands for an entire ancestor subtree.

\subsection{Cost}\label{sec:compression-cost}

The relation's cost is determined by the number of signature verifications and the number of hash compressions, and the structure of the design is what keeps both small.

\emph{Signature verifications.} Exactly one predicate evaluation per transfer step actually expanded in this proof, plus one per ancestor burn expanded in this proof. A step discharged by recursion costs none. A multi-signature or threshold predicate costs its own number of verifications, as it does outside. Beyond the predicates, the relation performs one BFT quorum verification per absorbed attestation reconciled by the seal route of check~5, and none for an attestation reconciled by the prefix route. A prover that reconciles every fold by prefix performs no BFT signature verification anywhere in the relation.

\emph{Hash compressions.} Per transfer step, the transaction and predicate hashes of Sec.~\ref{sec:transfer-tx}; per anchored leaf, one SMT path plus the shard-tree and unicity-tree paths of Appendix~\ref{app:bridging-anchor}; per derivation, one batched round table costing $O(d\log(1 + N^*/d) + \log N^*)$ over the $d$ distinct rounds it touches --- the $\Omega(d)$ term is the table entries themselves and does not vanish; per absorbed attestation, one $O(\log N^*)$ prefix-consistency proof, or one hash per epoch stepped over on the trust base chain when the seal route is used instead; per expanded split edge, the RSMST allocation paths and manifest decoding of Sec.~\ref{sec:split-verification}.

For a holder who re-presents the derivation's leaves (Sec.~\ref{sec:compression-anchors}), $d$ is the number of distinct rounds the queried shards last certified in, bounded by the rounds falling within one \texttt{t2} and by the number of shards, and is independent of the length of the history. A derivation that instead reuses the token's stored certificates has $d$ equal to the number of distinct rounds in that history, which is the case the batched form of the round table was designed for.

Against these costs stands what the relation removes: an uncompressed token carries one Unicity Certificate, and hence one BFT quorum verification, per certified transaction. The SMT paths dominate the hash count and are not removed by compression --- they are moved inside the proof --- so the saving is concentrated in the signature count.

The root history paths are an asymptotic addition rather than a free saving. A shard-root anchor would need none, at the cost of not spanning shards at all. What they buy is the removal of one BFT quorum signature verification per leaf, leaving one for the whole attestation. Hashes are the cheap resource here and signatures the expensive one, so the exchange is heavily favourable, but the $\log N^*$ factor is real and should be measured rather than assumed away.

\emph{Recursive verifications.} One per sub-derivation discharged by an attestation, including a holder's own previous fold, each accompanied by one anchor reconciliation.

The marginal cost of a merge of $k$ sources whose attestations already exist is therefore $k$ recursive verifications, $k$ reconciliations, $k$ burn signatures, and the merging token's own transfers, independent of how much history or provenance sits behind those $k$ sources. That amortization is the property the whole construction exists to provide. The reconciliations are the price of the security property of check~5 and are not optional. By the prefix route, at $O(\log N^*)$ hashes each, they are far below the recursive verification they accompany; by the seal route they are comparable to it.

For the relying party, verification is one proof, one seal, and one \emph{mint authorization} check per genesis the relation left opaque, authorization only, with no certificate and no historical trust base. For a provenance-complete attestation those geneses are exactly the distinct issuance events behind the token, and nothing else appears: no transfer history, no provenance graph, no source burns. For an attestation that leaves its own genesis opaque, the check on that genesis is the format's own verifier, which resolves the sources from $\mathcal{E}$ and verifies their burns as ordinary certified transfers, so the provenance below that point is verified in the ordinary way and costs what it ordinarily costs.

Expanding a conserving genesis rather than leaving it opaque moves its sources' burn signatures from the verifier, where each is one native signature verification, into the relation, where each is one in-circuit predicate evaluation. Compression of provenance is therefore not uniformly cheaper: it is cheaper to verify and more expensive to prove, and the point at which a holder stops expanding is where it places that trade.

\subsection{Rules and Scope}\label{sec:compression-scope}

\begin{description}
	\item[Terminal burns are never folded] The token an attestation attests to MUST have the burn that consumes it presented in the clear, in $\mathcal{E}$ beside the attestation. The consuming verifier checks that burn's auxiliary data and recipient predicate byte-exactly, and a proof does not supply them. This applies at the boundary only: burns consumed by a genesis the relation expanded are verified inside it as ordinary transfer steps (Sec.~\ref{sec:compression-relation}, check~2).
	\item[Reason formats that read certification data cannot be discharged from an attestation] Alg.~\ref{alg:mint-auth} passes the inclusion proof $\pi_0$ to the reason verifier and to $\Call{VerifyIssuance}{}$. A genesis discharged from an attestation has no $\pi_0$ --- its certification was established inside the proof --- so a format whose verifier reads $\mathsf{time}(\pi_0)$, or any other field of the inclusion proof, MUST be presented with its certificate instead, and a type admitting such a format is not compressible past that genesis. No format defined in Appendix~\ref{app:token-registry} does so: every one of them authorizes a mint by a commitment over $D_\mathsf{mint}$ alone.
	\item[Source burns keep their certificates only where the edge is opaque] The burn that consumes a source is outside that source's own attestation by construction, since it postdates it, so its certification is not proven and it is verified as an ordinary certified transfer. The evidence set therefore carries one certified burn per source named by a genesis the relation left opaque, and none for a source named by a genesis it expanded, whose burn it verified as a transfer step (Sec.~\ref{sec:compression-relation}, check~2). A provenance-complete attestation carries no source burns at all. One that leaves its own genesis opaque carries one for a split and $k$ for a $k$-source merge, and transitively whatever the evidence below it names.
	\item[Provenance breadth is not compressed] Expansion collapses provenance \emph{depth} to a single proof, but each independent lineage flowing into a merge contributes its own issuance event, and every one of those is verified in the clear. With its provenance fully expanded a token's cost is therefore proportional to the number of distinct issuance events behind it --- one for a token that has only ever been split, more for a heavily merged one --- and not to its transaction history. Shallow, narrow provenance remains preferable: issuing in fixed denominations and consolidating deliberately beats repeated splitting and merging.
	\item[Per-transfer type checks are out of scope in version 1] $\mathfrak{R}_\mathsf{tok}$ omits check~6 of transfer verification (Sec.~\ref{sec:transfer-tx}), which is a no-op for types that define no per-transfer rules --- the common case (Sec.~\ref{sec:mint-authorization}). A type that defines per-transfer rules, such as a pool type (Appendix~\ref{app:autonomous-pools}), requires those rules inside the relation; its definition manifest MUST then pin the verification key of the relation variant that implements them, and a verifier MUST NOT accept attestations for such a type under the generic key.
	\item[Compression is not required, and not always the cheapest answer] For a type whose admissible set includes an issuance format, the issuer can already create value of that type, so having the issuer verify a token and authorize a fresh equivalent adds no trust assumption that the type does not already carry --- and costs no proving at all. Compression is what makes provenance bounded \emph{without} an issuer in the loop, which is what capped types (Appendix~\ref{app:uts-capped}), bridged types (Sec.~\ref{sec:bridged-assets}), and holders unwilling to reveal a token to its issuer require.
\end{description}

\paragraph{Data minimization, not privacy.} A recipient of a compressed token does not receive the predicates, unlocking arguments or auxiliary data of the folded transitions --- including any ephemeral keys those transitions carried (Sec.~\ref{sec:private-transactions}) --- and does not receive the ancestor tokens at all. This is a reduction in what is disclosed, not a privacy guarantee: unless the proof system is zero-knowledge, no hiding property is claimed for $\pi_\mathsf{tok}$; the genesis payload and every issuance event are disclosed in full by construction; and every party that held the token earlier retains the raw history regardless. Applications MUST NOT rely on compression as a privacy mechanism; unlinkability is provided by the protocols of Sec.~\ref{sec:private-transactions}.

(ii)~CBOR encodings and semantic tags of $\mathcal{K}$ and of the evidence set. (iii)~In-relation budget accounting mirroring $\Lambda$, including the cost of recursive verification and of inline provenance expansion. (iv)~A formal statement of the transfer-verification step in-circuit, shared with the bridging relation (Appendix~\ref{app:bridging-relation}). (v)~The relation variant carrying per-transfer type checks, prerequisite to compressing pool tokens. (vi)~Reference form for the conversion reason (Appendix~\ref{app:reason-convert}) and the pool transition records (Appendix~\ref{app:autonomous-pools}), which embed tokens by value today and are therefore the only remaining incompressible formats. (vii)~Whether the evidence set should present source burns as anchored leaves against a seal it carries, rather than as full certified transfers, which would make the burn count cost hashes instead of signatures. (viii)~Retention depth guidance for aggregators, which fixes the attestation age at which folding falls back from prefix to seal reconciliation (Sec.~\ref{sec:root-history-pruning}), and measurement of whether the seal route's quorum verification is cheap enough in practice for the fallback to be the default rather than the exception. \section{Bridged Assets}\label{sec:bridged-assets}

\index{bridge}\index{bridged asset}
A fungible token may represent an asset held in custody on an \emph{external chain} (e.g.\ an account-based EVM chain). Bridging is bi-directional. \emph{Bridge-in} locks the external asset in a settlement contract (the \emph{vault}) and mints a Unicity token whose mint reason (Sec.~\ref{sec:mint-justification}) is a \emph{backing proof} binding the token to that lock. \emph{Bridge-out}, or \emph{return}, burns the Unicity token and releases the matching external asset. Both directions are realized without a trusted bridge operator or committee: bridge-in as a token-type specific mint-reason verifier that every recipient re-runs, and bridge-out as a succinct validity proof the vault verifies. This section specifies both; concrete data structures and algorithms are in Appendix~\ref{app:bridging}.

\subsection{Bridge-In: Lock and Mint}\label{sec:bridge-in}

To bring an asset in, the locker fixes the recipient's first-owner predicate $\predi'_0$ and a token salt, determining the token identifier $\mathsf{id} = H(\mathsf{salt},\alpha)$ (Sec.~\ref{sec:mint-tx}) and the recipient commitment $h_\mathsf{rcpt} = H(\mathsf{CBOR}(\predi'_0))$. The locker calls the vault on the external chain, which escrows the asset into pooled custody, assigns a monotone lock nonce $n$, and emits a \emph{lock event} committing to $\mathsf{id}$, $h_\mathsf{rcpt}$, and the locked amount. The locker then mints a Unicity token of type $\mathsf{ty}$ to $\predi'_0$ whose genesis carries a \emph{backing reason} that references the lock by $(\chi, a_\mathsf{V}, a_\mathsf{A}, n)$ (Appendix~\ref{app:bridging-lock}).

Minting is permissionless: the minter key is a public constant derived from $\mathsf{id}$ (Appendix~\ref{app:el-constants}), so a valid genesis signature conveys no authority by itself. Authority comes entirely from the backing reason, verified by every recipient as the token-type specific mint-reason check (Sec.~\ref{sec:mint-tx}, step~5). The verifier (Appendix~\ref{app:bridging-backing}) confirms that a \emph{final} lock with nonce $n$ exists at the configured vault and asset on the configured chain, and binds it to the genesis: the lock's committed identifier equals $\mathsf{id}$, its recipient commitment equals $h_\mathsf{rcpt}$, and its amount equals the genesis's declared value for $\mathsf{aid}$. The reason body carries only the lock locator and the trust anchors; every security-relevant value is read from the certified genesis and the lock event and validated cryptographically.

Bridge-in cannot be instantaneous. A reorganization of the external chain could undo the lock after the token is minted and in circulation, so a recipient must wait for the lock to be final on the external chain before treating the token as good. This finality wait is intrinsic to accepting a deposit from a chain with probabilistic finality. Confirming the lock requires reading external-chain state: the recipient does so either by querying an external-chain node, or by verifying an external-chain inclusion proof carried in the backing reason against a pinned external-chain anchor (Appendix~\ref{app:bridging-finality}). Either way each recipient is its own verifier, so bridge-in introduces no trusted bridge party; its only assumption is the external chain's own consensus.

The wait is enforced by each verifier for itself, not attached to the token as a global condition. In particular, the locker minting to a predicate it already controls needs no wait: it already knows whether its own deposit exists, so no reorganization can surprise it, and a wallet may show such a token to its own owner immediately. The wait binds the first party that did \emph{not} witness the lock --- typically the first recipient the token reaches after leaving the locker's own custody --- since only that party's own $\Call{LockFinal}{}$ check protects it from a lock later undone by a reorganization.

\paragraph{Security.}
\begin{description}
\item[No mint without a lock] The backing verifier accepts the genesis only if a matching final lock exists on the configured chain and asset; a token minted without a lock fails verification and is never accepted.
\item[No double mint] The genesis of a token with identifier $\mathsf{id}$ is recorded at a single state determined by $\mathsf{id}$ (Sec.~\ref{sec:mint-tx},~\ref{sec:request-validation}); since the lock commits to $\mathsf{id}$, one lock funds exactly one token and cannot be replayed for a second mint.
\item[No theft] Although anyone may construct the genesis, $h_\mathsf{rcpt}$ binds ownership to the predicate the locker named on the external chain, so only the intended recipient can spend the minted token.
\item[No value inflation] The declared genesis value for $\mathsf{aid}$ must equal the locked amount, so minted value never exceeds custody.
\item[No rogue contract] The chain, vault, and asset in the reason must equal the pinned configuration, so a genesis pointing at an unauthorized contract is rejected.
\item[No reorged lock] The lock must be final on the external chain, so a deposit that could still be reversed is not accepted.
\end{description}

\subsection{Bridge-Out: Setting}\label{sec:bridge-setting}

A Unicity burn is final the instant it is certified by the BFT Consensus layer and is verifiable offline by $\Call{VerifyToken}{}$ (Sec.~\ref{sec:token-verification}) against the trust base $\mathcal{T}$ alone: there is no source-finality wait, no validator node, and no external RPC query. The limitation is that the external vault is computationally weak --- re-running $\Call{VerifyToken}{}$ on-chain incurs cost which grows with token history. A \emph{succinct validity proof} (Appendix~\ref{app:bridging-primitives}) compresses that token history-dependent check into a single verification of constant cost.

The vault holds pooled custody of one asset, has persistent storage, can verify a succinct proof for constant cost, and pins (i)~an allow-listed trust-base hash $h_\mathcal{T} = H(\mathcal{T})$, selecting \emph{which} Unicity Service instance is authoritative, and (ii)~an immutable configuration hash $h_\mathsf{cfg}$ committing the external chain identifier, the vault and asset addresses, the bridged token type $\mathsf{ty}$, the asset identifier $\mathsf{aid}$, and the protocol's domain separators (Appendix~\ref{app:bridging-config}). There is no trusted operator, committee, or challenge window: the vault releases funds only against a valid proof.

The return proof is structured in layers: a shared Unicity anchor authenticates historical transition leaves; token-lineage verification checks ownership and chain linkage; value/backing verification ties the burned value to a recorded source-chain lock; replay verification advances the spent-burn accumulator; and the settlement layer binds the public release leaves to the vault transfers. Only the final settlement layer touches source-chain state.

\subsection{Return Authorization}\label{sec:bridge-return-reason}

To return value, the holder forms a \emph{return reason} $\mathcal{R}$ and its canonical encoding $b_\mathcal{R}$. The holder then burns the token (Sec.~\ref{sec:burn-transaction}) with auxiliary data $b_\mathcal{R}$ and recipient predicate $\predi_\mathsf{burn}(H(b_\mathcal{R}))$. The reason commits to the external release: the recipient, a gross amount $v$ equal to the burned token's certified value for $\mathsf{aid}$, an optional relayer fee, a fee deadline, and the pinned configuration fields (Appendix~\ref{app:bridging-reason}). A fungible token might have been split (Sec.~\ref{sec:token-splitting}), causing fractional returns.

\subsection{Replay Prevention}\label{sec:bridge-replay}

Replay prevention is implemented via a \emph{nullifier accumulator}, whose root $A$ is stored on-chain by the vault: an authenticated set (implemented by the sparse Merkle tree of Sec.~\ref{sec:smt}, which already provides inclusion and non-inclusion certificates) of the burns already released. The \emph{nullifier} of a burn is derived from its certified leaf, whose state identifier the Unicity Service records at most once (Sec.~\ref{sec:request-validation}); it is therefore globally unique by the same mechanism that prevents double-spending. A release proves the nullifier is \emph{absent} from $A$ and inserts it, and the vault advances $A$. Consequently, the on-chain state necessary for replay prevention is \emph{constant} --- one root.

The nullifier accumulator can be deterministically rebuilt by anybody based on transaction history of the source blockchain.

\subsection{Validity Statement}\label{sec:bridge-statement}

For a batch of $B$ burns, the proof attests the conjunction of the following claims:

\begin{description}
\item[Anchor.] A single recent Unicity Certificate $UC^*$ certifies an SMT root $h^* = UC^*.IR.h$ under $\mathcal{T}$, and $H(\mathcal{T}) = h_\mathcal{T}$. Because the SMT is add-only (Sec.~\ref{sec:smt}), every state a token ever occupied remains provable under any later root, so one $UC^*$ anchors entire token histories. The proof verifies this BFT certificate \emph{once} per batch, instead of one certificate per transition.
\item[Finality.] Each burned token verifies by $\Call{VerifyToken}{}$, with every certified transaction's leaf shown included under the shared root $h^*$; in particular the final state is a burn whose auxiliary data is the encoded return reason and whose recipient predicate binds its hash. This anchored mode is restricted to predicates whose validation does not depend on the original Unicity request-validation time.
\item[Value and backing.] Each burned amount equals the token's certified value for $\mathsf{aid}$, which traces --- through split value-conservation (Sec.~\ref{sec:split-verification}) --- to a genesis whose backing proof references a lock the vault recorded at bridge-in.
\item[Destination.] Each $\mathcal{R}$ matches the pinned configuration and yields a public \emph{release leaf} (recipient, amount, fee).
\item[Replay.] Each nullifier is absent from the input accumulator root $A_\mathsf{old}$; inserting them yields $A_\mathsf{new}$.
\end{description}

The vault verifies the proof, checks $h_\mathsf{cfg}$ and that $h_\mathcal{T}$ is allow-listed, requires $A_\mathsf{old}$ to equal its stored root, confirms each referenced lock digest against its own bridge-in records, advances the root to $A_\mathsf{new}$, and pays each release leaf. No external query is made at return time: backing was committed locally when the asset was locked.

\subsection{Security}\label{sec:bridge-security}

\begin{description}
\item[Solvency.] Every bridged token in circulation is backed by an equal external lock (bridge-in), and split verification guarantees children never exceed their parent (Sec.~\ref{sec:split-verification}). Hence $\sum(\text{valid burns}) \le \sum(\text{locks})$, and valid releases can never drain custody below zero. Over-release would require a burn of an unbacked token, which the backing claim and the vault's lock-digest check exclude.
\item[No double release.] The nullifier is unique (single-spend, Sec.~\ref{sec:request-validation}); a release both proves its non-membership and inserts it, and the vault gates on $A_\mathsf{old}$ equal to its current root. A replayed proof is rejected because the root has advanced, and a freshly built one cannot prove non-membership of an inserted nullifier.
\item[Authenticity.] The proof embeds $\Call{VerifyToken}{}$ against the pinned $\mathcal{T}$, so a forged, malformed, or non-final burn is unrepresentable under proof-system soundness.
\item[No trusted parties.] The prover cannot alter the recipient or amount (fixed in the certified $\mathcal{R}$) nor fabricate a release; it can only stall, and any party holding the burned token can reproduce the proof.
\end{description}

\paragraph{Relation upgrades.} The verification key $\mathsf{vk}$ is immutable once a vault is deployed: this is what makes proof verification trustworthy, since no party --- including the deployer --- can silently swap in a different relation later. The consequence is that fixing a bug in the proving relation, or extending it, requires deploying a \emph{new} vault under a new $\mathsf{vk}$; it cannot be done in place. The old and new vaults share no state, so value locked under the superseded configuration must be returned under the old relation before, or independently of, adopting the new one. Appendix~\ref{app:bridging-upgrades} details the upgrade procedure.

The full data structures, the proving relation, the settlement procedure, and the batched proving mechanism are in Appendix~\ref{app:bridging}.

\section{Private Transactions}\label{sec:private-transactions}

In the transaction flow described above, Sec.~\ref{sec:transaction-flow}, the Unicity Service learns only the public key and signature (predicate and unlock data in general) of the token spending party; but it is not possible to associate transactions with tokens. Looking at a token it is possible to associate transactions if made by the same party using the same key. In order to achieve perfect privacy it is necessary to generate a fresh predicate $\predi'$ for every transaction. This requires generating and storing a fresh keypair per transaction, which may be impractical when the recipient's secure storage is limited, and forces the transaction sender to obtain recipient's key for every transaction, making the transacting protocol interactive.

This section presents protocols that allow the recipient to derive unlinkable predicates from a single persistent keypair, requiring no persistent state beyond the keypair itself. Also, this persistent keypair can be used as a persistent address (recipient's identifier).

The protocols below are implemented at the ``wallet'' level and need no support by the execution layer and Unicity Service. User can choose selectively wheter to make fully private transactions or not.

The privacy protocols produce a transaction-specific public key $\mathsf{pk}_{tx}$ that the sender embeds in the predicate $\predi' = \predi_\mathsf{sig}(\mathsf{pk}_{tx})$. An ephemeral public key $R$ is included in the auxiliary data $\auxd'$ of the transaction, enabling the recipient to reconstruct the corresponding private key $\mathsf{sk}_{tx}$ when spending.

The protocols below assume an elliptic curve group of order $n$ with generator $G$, and that the signature predicate $\predi_\mathsf{sig}$ uses a compatible scheme (e.g. ECDSA). The persistent keypair is $(\mathsf{sk}, \mathsf{pk})$ where $\mathsf{pk} = \mathsf{sk} \cdot G$.

\subsection{Interactive Protocol}\label{sec:private-interactive}

For each incoming transaction, the recipient generates an ephemeral blinding factor $r$ and derives a transaction-specific public key $\mathsf{pk}_{tx} = (\mathsf{sk} + r) \cdot G$. The protocol is shown in Figure~\ref{fig:private-interactive}.

\centering

  & & $r \stackrel{\$}{\gets} \mathbb{Z}_n$ \\
  & & $\mathsf{pk}_{tx} \gets (\mathsf{sk} + r) \cdot G$ \\
  & & $R \gets r \cdot G$ \\
  & $\xleftarrow{\hspace{0.6cm} \predi_\mathsf{sig}(\mathsf{pk}_{tx}),\; R \hspace{0.6cm}}$ & \\[2mm]
$\predi' \gets \predi_\mathsf{sig}(\mathsf{pk}_{tx})$ & & \\

The recipient sends $\predi_\mathsf{sig}(\mathsf{pk}_{tx})$ and the ephemeral public key $R$ to the sender, who includes $R$ in the auxiliary data $\auxd'$ of the transfer transaction. When spending the received token, the recipient reconstructs the blinding factor $r' = H(\mathsf{sk} \,\|\, R)$ from the persistent private key and $R$ (read from $\auxd'$), and computes the transaction-specific private key $\mathsf{sk}_{tx} = \mathsf{sk} + r' \bmod n$.

\subsection{Non-Interactive Protocol}\label{sec:private-non-interactive}

For applications where the recipient publishes a persistent public key $\mathsf{pk}$ as an address, the sender can derive unlinkable predicates without interaction using Diffie-Hellman key exchange inspired protocol, shown in Figure~\ref{fig:private-non-interactive}.

The key challenge is protecting against a malicious sender who might choose a predictable ephemeral key $r$ or leak it to compromise unlinkability. The construction addresses this by binding the blinding factor to both the shared secret and public transaction data.

\begin{figure}[!htb]
\centering
\fbox{
\begin{minipage}{0.95\textwidth}

\underline{Setup:} Recipient publishes persistent public key $\mathsf{pk} = \mathsf{sk} \cdot G$

\vspace{3mm}
\begin{tabular}{lcl}
\textbf{Sender} & & \textbf{Recipient} \\
\hline
\\[-2mm]
$r \stackrel{\$}{\gets} \mathbb{Z}_n^*$ & & \\
$R \gets r \cdot G$ & & \\
$s \gets H(r \cdot \mathsf{pk} \,\|\, R \,\|\, \sthash)$ & & \\
$\mathsf{pk}_{tx} \gets \mathsf{pk} + s \cdot G$ & & \\
$\predi' \gets \predi_\mathsf{sig}(\mathsf{pk}_{tx})$ & & \\
$\auxd' \gets \{\ldots, R\}$ & & \\
Create and certify $T$ & & \\
& $\xrightarrow{\hspace{0.6cm} \mathcal{L}\; \cup\; T^\mathsf{cert} \hspace{0.6cm}}$ & \\[3mm]
& & \textbf{if} $R = \mathcal{O}$ \textbf{then abort} \\
& & $s' \gets H(\mathsf{sk} \cdot R \,\|\, R \,\|\, \sthash)$ \\
& & \textbf{if} $\mathsf{pk} + s' \cdot G \neq \mathsf{pk}_{tx}$ \textbf{then abort} \\
& & $\mathsf{sk}_{tx} \gets \mathsf{sk} + s' \bmod n$ \\
& & Sign next transaction using $\mathsf{sk}_{tx}$ \\
\end{tabular}
\end{minipage}
}
\caption{Non-interactive protocol for generating unlinkable predicates.}
\label{fig:private-non-interactive}
\end{figure}

The sender generates an ephemeral keypair $(r, R = r \cdot G)$ and computes a Diffie-Hellman shared secret $r \cdot \mathsf{pk}$. The blinding factor is derived by hashing the shared secret together with $R$ and the current state hash $\sthash$:
$$s = H(r \cdot \mathsf{pk} \,\|\, R \,\|\, \sthash)$$

The transaction-specific public key is $\mathsf{pk}_{tx} = \mathsf{pk} + s \cdot G$, and $R$ is included in $\auxd'$. The sender sets $\predi' = \predi_\mathsf{sig}(\mathsf{pk}_{tx})$ in the transaction data. Upon receiving the transaction, the recipient:
\begin{enumerate}
\item Verifies $R \neq \mathcal{O}$ (not trivially insecure)
\item Computes the shared secret $\mathsf{sk} \cdot R = r \cdot \mathsf{pk}$ using the persistent private key
\item Derives $s' = H(\mathsf{sk} \cdot R \,\|\, R \,\|\, \sthash)$ and verifies $\mathsf{pk} + s' \cdot G = \mathsf{pk}_{tx}$
\item Computes $\mathsf{sk}_{tx} = \mathsf{sk} + s' \bmod n$
\end{enumerate}

Including both $R$ and $\sthash$ in the hash input ensures that:
\begin{itemize}
\item Even if the sender chooses a predictable $r$, the blinding factor $s$ remains unpredictable to external observers
\item The recipient can verify that the sender correctly computed $\mathsf{pk}_{tx}$ without learning $r$
\item Each transaction uses a unique blinding factor, since $\sthash$ is unique by construction (Sec.~\ref{sec:token-state}), preventing linkability even if the sender reuses the same $r$
\end{itemize}
