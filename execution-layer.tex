\chapter{Execution Layer}

The execution layer handles off-chain transaction processing and business logic. Tokens are self-contained digital assets transferred peer-to-peer between users. Only cryptographic commitments to state transitions are submitted to the Aggregation Layer for double-spending prevention. Transaction execution and verification are performed by the interested parties (recipients), not by consensus participants. This design moves computational overhead off-chain while maintaining trustless guarantees against double-spending.

\section{Execution Model}

In the Unicity execution model, digital assets called \emph{tokens}\index{token} are bearer instruments: whoever holds the token data and can satisfy the spending condition is the owner. Transactions occur directly between parties using any communication channel, with the Unicity Service consulted only to prevent double-spending.

The model relies on three key principles:
\begin{enumerate}
	\item \textbf{Off-chain execution}: Transaction creation, validation, and verification happen between sender and recipient without consensus participation.
	\item \textbf{On-chain uniqueness}: The Unicity Service maintains an append-only registry of spent token states, ensuring each state can be spent at most once.
	\item \textbf{Recipient verification}: The recipient (relying party) independently verifies the complete token history before accepting a transfer.
\end{enumerate}

\subsection{Token Lifecycle}\label{sec:token-lifecycle}

A token progresses through the following stages:
\begin{description}
\item[Minting]\index{mint transaction} Creates a new token with an initial state. Minting uses a publicly known minting key pair $(\mathsf{sk}_\mathsf{mint}, \mathsf{pk}_\mathsf{mint})$ which MAY be network specific.
\item[Transfer]\index{transfer transaction} Changes ownership by spending the current state and creating a new state with a new owner predicate.
\item[Compression]\index{token compression} Compacts the token by replacing a prefix of its transfer history with a succinct proof of validity of those transactions. Unlike the other stages, compression is a change of \emph{representation} rather than a transaction: no state is spent, no state is created, the token identifier is unchanged and the Unicity Service is not involved. See Sec.~\ref{sec:history-compression}.
\item[Split]\index{split transaction} (Fungible tokens only.) Burns the original token and mints new tokens, with a cryptographic value conservation proof ensuring no value is created or destroyed. See Sec.~\ref{sec:token-splitting}.
\item[Burn]\index{burn transaction} Permanently locks a token by transferring it to a burn predicate that cannot be unlocked. See Sec.~\ref{sec:burn-transaction}.
\end{description}

\subsection{Token State}\label{sec:token-state}

\index{token!state}
A \emph{token state} is a pair $(\predi, \sthash)$, where:
\begin{itemize}
	\item $\predi$ -- the spending predicate (defines who can spend the token); see Sec.~\ref{sec:predicates}
	\item $\sthash \in \hashtype$ -- the state hash, linking the token's transaction history
\end{itemize}

The \emph{state identifier}\index{state identifier}\index{$\mathsf{sid}$ (state identifier)} is the key used in the Unicity Service registry:
\[
\mathsf{sid} = H(\predi, \sthash)
\]

When a transaction with random value $x \gets \{0,1\}^\ell$ is executed, the next state hash is computed as:
\[
\sthash' = H(\sthash, x)
\]

The randomness of \emph{state mask}\index{state mask} $x$ ensures that the next state identifier $H(\predi', \sthash')$ is unpredictable, preventing the Unicity Service from linking consecutive states of the same token.

The state mask $x$ MUST be sampled with at least 128 bits of min-entropy.

\subsection{Token Structure}\label{sec:token-structure}

A \emph{token}\index{token!structure} is a self-contained data structure carrying its complete provenance. Any party can independently verify the entire history without consulting external state. Formally, a token is a sequence:
\[
\mathcal{L} = (T_0^\mathsf{cert}, T_1^\mathsf{cert}, \ldots, T_n^\mathsf{cert})
\]
where $T_0^\mathsf{cert}$ is a certified mint transaction and $T_i^\mathsf{cert}$ for $i > 0$ are certified transfer transactions.

A token has two compressible dimensions, both treated in Sec.~\ref{sec:history-compression} and neither of which alters a certified transaction: its own transfer sequence, a prefix of which MAY be replaced by a \emph{compressed history} object; and its \emph{provenance}, the ancestor tokens its genesis reason depends on, which MAY be supplied as \emph{token certificates} instead of in full. Either result denotes the same token in the same state, is verified by the same function $\Call{VerifyToken}{}$, and is spent by an ordinary transfer.

\subsubsection{Mint Transaction}\label{sec:mint-tx}

\index{mint transaction!structure}
A \emph{certified mint transaction} is a tuple $(T_0, \pi_0)$, where $T_0 = (\sthash, D_\mathsf{mint})$ and
\[
D_\mathsf{mint} = (\alpha, \predi', \mathsf{salt}, \mathsf{ty}, \mathsf{reason}, \auxd') .
\]
\begin{itemize}
	\item $\sthash = H(\mathsf{id}, \mathsf{MINT\_SUFFIX})$ -- source state hash, for state identifier derivation
	\item $D_\mathsf{mint}$ -- mint transaction data, containing in this order:
	\begin{itemize}
		\item $\alpha \in \mathbb{A}$ -- network identifier, binding the token to a specific Unicity network instance
		\item $\predi'$ -- spending predicate of the first owner
		\item $\mathsf{salt} \in \{0,1\}^{256}$ -- token identifier salt, chosen by the minter and required to be unique among the minter's salt choices (e.g.\ by uniform random sampling or by a local counter); $\mathsf{salt}$ has no masking role and need not be high-entropy
		\item $\mathsf{ty}$ -- token type, classifying the token category, defining its mandatory validation rules
		\item $\mathsf{reason}$ -- mint reason; content depends on the token type. Justifies minting this token, e.g., by proving minting authority
		\item $\auxd'$ -- auxiliary payload (application-specific; e.g. asset value for fungible tokens)
	\end{itemize}
	\item $\pi_0$ -- inclusion proof from the Unicity Service
\end{itemize}

The reason is part of the certified transaction data and therefore fixed forever by $\txhash$. A reason format that must remain compressible states its dependencies on other tokens \emph{by identifier} rather than by embedding them, so that the evidence for those tokens travels beside the token and may be re-encoded; this is the \emph{reference form} of Sec.~\ref{sec:token-evidence}.

The \emph{token identifier}\index{token!identifier} is derived as
\[
\mathsf{id} \;:=\; H(\mathsf{salt}, \alpha) \;\in\; \idtype \;.
\]
This ensures that two tokens minted on different networks cannot induce colliding state identifiers.

$\mathsf{MINT\_SUFFIX}$\index{MINT\_SUFFIX} is a fixed domain separator constant. The minting key pair $(\mathsf{sk}_\mathsf{mint}, \mathsf{pk}_\mathsf{mint})$ is a public constant; it serves only to provide a uniform request interface with the Unicity Service. Values: Appendix~\ref{app:el-constants}.

\paragraph{Certifying a mint transaction} $T_0 = (\sthash, D_\mathsf{mint})$:
\begin{enumerate}
	\item $\txhash \gets H(D_\mathsf{mint})$
	\item $h_T \gets H(\sthash, \txhash)$
	\item $\sigma \gets \mathsf{Sign}(\mathsf{sk}_\mathsf{mint}, h_T)$
	\item $Q \gets (\mathsf{pk}_\mathsf{mint}, \sthash, \txhash, \sigma)$
	\item $\pi_0 \gets \unisrv(Q)$
\end{enumerate}

\paragraph{Verifying a certified mint transaction} $(T_0, \pi_0)$ against trust base $\mathcal{T}$, using known, fixed mint keys:
\begin{enumerate}
	\item require $T_0.D_\mathsf{mint}.\alpha = \pi_0.UC.C^\mathsf{r}.\alpha = \mathcal{T}.\alpha$
	\item derive $\mathsf{id} \gets H(T_0.D_\mathsf{mint}.\mathsf{salt}, T_0.D_\mathsf{mint}.\alpha)$;\; require $T_0.\sthash = H(\mathsf{id}, \mathsf{MINT\_SUFFIX})$
	\item $\txhash \gets H(D_\mathsf{mint})$;\; require $\txhash = \pi_0.\txhash$
	\item $\mathcal{V}(H(\mathsf{pk}_\mathsf{mint}, \sthash), \txhash, \pi_0, \mathcal{CD}_\beta, \mathcal{T}) = 1$
	\item Mint authorization check on $\mathsf{ty}$, $\mathsf{reason}$ and $\auxd'$: mint reason validity and auxiliary payload format and semantics, dispatched by token type (Sec.~\ref{sec:mint-authorization}, Alg.~\ref{alg:mint-auth})
\end{enumerate}

Correctness of the token id derivation is enforced implicitly by step~2: $\sthash$ is bound to $\mathsf{id}$ by the source-state-hash check, and $\mathsf{id}$ is recomputed from $(\mathsf{salt}, \alpha)$.


\subsubsection{Transfer Transaction}\label{sec:transfer-tx}

\index{transfer transaction!structure}
A \emph{certified transfer transaction} is a tuple $(T, u, \pi)$, where $T = (\sthash, D)$:
\begin{itemize}
	\item $D = (\predi', x, \auxd')$ -- transaction data:
	\begin{itemize}
		\item $\predi'$ -- spending predicate of the next owner
		\item $x \gets \{0,1\}^\ell$ -- random value for state hash derivation
		\item $\auxd'$ -- auxiliary data for the next state
	\end{itemize}
	\item $u$ -- unlocking argument satisfying the current predicate $\predi$
	\item $\pi$ -- inclusion proof from the Unicity Service
\end{itemize}

\paragraph{Certifying a transfer transaction} $T = (\sthash, D)$ in the current state $(\predi, h)$:
\begin{enumerate}
	\item $\txhash \gets H(D)$
	\item $h_T \gets H(\sthash, \txhash)$
	\item Create $u$ such that $\predi(\tau_\mathsf{exp}, h_T, u) = 1$ for an expected system time $\tau_\mathsf{exp}$
	\item $Q \gets (\predi, \sthash, \txhash, u)$
	\item $\pi \gets \unisrv(Q)$
\end{enumerate}

\paragraph{Verifying a certified transfer transaction} $(T, u, \pi)$ in state $(\predi, h)$:
\begin{enumerate}
	\item $T.\sthash = h$ \quad (state hash matches expected)
	\item $\pi.UC.C^\mathsf{r}.\alpha = \mathcal{T}.\alpha$ \quad (inclusion proof is from the same network as the trust base)
	\item $\txhash \gets H(T.D)$;\; require $\txhash = \pi.\txhash$ \quad (transaction data binds to the certified SMT leaf)
	\item $\predi(\mathsf{time}(\pi), H(\sthash, \txhash), u) = 1$ \quad (predicate satisfied)
	\item $\mathcal{V}(H(\predi, T.\sthash), \txhash, \pi, \mathcal{CD}_\beta, \mathcal{T}) = 1$ \quad (inclusion proof valid and certified by the correct shard)
	\item Additional token type-specific checks (Sec.~\ref{sec:token-types})
\end{enumerate}

\subsection{Token Verification}\label{sec:token-verification}

\index{token!verification}\index{functions!VerifyToken}
$\mathsf{VerifyToken}$ -- token verification function of type $\mathbb{L} \times \mathbb{UB} \to \bool$

\textbf{Input}:
\begin{enumerate}
	\item $\mathcal{L} = (T_0^\mathsf{cert}, [\mathcal{H}], T_{m+1}^\mathsf{cert}, \ldots, T_n^\mathsf{cert})$ -- token, where the optional compressed history $\mathcal{H}$ stands for transfers $1 \ldots m$ (Sec.~\ref{sec:history-compression}); an uncompressed token omits $\mathcal{H}$ and has $m = 0$. The watermark $m$ is implicit in the representation, not a stored field
	\item $\mathcal{T}$ -- trust base
\end{enumerate}

\textbf{Output}: \TRUE or \FALSE

\textbf{Computation}:
\begin{algorithmic}[0]
	\State \Parse $T_0^\mathsf{cert}$ \textbf{as} $(T_0, \pi_0)$
	\If {$T_0.D_\mathsf{mint}.\alpha \ne \mathcal{T}.\alpha$} \Return \FALSE \EndIf
	\If {$\neg \Call{VerifyMintTransaction}{T_0, \pi_0, \mathcal{T}}$} \Return \FALSE \EndIf
	\State $\predi^0 \gets T_0.D_\mathsf{mint}.\predi'$
	\State $h^0 \gets H(H(T_0.D_\mathsf{mint}.\mathsf{salt}, T_0.D_\mathsf{mint}.\alpha), \mathsf{MINT\_SUFFIX})$
	\If {$\mathcal{H}$ present}
		\If {$\neg \Call{VerifyCompressedHistory}{\mathcal{H}, \predi^0, h^0, \mathcal{T}}$} \Return \FALSE \EndIf
		\State $\predi^{m} \gets \decpred(\mathcal{H}.e)$;\quad $h^{m} \gets \mathcal{H}.h$ \Comment{carry restored from the proof}
	\EndIf
	\For {$i \gets m+1 \ldots n$}
		\State \Parse $T_i^\mathsf{cert}$ \textbf{as} $(T_i, u_i, \pi_i)$
		\If {$\neg \Call{VerifyTransferTransaction}{T_i, u_i, \pi_i, \predi^{i-1}, h^{i-1}, \mathcal{T}}$} \Return \FALSE \EndIf
		\State $\predi^{i} \gets T_i.D.\predi'$
		\State $h^{i} \gets H(h^{i-1}, T_i.D.x)$
	\EndFor
	\State \Return \TRUE
\end{algorithmic}

$\Call{VerifyMintTransaction}{}$ and $\Call{VerifyTransferTransaction}{}$ are defined by verification steps in chapters \ref{sec:mint-tx}, \ref{sec:transfer-tx}; $\Call{VerifyCompressedHistory}{}$ in Sec.~\ref{sec:compressed-verification}.

Some mint reasons embed complete source tokens. These are verified iteratively under the same trust base, verifier registry and cumulative resource limits as the outer token (Sec.~\ref{sec:nested-verification}).

\section{Programmable Spending Conditions}\label{sec:predicates}

Instead of restricting ownership to a single public key, the Unicity execution layer generalizes ownership to \emph{predicates}\index{predicate} -- programmable boolean functions that define the conditions under which a token state can be spent. This enables smart-contract-like functionality executed off-chain by relying parties rather than by consensus participants.

\subsection{Predicate Framework}\label{sec:predicate-framework}

\index{predicate!framework}
A \emph{predicate} $\predi_\mathsf{name}(\mathsf{par}; \cdot)$ is a boolean function with:
\begin{itemize}
	\item \textbf{Name} $\mathsf{name}$ -- identifies the predicate type
	\item \textbf{Parameters} $\mathsf{par}$ -- type-dependent configuration (e.g. a public key)
	\item \textbf{Arguments} $(\tau, m, u)$:
	\begin{itemize}
		\item $\tau \in \mathbb{T}$ -- system time, extracted from the Unicity Seal timestamp $C^\mathsf{r}.t_r$
		\item $m \in \hashtype$ -- message hash $H(\sthash, \txhash)$
		\item $u$ -- unlocking argument, structure depends on predicate type
	\end{itemize}
\end{itemize}

The predicate evaluates to $\predi_\mathsf{name}(\mathsf{par}; \tau, m, u) \in \{0, 1\}$.


\subsubsection{Time Reference}\label{sec:time-extraction}

\index{$\tau$}\index{time extraction}
Predicate evaluation must be deterministic and transparent: the Unicity Service (at certification time) and any later verifier (re-validating from an inclusion proof) must agree on the exact value of $\tau$ used. The system therefore fixes $\tau$ per Aggregator round, with the value coming through BFT Core consensus.

\paragraph{Per-round fixed reference time.}
The BFT Core's Unicity Seal carries a wall-clock round-creation timestamp $C^\mathsf{r}.t_r$ (Sec.~\ref{se:unicity-certificate}), with one-second precision, agreed by BFT Core consensus. When Aggregator assembles a certification request for its round $n{+}1$, it copies the timestamp from the Unicity Seal of the \emph{previous} UC it is extending into the Shard Input Record field $\mathcal{IR}.t$ (Sec.~\ref{shard-input-record}):
\[
	\mathsf{CR}.\mathcal{IR}.t \;\gets\; UC_-.C^\mathsf{r}.t_r
\]
where $UC_-$ is the last valid Unicity Certificate of that shard (which the Aggregator is \emph{extending}). This is the \emph{reference time for request validation} of the round being validated. All predicates evaluated against Unicity Service requests in that round use this single value as $\tau$.

\paragraph{BFT Core enforcement.}
The BFT Core verifies the Aggregator's choice of reference time as part of request admission (Sec.~\ref{certification-request}, check $\mathsf{CR}.\mathcal{IR}.t = \mathcal{SI}[\beta,\sigma].UC_-.C^\mathsf{r}.t_r$).

\paragraph{Extraction from inclusion proofs.}
Given an inclusion proof $\pi^\mathsf{inc} = (\mathsf{sid}, \txhash, C^\mathsf{inc}, UC)$, the \emph{system time} used for predicate evaluation is extracted as
\[
	\mathsf{time}(\pi^\mathsf{inc}) \;=\; UC.\mathcal{IR}.t
\]
This is the same value the Aggregator used when admitting the request -- the previous seal's $t_r$, copied into $\mathcal{IR}.t$ and BFT-verified. Re-validation by any later verifier is therefore deterministic and yields the identical predicate evaluation outcome.

Note that $UC.\mathcal{IR}.t \ne UC.C^\mathsf{r}.t_r$ in general: $\mathcal{IR}.t$ is the reference time of the round \emph{being} certified (taken from the prior seal), whereas $C^\mathsf{r}.t_r$ is the wall-clock time at which the new seal itself was produced. Predicate evaluation uses $\mathcal{IR}.t$.

\subsection{Standard Predicates}\label{sec:standard-predicates}

\subsubsection{Signature Predicate}

\index{predicate!signature ($\predi_\mathsf{sig}$)}
The \emph{signature predicate} $\predi_\mathsf{sig}(\mathsf{pk};\cdot)$ with a single public key $\mathsf{pk}$ as parameter is equivalent to digital signature verification. This is the basic ``pay to public key'' ownership model.

\begin{itemize}
	\item \textbf{Parameters}: $\mathsf{pk}$ (public key)
	\item \textbf{Unlocking argument}: $u = \sigma$ (digital signature)
	\item \textbf{Definition}: $\predi_\mathsf{sig}(\mathsf{pk}; \tau, m, \sigma) = 1$ iff $\mathsf{Verify}(\mathsf{pk}, m, \sigma) = 1$
\end{itemize}

\subsubsection{P2PKH Predicate}

\index{predicate!P2PKH ($\predi_\mathsf{p2pkh}$)}
The \emph{Pay-to-Public-Key-Hash} predicate $\predi_\mathsf{p2pkh}(h_\mathsf{pk};\cdot)$ stores only the hash of the public key, requiring the spender to reveal the full public key alongside the signature.

\begin{itemize}
	\item \textbf{Parameters}: $h_\mathsf{pk} \in \hashtype$ (public key hash)
	\item \textbf{Unlocking argument}: $u = (\mathsf{pk}, \sigma)$
	\item \textbf{Definition}: $\predi_\mathsf{p2pkh}(h_\mathsf{pk}; \tau, m, (\mathsf{pk}, \sigma)) = 1$ iff $H(\mathsf{pk}) = h_\mathsf{pk} \;\land\; \mathsf{Verify}(\mathsf{pk}, m, \sigma) = 1$
\end{itemize}

\subsubsection{P2SH Predicate}\label{sec:p2sh}

\index{predicate!P2SH ($\predi_\mathsf{p2sh}$)}
The \emph{Pay-to-Script-Hash} predicate $\predi_\mathsf{p2sh}(h_\predi;\cdot)$ generalizes P2PKH by storing the hash of an arbitrary predicate rather than just a public key hash. The recipient is identified by $h_\predi = H(\mathsf{CBOR}(\predi'))$, which provides a uniform-size recipient field regardless of predicate complexity and preserves privacy by hiding the predicate type until the token is spent.

\begin{itemize}
	\item \textbf{Parameters}: $h_\predi \in \hashtype$ (predicate hash)
	\item \textbf{Unlocking argument}: $u = (\predi', u')$ where $\predi'$ is the full predicate and $u'$ is its unlocking argument
	\item \textbf{Definition}: $\predi_\mathsf{p2sh}(h_\predi; \tau, m, (\predi', u')) = 1$ iff $H(\mathsf{CBOR}(\predi')) = h_\predi \;\land\; \predi'(\tau, m, u') = 1$
\end{itemize}

When spending, the full predicate $\predi'$ is revealed in the lock script field of the transfer transaction, and verifiers check that $H(\mathsf{CBOR}(\predi'))$ matches the recipient hash from the previous transaction.

\subsubsection{Multi-Signature Predicate}

\index{predicate!multi-signature ($\predi_\mathsf{msig}$)}
The \emph{multi-signature predicate} $\predi_\mathsf{msig}(\mathsf{pk}_1, \ldots, \mathsf{pk}_n;\cdot)$ requires $n$ valid signatures from $n$ specified public keys (all-of-$n$).

\begin{itemize}
	\item \textbf{Parameters}: $(\mathsf{pk}_1, \ldots, \mathsf{pk}_n)$
	\item \textbf{Unlocking argument}: $u = (\sigma_1, \ldots, \sigma_n)$
	\item \textbf{Definition}: $\predi_\mathsf{msig}(\mathsf{pk}_1, \ldots, \mathsf{pk}_n; \tau, m, u) = 1$ iff $\mathsf{Verify}(\mathsf{pk}_i, m, \sigma_i) = 1$ for every $i \in \{1, \ldots, n\}$
\end{itemize}


\subsubsection{Threshold-Signature Predicate}

\index{predicate!threshold-signature ($\predi_\mathsf{tsig}$)}
The \emph{threshold-signature predicate} $\predi_\mathsf{tsig}(k, \mathsf{pk}_1, \ldots, \mathsf{pk}_n;\cdot)$ requires $k$-of-$n$ valid signatures from distinct public keys.

\begin{itemize}
	\item \textbf{Parameters}: $(k, \mathsf{pk}_1, \ldots, \mathsf{pk}_n)$ where $k \in \{1, \ldots, n\}$
	\item \textbf{Unlocking argument}: $u = ((\sigma_1, j_1), \ldots, (\sigma_k, j_k))$ where $j_i$ is the index of the public key used for $\sigma_i$
	\item \textbf{Definition}: $\predi_\mathsf{tsig}(k, \mathsf{pk}_1, \ldots, \mathsf{pk}_n; \tau, m, u) = 1$ iff:
	\begin{enumerate}
		\item $\mathsf{Verify}(\mathsf{pk}_{j_i}, m, \sigma_i) = 1$ for every $i \in \{1, \ldots, k\}$
		\item All indices $j_i$ are distinct: $j_i = j_{i'}$ implies $i = i'$
	\end{enumerate}
\end{itemize}

The distinctness requirement prevents satisfying the predicate by presenting $k$ copies of the same signature.


\subsubsection{Burn Predicate}\label{sec:burn-predicate}

\index{predicate!burn ($\predi_\mathsf{burn}$)}
The \emph{burn predicate} $\predi_\mathsf{burn}(h_\mathsf{reason})$ cannot be unlocked. A token transferred to a burn predicate is permanently spent.

\begin{itemize}
	\item \textbf{Parameters}: $h_\mathsf{reason} \in \hashtype$ (reason hash, linking the burn to its purpose)
	\item \textbf{Unlocking argument}: none
	\item \textbf{Definition}: $\predi_\mathsf{burn}(h_\mathsf{reason}; \tau, m, u) = 0$ for all arguments
\end{itemize}

The burn predicate is used in token splitting (Sec.~\ref{sec:token-splitting}), where the reason hash is $\mathsf{SHA\text{-}256}(b_\mathcal{M})$ for the complete canonical split-manifest encoding $b_\mathcal{M}$.


\subsubsection{Open Predicate}\label{sec:open-predicate}

\index{predicate!open ($\predi_\mathsf{open}$)}
The \emph{open predicate} $\predi_\mathsf{open}$ is satisfied by any argument --- the dual of the burn predicate.

\begin{itemize}
	\item \textbf{Parameters}: none
	\item \textbf{Unlocking argument}: ignored
	\item \textbf{Definition}: $\predi_\mathsf{open}(\tau, m, u) = 1$ for all arguments
\end{itemize}

On its own, an open-owned state is spendable by anyone and holds no value. Its purpose is \emph{protocol-owned} tokens: combined with type-defined per-transfer checks (Sec.~\ref{sec:mint-authorization}), spending is constrained by validation rules instead of keys --- any party may advance the token's state, but only along transitions its type permits (e.g.\ autonomous pools, Appendix~\ref{app:autonomous-pools}).


\subsubsection{Timelock Predicate}

\index{predicate!timelock ($\predi_\mathsf{tlock}$)}
The \emph{timelock predicate} $\predi_\mathsf{tlock}(\mathsf{pk}, \tau_\mathsf{min};\cdot)$ prevents spending until the system time reaches a specified threshold. This is used to implement e.g. vesting schedules and lock-up periods for tokens.

\begin{itemize}
	\item \textbf{Parameters}: $(\mathsf{pk}, \tau_\mathsf{min})$ where $\mathsf{pk}$ is a public key and $\tau_\mathsf{min} \in \mathbb{T}$ is the unlock time
	\item \textbf{Unlocking argument}: $u = \sigma$ (digital signature)
	\item \textbf{Definition}: $\predi_\mathsf{tlock}(\mathsf{pk}, \tau_\mathsf{min}; \tau, m, \sigma) = 1$ iff $\tau \ge \tau_\mathsf{min} \;\land\; \mathsf{Verify}(\mathsf{pk}, m, \sigma) = 1$
\end{itemize}

The token remains locked until system time $\tau \ge \tau_\mathsf{min}$, after which it can be spent by producing a valid signature under $\mathsf{pk}$ and forming a witness unlocking the predicate and appending a spending transaction to the token ledger.


\subsubsection{Hashed Timelock Predicate}

\index{predicate!hashed timelock ($\predi_\mathsf{htlc}$)}
The \emph{hashed timelock predicate} $\predi_\mathsf{htlc}(\mathsf{pk}, \mathsf{pk}', y, \tau_\mathsf{max};\cdot)$ combines hash-locked and time-locked spending paths. The parameter $\mathsf{pk}$ is the refund key (original sender), $\mathsf{pk}'$ is the claim key (intended recipient), $y \in \hashtype$ is a hash lock, and $\tau_\mathsf{max} \in \mathbb{T}$ is a timeout.

\begin{itemize}
	\item \textbf{Parameters}: $(\mathsf{pk}, \mathsf{pk}', y, \tau_\mathsf{max})$
	\item \textbf{Unlocking argument}: $u = (x, \sigma)$ where $x$ is a preimage candidate and $\sigma$ is a digital signature
	\item \textbf{Definition}: $\predi_\mathsf{htlc}(\mathsf{pk}, \mathsf{pk}', y, \tau_\mathsf{max}; \tau, m, (x, \sigma)) = 1$ iff (a) or (b):
	\begin{itemize}
		\item[(a)] \emph{Claim path}: $\mathsf{Verify}(\mathsf{pk}', m, \sigma) = 1 \;\land\; y = H(x) \;\land\; \tau \le \tau_\mathsf{max}$
		\item[(b)] \emph{Refund path}: $\mathsf{Verify}(\mathsf{pk}, m, \sigma) = 1 \;\land\; \tau > \tau_\mathsf{max}$
	\end{itemize}
\end{itemize}

Clause~(a) allows the recipient to claim the token before the timeout by revealing the $H$-preimage $x$ of $y$ and signing with $\mathsf{pk}'$. Clause~(b) allows the sender to reclaim the token after the timeout by signing with $\mathsf{pk}$.

Example use-case is atomic swap, where two HTLC predicates on different ledgers/partitions share the same hash lock $y$; claiming on one ledger reveals $x$, enabling the counterparty to claim on the other. Note that this assumes ledgers to be public, which is not always the case on p2p networks.


\section{Interaction with Unicity Service}\label{sec:el-us-interaction}

\index{Unicity Service!execution layer interaction}
This section describes how the execution layer interacts with the Unicity Service (Sec.~\ref{sec:request-validation}) for state transition certification.

\subsection{Certification Request}

A certification request from the execution layer is a tuple $Q = (\predi, \sthash, \txhash, u)$, where:
\begin{itemize}
	\item $\predi$ -- spending predicate of the current owner
	\item $\sthash$ -- current state hash
	\item $\txhash$ -- transaction data hash
	\item $u$ -- unlocking argument satisfying $\predi$
\end{itemize}

\subsection{Processing}

The Unicity Service processes the request as follows:
\begin{enumerate}
	\item Compute state identifier: $\mathsf{sid} \gets H(\predi, \sthash)$
	\item Compute message hash: $m \gets H(\sthash, \txhash)$
	\item Evaluate predicate: verify $\predi(\tau, m, u) = 1$
	\item Check uniqueness: verify $R[\mathsf{sid}] = \bot$
	\item If both checks pass: $R[\mathsf{sid}] \gets \txhash$\footnote{The current SDK implementation stores $H(\mathsf{CBOR}(\predi, \sthash, \txhash, u))$ as the leaf value instead of $\txhash$, because of backward compatibility with the legacy SDK.}
\end{enumerate}

If the request is accepted, the Unicity Service returns an inclusion proof $\pinc$. If the state has already been spent (uniqueness check fails) or the predicate evaluation fails, the request is rejected.


\section{Transaction Flow}\label{sec:transaction-flow}

\section{Token Types and Mint Authorization}\label{sec:token-types}

\index{token!type}\index{mint reason}\index{mint authorization}
Minting on the Unicity platform is technically permissionless: the minting key pair is a public constant (Sec.~\ref{sec:mint-tx}, Appendix~\ref{app:el-constants}), so a certified mint transaction proves only that the token identifier is fresh --- it conveys no issuance authority by itself. All authority to mint is carried by data inside the genesis and is re-verified by every subsequent recipient of the token. Two genesis fields implement this:
\begin{itemize}
	\item $\mathsf{ty}$ -- the \emph{token type}, classifying the token and selecting the validation rules that govern it for its entire lifetime;
	\item $\mathsf{reason}$ -- the \emph{mint reason}, an abstract payload that justifies the act of minting under the rules of type $\mathsf{ty}$: an issuer's authorization signature, a value-conservation proof of a split, a proof of external backing, or a zero-knowledge proof of an arbitrary type-defined statement.
\end{itemize}

This section specifies the generic verification flow that checks mint authorization --- the expansion of step~5 of mint-transaction verification (Sec.~\ref{sec:mint-tx}) and of step~6 of transfer verification (Sec.~\ref{sec:transfer-tx}). Concrete reason formats and standard token types are provided in Appendix~\ref{app:token-registry}.

\subsection{Token Type}\label{sec:token-type}

\index{token type}
A token type is an opaque byte string $\mathsf{ty} \in \bytestr$ with $1 \le \len{\mathsf{ty}} \le 64$ (typically 32 bytes), compared by byte equality. The type is fixed by the mint transaction and is immutable: no transfer, split (Sec.~\ref{sec:split-verification}, check~6), or any other operation may change it.

The identifier itself carries no meaning; it binds the token to a \emph{token type definition}
\[
\mathcal{D}_\mathsf{ty} = (\mathsf{ty},\; \mathsf{RT},\; \Call{ParseAux}{},\; \Call{VerifyIssuance}{},\; \mathsf{meta}),
\]
where
\begin{itemize}
	\item $\mathsf{RT}$ -- the set of admissible mint-reason formats, given as CBOR semantic tags (Appendix~\ref{app:cbor-tags}); the set MAY include $\bot$, admitting an absent reason;
	\item $\Call{ParseAux}{\mathsf{ty}, \auxd'}$ -- the deterministic decoder and validator of the token's genesis payload; for fungible types this is the function $\Call{Assets}{}$ of Sec.~\ref{sec:token-splitting};
	\item $\Call{VerifyIssuance}{}$ -- the type's issuance policy: a boolean function over the certified genesis, run in addition to the format-level reason verifier (e.g.\ pinning the expected issuer key, a bridge configuration, or a proof-system verification key);
	\item $\mathsf{meta}$ -- external, non-consensus metadata (display name, symbol, decimals, icons; Appendix~\ref{app:asset-metadata}).
\end{itemize}

A published definition MUST be frozen: every verifier of every recipient must apply byte-identical parsing and verification rules indefinitely, or tokens of that type would verify for some recipients and fail for others.

\paragraph{Type identifier derivation.} A type identifier MAY be an arbitrary (e.g.\ random) value, bound to its definition by the token type registry (Appendix~\ref{app:type-registry}). For new types it is RECOMMENDED to derive the identifier from the definition itself,
\[
\mathsf{ty} := H(\mathsf{TYPE\_DEF},\; b_\mathcal{D}),
\]
where $b_\mathcal{D}$ is the canonical CBOR encoding of the frozen definition manifest (Appendix~\ref{app:type-registry}) and $\mathsf{TYPE\_DEF}$ a fixed domain separator. This makes the binding between identifier and rules self-authenticating.

\subsection{Mint Reason}\label{sec:mint-justification}

\index{mint justification}\index{mint reason}
The mint reason is either absent ($\bot$) or a byte string containing a single tagged deterministic CBOR item. The semantic tag $t$ identifies the \emph{reason format}: the parsing rules and the verification algorithm of the reason body. Reason formats are format-level building blocks, decoupled from token types: one format (e.g.\ the split reason, Sec.~\ref{sec:token-splitting}) serves many token types, and one type may admit several formats for its issuance events. The type definition's admissible set $\mathsf{RT}$ makes the coupling explicit.

The fields should be interpreted as follows:

\begin{description}
	\item[reason] authorizes the mint
	\item[aux'] describes the minted token, a message to the next (') verifier or a transaction meta-data field in general.
\end{description}

A reason verifier receives the complete mint-transaction data and validates the binding between the two --- e.g.\ that the value declared in $\auxd'$ equals the value the reason actually authorizes.

\subsection{Verifier Registry}\label{sec:verifier-registry}

\index{verifier registry}
A relying party's verification capability is described by a \emph{verifier registry}
\[
\Gamma = (\mathcal{RV},\; \mathcal{TD},\; \Lambda),
\]
where
\begin{itemize}
	\item $\mathcal{RV}$ -- a partial map from reason-format tags to \emph{reason verifiers}; $\mathcal{RV}[t]$ is the verification function of format $t$, of the form $V_t(T_0, \pi_0, \Gamma, \mathsf{collect}) \in \{0,1\}$;
	\item $\mathcal{TD}$ -- a partial map from token type identifiers to token type definitions $\mathcal{D}_\mathsf{ty}$;
	\item $\Lambda$ -- cumulative resource budgets (bytes, items, nesting depth, proof steps, embedded tokens; cf.\ Appendix~\ref{app:split-proof-encoding}) shared by an entire verification run; when this budget is exhausted, verification fails deterministically with a resource-limit error.
\end{itemize}

The contents of $\mathcal{RV}$ and $\mathcal{TD}$ are an application-level trust decision (e.g., a wallet is designed to handle a specific set of token types, sufficient for its business goals). An implementation ships built-in verifiers for the standard formats and types (Appendix~\ref{app:token-registry}) and accepts application-supplied plug-ins for others. The registry is shared by the whole verification of a token: e.g., tokens embedded in mint reasons (Sec.~\ref{sec:nested-verification}) are verified under the same $\Gamma$, the same trust base $\mathcal{T}$, and the remaining budget $\Lambda$ as the outer token (cf.\ Sec.~\ref{sec:split-verification}, check~3).

\subsection{Mint Authorization Check}\label{sec:mint-authorization}

Algorithm~\ref{alg:mint-auth} defines the mint authorization check, run as step~5 of mint-transaction verification (Sec.~\ref{sec:mint-tx}) after the generic certification checks (steps~1--4) have passed. Every $\mathsf{ensure}$ failure, decoding error or exhausted budget rejects the transaction. $\mathsf{collect}$ is the nested-token collector of Sec.~\ref{sec:nested-verification}.

\begin{algorithm}[!htb]
\caption{Mint Authorization Verification}\label{alg:mint-auth}
\begin{algorithmic}[]
\Function{VerifyMintAuthorization}{$T_0, \pi_0, \Gamma, \mathsf{collect}$}
	\State $D \gets T_0.D_\mathsf{mint}$
	\State $\mathcal{D}_\mathsf{ty} \gets \Gamma.\mathcal{TD}[D.\mathsf{ty}]$
	\If{$\mathcal{D}_\mathsf{ty} = \bot$} \Return \FALSE \Comment{fail-shut: unsupported token type} \EndIf
	\If{$D.\mathsf{reason} = \bot$}
		\State ensure($\bot \in \mathcal{D}_\mathsf{ty}.\mathsf{RT}$) \Comment{type admits absent reason}
	\Else
		\State $t \gets$ CBOR semantic tag of $D.\mathsf{reason}$ \Comment{malformed CBOR rejects}
		\State ensure($t \in \mathcal{D}_\mathsf{ty}.\mathsf{RT}$) \Comment{type admits this reason format}
		\State $V \gets \Gamma.\mathcal{RV}[t]$
		\If{$V = \bot$} \Return \FALSE \Comment{fail-shut: unsupported reason format} \EndIf
		\State ensure($V(T_0, \pi_0, \Gamma, \mathsf{collect}) = 1$) \Comment{format-specific verification}
	\EndIf
	\State ensure($\mathcal{D}_\mathsf{ty}.\Call{ParseAux}{D.\mathsf{ty}, D.\auxd'} \ne \bot$) \Comment{payload well-formed for this type}
	\State ensure($\mathcal{D}_\mathsf{ty}.\Call{VerifyIssuance}{T_0, \pi_0} = 1$) \Comment{type-specific issuance policy}
	\State \Return \TRUE
\EndFunction
\end{algorithmic}
\end{algorithm}

A reason verifier $V_t$ obtains the tokens a reason depends on from the \emph{evidence set} accompanying the token (Sec.~\ref{sec:token-evidence}) when the format is in reference form, and from the reason body itself when the format embeds them.

Reason bodies and payloads are decoded under the strict deterministic-CBOR discipline of Appendix~\ref{app:split-proof-encoding}: wrong or unknown tags, non-minimal encodings, wrong field counts or types, trailing bytes, and exhausted budgets are all rejected.

Type-specific validation is not limited to the genesis: step~6 of transfer verification (Sec.~\ref{sec:transfer-tx}) runs the per-transfer checks of $\mathcal{D}_\mathsf{ty}$, where the type defines any. For most types there are none --- the authoritative type-governed payload is the genesis payload $\auxd'_0$, and transfer-level auxiliary data is free-form transport (e.g.\ ephemeral keys of Sec.~\ref{sec:private-transactions}) unless the type states otherwise.

\paragraph{Fail-shut policy.}\index{fail-shut policy}
On the Unicity Mainnet ($\alpha = 1$), token acceptance MUST be \emph{fail-shut}: a relying party accepting a token MUST reject any token whose type has no entry in $\mathcal{TD}$, whose reason format has no entry in $\mathcal{RV}$, or whose reason tag lies outside the type's admissible set --- each with a distinct diagnostic error. A permissive mode that skips authorization checks for unregistered types MAY exist in testnet for diagnostic, archival or explorer tooling, but MUST NOT gate acceptance of value.

\subsection{Nested Tokens and Resource Limits}\label{sec:nested-verification}

\index{nested token verification}
Several reason formats embed complete tokens: the burned source token of a split, and in general any format whose authorization derives from the prior existence of another certified token. A reason verifier MUST NOT verify embedded tokens by recursive invocation of $\mathsf{VerifyToken}$; instead it validates the reason's own structure and bindings, and emits each embedded token to the collector $\mathsf{collect}$. The driver maintains a worklist seeded with the outer token: it pops a token, verifies it (which may collect further ancestors), and repeats until the worklist is empty or the budget $\Lambda$ is exhausted.

All components of $\Lambda$ are cumulative across the entire worklist. A maliciously deep or wide provenance graph (e.g.\ repeated splits of splits) therefore exhausts the budget and is rejected as invalid, rather than exhausting the verifier's memory or time. Budget limits are part of the network's validation policy: two verifiers with the same $\Gamma$ accept exactly the same tokens, making the validation deterministic.

\section{Fungible Token Payload}\label{sec:fungible-tokens}

For fungible tokens (e.g. digital currency), the execution layer defines additional structure within the token's auxiliary data to support money-like operations: value tracking, splitting, and value conservation proofs.

\subsection{Asset Structure}\label{sec:asset-structure}

\index{asset}
An \emph{asset} is a pair $(\mathsf{aid}, v)$, where:
\begin{itemize}
	\item $\mathsf{aid}$ -- asset identifier, specifying the asset type (e.g. currency)
	\item $v \in \mathbb{N}$ -- asset value (non-negative integer amount)
\end{itemize}

A token may carry multiple assets, represented as a collection:
\[
\mathcal{A} = \{(\mathsf{aid}_1, v_1), \ldots, (\mathsf{aid}_m, v_m)\}
\]
where all asset identifiers $\mathsf{aid}_i$ are distinct.

\subsection{Token Splitting}\label{sec:token-splitting}

\index{token!splitting}
Splitting allows a fungible token to be divided into multiple new tokens while preserving the amount of every enclosed asset independently.  The protocol uses one \emph{Radix Sparse Merkle Sum Tree}\index{Radix Sparse Merkle Sum Tree} (RSMST) per asset identifier.  An RSMST reuses the radix sparse Merkle tree structure with sums committed next to every child hash, so verification of any output proves that its amount is included in a committed allocation whose total equals the source amount.

Each fractional token is self-contained and carries the complete certified burned source token in its mint reason. Implementations may deduplicate identical source-token bytes internally.

\subsubsection{Split Protocol}

Let $\Call{Assets}{\mathsf{ty},\auxd'}$ denote the token-type-specific, deterministic decoding and validation of a fungible payload.  Asset identifiers in the resulting collection are non-empty, distinct and placed in canonical bytewise order, and every amount is positive.  A payload containing a zero-valued entry is rejected rather than normalized.  Given a valid token $\mathcal{L}$ on network $\alpha$ carrying
\[
\mathcal{A}=\Call{Assets}{\mathsf{ty},\auxd'},
\]
the owner prepares $k \geq 1$ output mint transactions on the same network and with exactly the same token type $\mathsf{ty}$, with canonical asset collections $\mathcal{A}_1,\ldots,\mathcal{A}_k$.  Splitting is not a token-type conversion mechanism.  For every source asset identifier $\mathsf{aid}$ the allocations must satisfy
\[
\sum_{j=1}^{k} v_j(\mathsf{aid}) = v(\mathsf{aid})
\]
where a missing entry has value zero.  No output may introduce an asset identifier absent from $\mathcal{A}$.  Amounts of different asset identifiers are never added to or substituted for one another.

For output $j$, let $D_{\mathsf{out},j}$ consist of the source token identifier and all output mint fields except the mint reason.  Its commitment
\[
d_j = H(\mathsf{SPLIT\_OUTPUT},D_{\mathsf{out},j})
\]
binds the allocation to the source token, network, recipient predicate, salt and resulting token identifier, token type, and the complete canonical auxiliary payload.  In particular, a proof prepared for one recipient or token type cannot authorize a mint to another, even though the standard minting key is public.

The split proceeds as follows:
\begin{enumerate}
	\item Verify $\mathcal{L}$ completely, including its fungible payload, mint reason and issuer policy, before submitting any irreversible burn request.  Derive pairwise distinct output token identifiers $\mathsf{id}_j=H(\mathsf{salt}_j,\alpha)$ and the corresponding commitments $d_j$.
	\item For every source asset $\mathsf{aid}_i$ in canonical order, construct an RSMST $\mathcal{S}_i$.  For each output carrying that asset, insert the leaf
	\[
	(\mathsf{id}_j,d_j,v_j(\mathsf{aid}_i)).
	\]
	Require the RSMST root sum to equal $v(\mathsf{aid}_i)$.  Let $r_i$ be its root hash.
	\item Construct the \emph{split manifest}
	\[
	\mathcal{M}=\langle r_1,\ldots,r_m\rangle,
	\]
	where the roots are positionally aligned with the canonical source asset collection.  The manifest contains no repeated source identifier, asset identifiers or amounts: all are already authenticated by the burned token.  Its precise encoding $b_\mathcal{M}$ is defined in Appendix~\ref{app:split-proof-encoding}.  Extract and durably store every output's RSMST proofs and mint fields, together with the manifest and complete burn-transfer fields, before proceeding.
	\item Burn the source by creating and certifying a transfer whose auxiliary data is exactly $b_\mathcal{M}$ and whose recipient is $\predi_\mathsf{burn}(\mathsf{SHA\text{-}256}(b_\mathcal{M}))$.  The resulting certified burned token is denoted $\mathcal{L}_\mathsf{burn}$.
	\item Mint each output token $j$ with the exact fields committed by $d_j$.  Its mint reason contains $\mathcal{L}_\mathsf{burn}$ and, in canonical output-asset order, one RSMST inclusion proof for every asset it carries.  The proof contains only leaf-to-root sibling entries $(\delta,s,w)$ with explicit bifurcation depth, sibling hash and sibling sum; it omits the asset identifier, output identifier, output commitment, leaf amount and root hash because the verifier derives them respectively from the output payload, mint transaction, and split manifest.
\end{enumerate}


\subsubsection{Split Verification}\label{sec:split-verification}

Given a token whose mint reason claims split origin, the verifier must perform all of the following checks.  Failure of any check rejects the token.
\begin{enumerate}
	\item Decode the mint reason, manifest, payloads and proofs using deterministic CBOR.  Reject wrong or unknown tags, non-canonical integers or byte strings, duplicate or unordered asset identifiers, invalid field counts or types, trailing bytes, arithmetic overflow and any input exceeding the protocol's decoding and verification limits.
	\item Verify the output mint transaction and its Unicity Certificate.  Decode and validate its auxiliary payload according to its token type; the payload must contain a non-empty canonical collection of distinct, positive-valued assets.
	\item Recursively verify the complete burned source token, including every Unicity Certificate, transaction, nested mint reason, fungible payload and token type specific issuance policy, under the same trust base $\mathcal{T}$, verifier registry and cumulative resource limits used for the output.  Both tokens must have network identifier $\mathcal{T}.\alpha$.
	\item Require the source token to end in a certified transfer whose auxiliary data is the exact canonical split-manifest encoding $b_\mathcal{M}$ and whose recipient predicate is exactly $\predi_\mathsf{burn}(\mathsf{SHA\text{-}256}(b_\mathcal{M}))$.
	\item Decode the source fungible payload, place its distinct asset identifiers in canonical order, and require the manifest to contain exactly one root hash for each source asset in that order.
	\item Require the output token type to be byte-identical to the source token type.  A split proof cannot authorize minting under any other token type, even if that type would decode the same asset identifiers and amounts.
	\item Recompute $d_j$ from the verified source identifier and the output mint fields other than $\mathsf{reason}$.  The recomputation must cover the exact canonical recipient predicate, network, salt, token identifier, token type and complete auxiliary payload.
	\item Require the proof count to equal the number of assets in the output payload.  Associate proofs with assets only by their canonical order; reject missing, duplicate or additional proofs.
	\item For every output asset $(\mathsf{aid}_i,v_j(\mathsf{aid}_i))$, require that $\mathsf{aid}_i$ occurs in the source payload.  Verify its RSMST proof using key $\mathsf{id}_j$, leaf data $d_j$, leaf value $v_j(\mathsf{aid}_i)$ and expected root $r_i$ selected from the manifest.  Require both inclusion and root-hash equality.
	\item Require the root sum reconstructed by that proof to equal the source amount $v(\mathsf{aid}_i)$.  This equality is checked independently for every asset identifier and is the verifier-side value-conservation rule; successful construction by a wallet is not evidence of conservation.
\end{enumerate}

These checks establish that the source was authentic and irreversibly spent, the burn committed to the exact set of per-asset allocation roots, every accepted output and its ownership were fixed before the burn, and no accepted output can create value.  The protocol does not guarantee that every prepared output will subsequently be minted or delivered: failure to mint an output can destroy value but cannot transfer or inflate it.  The party performing the irreversible burn is responsible for durably retaining the manifest, output salts and proofs required to resume minting.

\subsection{Burn Transaction}\label{sec:burn-transaction}

\index{burn transaction}
A \emph{burn transaction} is a transfer transaction where the recipient predicate is $\predi_\mathsf{burn}(h_\mathsf{reason})$ (Sec.~\ref{sec:burn-predicate}). Since the burn predicate cannot be unlocked, the token is permanently spent and cannot be transferred further.

The reason hash $h_\mathsf{reason}$ links the burn to its purpose. In a split operation, it is the hash of the complete canonical split-manifest encoding $b_\mathcal{M}$, enabling verifiers of the resulting tokens to bind the source burn to the exact ordered vector of per-asset allocation roots.


\section{Token History Compression}\label{sec:history-compression}

\index{token compression}
A token accumulates one certified transaction per transfer, so verification cost and token size grow with its history (Sec.~\ref{sec:token-verification}). \emph{Compression} replaces a prefix of the transfer sequence with a succinct proof that the prefix was a valid, certified chain of transitions. The second dimension --- the ancestor tokens a split or merge genesis depends on --- is treated in Sec.~\ref{sec:provenance-compression}, on the machinery this section establishes.

Compression is a change of representation, not a transaction. No state is spent and none is created; the token identifier, the genesis and the current state are unchanged; the Unicity Service is not involved and observes nothing. A compressed token and the uncompressed token it was derived from denote the same token in the same state: whichever representation a holder presents, spending it consumes the same state identifier, which the Unicity Service admits at most once (Sec.~\ref{sec:request-validation}). Compression therefore requires no token-type opt-in and creates no double-representation risk.

Two consequences shape both sections. First, compression is \emph{discretionary} and outside the critical path of transacting: a holder compresses when it chooses --- typically as a background job --- and never as part of preparing a transaction. Second, compression is \emph{lossy and irreversible}: the proof does not yield the transfer records back. A holder that compresses and discards its records can no longer produce the uncompressed form, and can therefore no longer pay a relying party whose verifier lacks the compression verification keys. Wallets SHOULD retain the raw history independently and treat the compressed form as a transport representation rather than as storage.

\subsection{Design Constraints}

Two properties are imposed on the construction, both for the same reason --- keeping the proving relation small and the trust decisions in ordinary, auditable code:

\begin{description}
	\item[No certificate verification inside the relation] Every Unicity Certificate a compressed token depends on is verified by the relying party's normal $\mathsf{VerifyUnicityCert}$ path against its own trust base $\mathcal{T}$, exactly as for an uncompressed token, and enters the proof only as a certified scalar. The relation never contains BFT signature verification, validator sets or trust base evolution.
	\item[Issuance is never proven, only checked] The mint transaction, its reason and its payload remain present in full, for this token and --- through the issuance roots of Sec.~\ref{sec:token-certificate} --- for every ancestor whose genesis was an act of issuance. Mint authorization (Sec.~\ref{sec:mint-authorization}) is thus checked by the ordinary verifier under its own $\Gamma$, and no issuance format ever needs an in-relation counterpart.
\end{description}

\subsection{Anchored Inclusion and Anchor Accumulation}\label{sec:compression-anchors}

\index{anchor certificate}
Because the SMT is add-only (Sec.~\ref{sec:smt}), one recent certificate suffices to establish inclusion of many older leaves. Fix an \emph{anchor certificate} $UC^*$ and its root $h^* = UC^*.\mathcal{IR}.h$; a leaf $L = (\mathsf{sid}, \txhash)$ is anchored by an SMT inclusion certificate of $L$ against $h^*$ (Appendix~\ref{app:bridging-anchor}). This replaces one certificate verification per transition by one certificate plus a hash-path check per transition.

A proof produced today is anchored at today's root. When the holder later extends it with newer transitions, those are anchored at a newer root, and the older anchor cannot be re-derived: collapsing two anchors into one would require a consistency proof between two arbitrary certified roots, which the aggregation layer does not currently publish (consistency proofs are verified by the BFT Core when issuing a certificate, Sec.~\ref{sec:request-validation}, and not retained). A compressed history therefore carries an ordered list of anchors $\langle UC^*_1, \ldots, UC^*_F\rangle$, one per compression event, accumulated into a single public value
\[
A_0 := H(\mathsf{ANCHOR\_INIT}), \qquad A_f := H(A_{f-1},\; UC^*_f.\mathcal{IR}.h),
\]
so that the proof's public input stays constant-size while the verifier recomputes $A_F$ from the certificates it has just verified itself.

Section~\ref{sec:compression-folding} shows how a holder collapses the list back to $F = 1$ without retaining the history, so $F$ grows only for holders that choose not to.

\subsection{Two Relations}\label{sec:compression-relations}

The statement is split along the line separating \emph{validity} of the transfer chain from its \emph{certification}. The two halves have very different cost profiles and very different re-proving requirements, and separating them is what makes anchors collapsible.

Both relations, their proof system and their verification keys $\mathsf{vk}_\mathsf{ch}, \mathsf{vk}_\mathsf{in}$ are network-level constants, frozen and published in the registry (Appendix~\ref{app:type-registry}) before activation; every verifier pins $H(\mathsf{vk}_\mathsf{ch})$ and $H(\mathsf{vk}_\mathsf{in})$ alongside its trust base. The upgrade discipline of Sec.~\ref{sec:bridge-security} applies: a corrected or extended relation is a new constant under a new version, never an in-place replacement.

Three ASCII domain separators are fixed: $\mathsf{ANCHOR\_INIT} = \texttt{"UNICITY\_ANCHOR\_INIT"}$, $\mathsf{STEP\_INIT} = \texttt{"UNICITY\_STEP\_INIT"}$ and $\mathsf{TREF\_INIT} = \texttt{"UNICITY\_TREF\_INIT"}$. Define the \emph{step chain} $C$ and the \emph{time-reference chain} $R$ as hash chains --- chosen over vector commitments so that extension is $O(1)$ and folding needs no rebuilding:
\[
	\begin{aligned}
		C_0 &:= H(\mathsf{STEP\_INIT}), &
		C_i &:= H(C_{i-1},\, \mathsf{sid}_i,\, \txhash_i), \\
		R_0 &:= H(\mathsf{TREF\_INIT}), &
		R_j &:= H(R_{j-1},\, \mathsf{sid}_j,\, \txhash_j,\, \tau).
	\end{aligned}
\]

\subsubsection{Chain Relation $\mathfrak{R}_\mathsf{ch}$}

Proves that a well-formed, predicate-satisfying transfer chain runs from the genesis carry to the watermark carry, and commits the leaves it would have to have produced. No anchor and no certificate appear.

\begin{longtable}{clp{8.4cm}}
\textbf{Index} & \textbf{Field} & \textbf{Description} \\
\hline
\endhead
0 & $\mathsf{ver}$ & relation version; this specification defines version $1$ \\
1 & $h^0$ & genesis state hash, $H(\mathsf{id}, \mathsf{MINT\_SUFFIX})$ \\
2 & $\hat{e}^0$ & $H(\encpred(\predi^0))$ of the genesis owner predicate \\
3 & $h^m$ & state hash at the watermark \\
4 & $\hat{e}^m$ & $H(\encpred(\predi^m))$ of the owner predicate at the watermark \\
5 & $C$ & step chain over the transitions $1 \ldots m$ \\
6 & $R$ & time-reference chain over the time-dependent transitions \\
\end{longtable}

\noindent Witness: the transfer transactions $T_i$, the unlocking arguments $u_i$ for $i = 1 \ldots m$, the genesis owner predicate, and the time-reference list. Starting from $(h, e) \gets (h^0, \encpred(\predi^0))$ --- with $H(e) = x.\hat{e}^0$ --- and $C \gets C_0$, $R \gets R_0$, for each $i$ the relation checks, writing $\predi^{i-1} = \decpred(e)$ for the carried predicate,

\begin{enumerate}
	\item $T_i.\sthash = h$ \quad (the chain is contiguous);
	\item $\txhash_i \gets H(T_i.D)$;\; $\mathsf{sid}_i \gets H(e, T_i.\sthash)$;
	\item $\predi^{i-1}(\tau_i, H(T_i.\sthash, \txhash_i), u_i) = 1$. Whether $\predi^{i-1}$ reads the reference time is a static property of its type (Appendix~\ref{app:predicate-encoding}). If it does, the relation consumes the next entry $(\mathsf{sid}, \txhash, \tau)$ of the witness time-reference list, requires $(\mathsf{sid}, \txhash) = (\mathsf{sid}_i, \txhash_i)$, folds the entry into $R \gets H(R, \mathsf{sid}, \txhash, \tau)$, and evaluates the predicate with $\tau_i \gets \tau$; if it does not, $\tau_i$ is unconstrained and no entry is consumed;
	\item $C \gets H(C, \mathsf{sid}_i, \txhash_i)$;\; $e \gets \encpred(T_i.D.\predi')$;\; $h \gets H(h, T_i.D.x)$;
\end{enumerate}
and finally $h = x.h^m$, $H(e) = x.\hat{e}^m$, $C = x.C$, $R = x.R$, and the witness time-reference list is fully consumed --- so the public $R$ accounts for exactly the transitions that read a reference time, no more and no fewer.

Steps 1--4 are precisely checks 1, 3 and 4 of transfer verification (Sec.~\ref{sec:transfer-tx}) together with the carry update of $\Call{VerifyToken}{}$. Check 2 of transfer verification (network identifier) and the certificate half of check 5 are discharged outside the relation; the inclusion half is discharged by $\mathfrak{R}_\mathsf{in}$.

\paragraph{Time-dependent transitions.} Anchored inclusion does not provide reference time (Appendix~\ref{app:bridging-anchor}), while $\predi_\mathsf{tlock}$ and $\predi_\mathsf{htlc}$ need it (Sec.~\ref{sec:time-extraction}). Rather than verifying those transitions' certificates inside the relation, the compressed history carries their original inclusion proofs on the wire: the verifier validates each in the ordinary way, extracts $(\mathsf{sid}, \txhash, \tau = UC.\mathcal{IR}.t)$, and reconstructs $R$. Binding $\tau$ to $(\mathsf{sid}, \txhash)$ prevents a prover from presenting an unrelated certificate with a fake timestamp. Cost is one certificate per time-dependent transition.

\subsubsection{Inclusion Relation $\mathfrak{R}_\mathsf{in}$}

Proves that every leaf committed by $C$ was certified, under at least one anchor.

\begin{longtable}{clp{8.4cm}}
\textbf{Index} & \textbf{Field} & \textbf{Description} \\
\hline
\endhead
0 & $\mathsf{ver}$ & relation version; this specification defines version $1$ \\
1 & $C$ & step chain, identical to $\mathfrak{R}_\mathsf{ch}$'s field 5 \\
2 & $A$ & anchor accumulator $A_F$ (Sec.~\ref{sec:compression-anchors}) \\
\end{longtable}

\noindent Witness: the leaf list $\langle(\mathsf{sid}_i, \txhash_i)\rangle_{i=1}^{m}$, an inclusion certificate per leaf, the anchor roots $\langle h^*_f \rangle$ and the segment boundaries assigning leaves to anchors. The relation recomputes the hash chain $C$ from the leaf list in order, recomputes $A$ from the anchor roots in order, and requires every leaf to be included under the root of its segment. Segment boundaries are witness data: publishing them would publish the fold history for no verification benefit.

Note the asymmetry. $\mathfrak{R}_\mathsf{ch}$ contains signature verification, but is extended incrementally and not re-proven. $\mathfrak{R}_\mathsf{in}$ is hash-based, and can be re-proven from scratch cheaply.

\subsection{Verification}\label{sec:compressed-verification}

A \emph{compressed history} is
\[
\mathcal{H} = (\mathsf{ver},\; h,\; e,\; C,\; \pi_\mathsf{ch},\; \pi_\mathsf{in},\; \langle UC^*_1, \ldots, UC^*_F\rangle,\; \langle \pinc_1, \ldots, \pinc_k \rangle),
\]
with $(h, e)$ the carry it restores, $C$ the step chain shared by the two proofs, $\pi_\mathsf{ch}, \pi_\mathsf{in}$ the proofs themselves, $UC^*_f$ the anchors in fold order, and $\pinc_j$ the inclusion proofs of the time-dependent transitions in transition order. The watermark $m$ is not carried: it is implicit in how many transfers remain in $\mathcal{L}$, it is not security-relevant --- the carry $(h, e)$ is what the tail is verified against --- and omitting it keeps the number of compressed transitions undisclosed.

$\Call{VerifyCompressedHistory}{\mathcal{H}, \predi^0, h^0, \mathcal{T}}$, invoked from $\Call{VerifyToken}{}$:

\begin{enumerate}
	\item Ensure $\mathsf{ver} = 1$; decode $e$ to $\predi^m$ under the canonical rules of Appendix~\ref{app:predicate-encoding}, rejecting a non-canonical encoding.
	\item $A \gets H(\mathsf{ANCHOR\_INIT})$; for $f = 1 \ldots F$: ensure $UC^*_f.C^\mathsf{r}.\alpha = \mathcal{T}.\alpha$ and $\mathsf{VerifyUnicityCert}(UC^*_f, \mathcal{T}) = 1$; accumulate $A \gets H(A, UC^*_f.\mathcal{IR}.h)$ in the given order.
	\item $R \gets H(\mathsf{TREF\_INIT})$; for $j = 1 \ldots k$: verify $\pinc_j$ in full against $\mathcal{T}$, exactly as an ordinary transfer's inclusion proof is verified (Sec.~\ref{sec:transfer-tx}, check 5); accumulate $R \gets H(R, \pinc_j.\mathsf{sid}, \pinc_j.\txhash, \mathsf{time}(\pinc_j))$.
	\item Ensure $\mathfrak{R}_\mathsf{ch}$ verifies under $\mathsf{vk}_\mathsf{ch}$ with public input $(1,\; h^0,\; H(\encpred(\predi^0)),\; h,\; H(e),\; C,\; R)$.
	\item Ensure $\mathfrak{R}_\mathsf{in}$ verifies under $\mathsf{vk}_\mathsf{in}$ with public input $(1,\; C,\; A)$ --- the same $C$, byte-identical.
\end{enumerate}

Every failure rejects. A verifier that does not pin $\mathsf{vk}_\mathsf{ch}$ and $\mathsf{vk}_\mathsf{in}$ MUST reject any compressed token with a distinct diagnostic error, as with an unregistered reason format (Sec.~\ref{sec:mint-authorization}); it MUST NOT fall back to accepting the token unverified.

Resource accounting (Sec.~\ref{sec:nested-verification}) charges $\Lambda$ a fixed cost for each proof verification plus the $F + k$ certificate verifications. The verification cost of a compressed history is independent of the number of transitions it stands for.

\subsection{Folding and Re-Anchoring}\label{sec:compression-folding}

Advancing the watermark from $m$ to $m'$ (a \emph{fold}) extends $\mathfrak{R}_\mathsf{ch}$ recursively: the relation verifies $\pi_\mathsf{ch}$ for $(h^0, \hat{e}^0) \to (h^m, \hat{e}^m)$ with step chain $C$, then continues the loop over transitions $m+1 \ldots m'$, emitting $(h^{m'}, \hat{e}^{m'})$ and the extended chains $C', R'$. Because $C$ and $R$ are hash chains, extension costs one hash per step and nothing is rebuilt.

$\mathfrak{R}_\mathsf{in}$ is then re-proven. Two options:
\begin{description}
	\item[Append] Prove inclusion of the new leaves under a fresh anchor $UC^*_{F+1}$ and append it, leaving the earlier segments as they are. Requires only the new leaves. $F$ grows by one.
	\item[Re-anchor] Re-prove $\mathfrak{R}_\mathsf{in}$ over the \emph{entire} leaf list under a single fresh anchor, and replace the anchor list by that one certificate. $F$ returns to $1$.
\end{description}

Re-anchoring needs the full leaf list $\langle(\mathsf{sid}_i, \txhash_i)\rangle$ and fresh inclusion certificates, but nothing else: not the transfer data, not the predicates, not the unlocking arguments. A holder that wishes to re-anchor indefinitely therefore retains 64 bytes per compressed transition and re-fetches the certificates from an aggregator on demand. That data is already public --- it is what the Unicity Service holds --- so retaining it carries no confidentiality obligation, and it does not grow with the size of the transactions themselves.

Holders SHOULD re-anchor rather than append whenever the leaf list is retained. A holder that has discarded the leaf list can still fold, by appending; a holder that has discarded the transfer data as well can still fold newly received transitions, since folding consumes only the previous proof and the new transitions.

\paragraph{Fold policy.} A fold replaces raw transitions by proofs and certificates, so it pays only above a break-even point: compressing a short history yields a \emph{larger} token than leaving it uncompressed. With succinct proofs of size $|\pi|$ and certificates of size $|UC|$, a compressed history costs approximately $|\pi_\mathsf{ch}| + |\pi_\mathsf{in}| + F\cdot|UC| + k\cdot|\pinc|$ regardless of $m$, and a holder SHOULD fold only once the raw prefix it would replace exceeds that. For the same reason a fold policy that appends should fold rarely and in large increments: with a threshold of $c$ times the anchor size, the anchor list contributes about $1/c$ of the replaced history, so appending yields a constant-factor reduction where re-anchoring yields a constant size.

\section{Provenance Compression}\label{sec:provenance-compression}

\index{token compression!provenance}
Section~\ref{sec:history-compression} bounds a token's own transfer history. It leaves the second dimension untouched: a token minted by a split or merge depends on its source tokens, each of which depends on \emph{its} sources, back to issuance. Compressing every ancestor's transfer history makes each link constant-size, but the number of links --- the depth of a chain of splits, the breadth of a tree of merges --- is unaffected. For fungible fragments that is the dominant term, and it is what this section removes.

\subsection{Token Evidence and Reference Form}\label{sec:token-evidence}

\index{evidence set}\index{reference form}
A reason format that \emph{embeds} its source tokens seals them into $\mathsf{reason}$, hence into $\txhash$, hence into the certified genesis: those bytes can never be re-encoded. The split reason of Sec.~\ref{sec:token-splitting} is of this kind, and this is why it is not compressible.

A format in \emph{reference form} names its sources by token identifier instead. The identifier is sufficient: $\mathsf{id} = H(\mathsf{salt}, \alpha)$ is unique network-wide and at most one certified genesis exists per identifier (Sec.~\ref{sec:request-validation}), so an identifier determines its token as tightly as the token bytes do. Everything the reason must fix --- which source, which allocation, which manifest --- stays committed; only the \emph{evidence} for the named token moves outside.

Accordingly, a token in reference form travels with an \emph{evidence set}
\[
\mathcal{E} = \{\, \mathsf{id} \mapsto \mathsf{ev}(\mathsf{id}) \,\},
\]
supplying, for every identifier its reason formats name, one of:
\begin{description}
	\item[a complete token] $\mathcal{L}$ with $\mathsf{id}(\mathcal{L}) = \mathsf{id}$, itself possibly carrying a compressed history --- the recursive, uncompressed case;
	\item[a token certificate] $\mathcal{K}$, a succinct attestation of that token's validity, defined below.
\end{description}
$\mathcal{E}$ is one flat map carried with the outermost token and resolved transitively: an entry supplied as a complete token may name further identifiers, whose entries must be present in the same $\mathcal{E}$. A missing entry rejects.

The evidence set is not certified data and is not committed by anything: it is checked, not trusted. A verifier resolving identifier $\mathsf{id}$ either verifies the supplied token by $\Call{VerifyToken}{}$ or verifies the supplied certificate, and in both cases obtains the same facts about the same token. Substituting one form for the other is therefore invisible to every check that consumes it, which is exactly what makes provenance compression a re-encoding rather than a protocol change.

\subsection{Token Certificate}\label{sec:token-certificate}

\index{token certificate}
A token certificate attests to everything a consuming reason verifier needs about a source token, in constant size. The facts are those the split and merge verifiers read from an embedded source (Sec.~\ref{sec:split-verification}, checks 3, 5, 6, 10): its identifier, its type, the assets its genesis payload carries, and the state it had reached.

\begin{longtable}{clp{8.4cm}}
\textbf{Index} & \textbf{Field} & \textbf{Description} \\
\hline
\endhead
0 & $\mathsf{ver}$ & relation version; this specification defines version $1$ \\
1 & $A$ & anchor accumulator (Sec.~\ref{sec:compression-anchors}) \\
2 & $R$ & time-reference chain (Sec.~\ref{sec:compression-relations}) \\
3 & $\mathsf{id}$ & identifier of the attested token \\
4 & $\mathsf{ty}$ & its token type \\
5 & $\mathcal{A}$ & its genesis asset collection, as values \\
6 & $(h, e)$ & the state carry it had reached \\
7 & $\mathcal{I}$ & issuance-root chain: a hash chain over the $\txhash$ of every genesis in the attested provenance whose reason format is not conserving \\
\end{longtable}

\noindent The certificate object carried in $\mathcal{E}$ is
\[
\mathcal{K} = (\mathsf{ver},\; \mathsf{id},\; \mathsf{ty},\; \mathcal{A},\; h,\; e,\; \pi_\mathsf{lin},\; \langle UC^*_f\rangle,\; \langle \pinc_j \rangle,\; \langle T_{0,r}^\mathsf{cert}\rangle),
\]
with $T_{0,r}^\mathsf{cert}$ the certified mint transactions of the issuance roots, carried in the clear.

\paragraph{Issuance stays outside the relation.} The design constraint of Sec.~\ref{sec:history-compression} extends one level up: just as certificates are verified by the relying party rather than in-circuit, so is \emph{mint authorization}. The lineage relation expands only the value-conserving formats --- the split reason and the merge reason, whose verification rules are network-wide and type-independent. On reaching an ancestor genesis with any other reason format, it stops, emits that genesis's $\txhash$ into $\mathcal{I}$, and assumes nothing further about it. The verifier discharges each emitted root by ordinary means: $\Call{VerifyMintTransaction}{}$ including Alg.~\ref{alg:mint-auth}, with its own $\Gamma$ and its own registered verifiers.

The relation therefore contains no issuer signatures, no slot commitments, no bridge configuration and no proof-system verification keys --- nothing type-specific at all. New issuance formats can be registered without touching it, and a capped type's slot geneses (Appendix~\ref{app:reason-slot}) are checked exactly as they are for an uncompressed token. What the relation does contain is the transfer step of Sec.~\ref{sec:compression-relations}, the anchored inclusion mechanism, and the conservation arithmetic of split and merge.

Asset decoding inside the relation is the generic canonical asset-collection decoding (Sec.~\ref{sec:asset-structure}, canonical rules of Appendix~\ref{app:split-proof-encoding}), not $\mathcal{D}_\mathsf{ty}.\Call{ParseAux}{}$: the type-specific part of payload validation --- permitted asset identifiers and the like --- is applied by the verifier to the public $\mathcal{A}$ and to each root genesis it verifies in the clear.

\subsection{Lineage Relation $\mathfrak{R}_\mathsf{lin}$}\label{sec:lineage-relation}

$\mathfrak{R}_\mathsf{lin}(x; \mathsf{w})$ holds iff, for the token identified by $x.\mathsf{id}$:
\begin{enumerate}
	\item \textbf{Genesis}: the witness contains a certified mint transaction $T_0$ with $H(D_\mathsf{mint}.\mathsf{salt}, D_\mathsf{mint}.\alpha) = x.\mathsf{id}$, $D_\mathsf{mint}.\mathsf{ty} = x.\mathsf{ty}$, whose payload decodes canonically to $x.\mathcal{A}$, and whose leaf is anchored under $A$.
	\item \textbf{Reason}: if $D_\mathsf{mint}.\mathsf{reason}$ is a conserving format (split or merge, in reference form), its verification rules are re-run inside the relation: each named source is resolved to a sub-derivation of this same relation, and the format's conservation checks are applied to the sub-derivations' asset collections. Otherwise, $H(D_\mathsf{mint})$ is folded into $\mathcal{I}$ and the genesis is accepted unexamined.
	\item \textbf{Transfers}: the transfer chain from the genesis carry to $x.(h, e)$ satisfies the step checks of $\mathfrak{R}_\mathsf{ch}$ (Sec.~\ref{sec:compression-relations}), with the same anchoring and the same treatment of time-dependent transitions.
	\item \textbf{Recursion}: a sub-derivation whose evidence is itself a certificate is discharged by verifying that certificate's $\pi_\mathsf{lin}$ in-circuit, folding its $A$, $R$ and $\mathcal{I}$ into this one. This is what makes depth constant: a certificate over a certificate is one proof, not two.
	\item \textbf{Terminal state}: for a source consumed by a burn, the chain stops immediately before that burn, and $x.(h,e)$ is the state the burn spends. The burn transfer itself is never inside the certificate (Sec.~\ref{sec:compression-scope}).
\end{enumerate}

\subsection{Verifying a Certificate}\label{sec:certificate-verification}

$\Call{VerifyTokenCertificate}{\mathcal{K}, \mathcal{T}, \Gamma}$, invoked wherever a reason verifier resolves an identifier to evidence:
\begin{enumerate}
	\item Ensure $\mathcal{K}.\mathsf{ver} = 1$; decode $e$ canonically (Appendix~\ref{app:predicate-encoding}).
	\item Verify the anchors and accumulate $A$; verify the time-reference inclusion proofs and accumulate $R$ --- both exactly as in Sec.~\ref{sec:compressed-verification}, steps 2 and 3.
	\item For each carried root $T_{0,r}^\mathsf{cert}$: ensure $\Call{VerifyMintTransaction}{T_{0,r}, \pi_{0,r}, \mathcal{T}} = 1$, which runs Alg.~\ref{alg:mint-auth} under the verifier's own $\Gamma$; accumulate $\mathcal{I} \gets H(\mathcal{I}, \pi_{0,r}.\txhash)$ in the given order. Every root consumes budget from $\Lambda$, so a provenance with more issuance roots than the budget admits is rejected exactly as a too-deep provenance graph is today (Sec.~\ref{sec:nested-verification}).
	\item Ensure $\mathfrak{R}_\mathsf{lin}$ verifies under $\mathsf{vk}_\mathsf{lin}$ with public input $(1, A, R, \mathcal{K}.\mathsf{id}, \mathcal{K}.\mathsf{ty}, \mathcal{K}.\mathcal{A}, (\mathcal{K}.h, \mathcal{K}.e), \mathcal{I})$.
	\item Return $(\mathsf{id}, \mathsf{ty}, \mathcal{A}, h, e)$ to the calling reason verifier; any failed check returns $\bot$ instead.
\end{enumerate}

A consuming verifier then proceeds exactly as it would with an embedded token: for a split, it verifies the source's terminal burn as an ordinary certified transfer out of $(\decpred(e), h)$, takes $b_\mathcal{M}$ from its auxiliary data, and applies checks 4--10 of Sec.~\ref{sec:split-verification} with $\mathcal{A}$ in place of the decoded source payload and $\mathsf{id}$ in place of the decoded source identifier.

\paragraph{Why the asset values are public.} $\mathcal{A}$ appears in the clear because conservation is checked in the clear: the RSMST root sum must equal the source amount (Sec.~\ref{sec:split-verification}, check 10), and that arithmetic is the verifier's, not the prover's. This discloses nothing new --- every holder of every split output already learns the source amount from that same check --- and it is what allows one certificate to serve all $k$ outputs of a split, since the certificate speaks about the source alone and is independent of any particular output.

\subsection{Preparation}\label{sec:certificate-preparation}

A certificate is about a token, not about a transaction that consumes it, so it can be produced before the consuming transaction exists. The intended discipline follows from that:

\begin{itemize}
	\item The holder of a token that will be split or merged prepares its certificate in advance --- by the same background job that folds transfer history (Sec.~\ref{sec:compression-folding}), and off the critical path of the split.
	\item At split time no proving occurs. The splitter burns and mints as usual, and hands each of the $k$ outputs the \emph{same} certificate as evidence for their common source. One proving job serves all $k$ recipients and, through them, the entire descendant subtree.
	\item Merge composes the same way: each of the $k$ sources contributes one certificate, and the merged token's own certificate --- prepared later --- folds all of them into one.
\end{itemize}

Where §\ref{sec:history-compression} has a break-even point, this does not: a certificate replaces an entire ancestor token, which is never smaller than a proof once the ancestor has any history of its own. The trade-off is proving time, not size.

\subsection{Rules and Scope}\label{sec:compression-scope}

\begin{description}
	\item[Terminal burns are never folded] A token consumed by a burn --- as the source of a split (Sec.~\ref{sec:split-verification}) or of any reason format that consumes a burn --- MUST have that final transfer presented in the clear, whether the rest of it is a compressed history ($m \le n-1$) or a certificate (the chain stops before the burn). The consuming verifier checks the burn's auxiliary data and recipient predicate byte-exactly, and neither a proof nor a certificate supplies them.
	\item[Per-transfer type checks are out of scope in version 1] $\mathfrak{R}_\mathsf{ch}$ and $\mathfrak{R}_\mathsf{lin}$ omit check 6 of transfer verification (Sec.~\ref{sec:transfer-tx}), which is a no-op for types that define no per-transfer rules --- the common case (Sec.~\ref{sec:mint-authorization}). A type that defines per-transfer rules, such as a pool type (Appendix~\ref{app:autonomous-pools}), requires those rules inside the relation; its definition manifest MUST then pin the verification keys of the relation variant that implements them, and a verifier MUST NOT accept compressed tokens of such a type under the generic keys.
	\item[Only reference-form reasons compress] A genesis whose reason embeds its sources by value seals them permanently. Provenance compression is therefore available to a token exactly when every genesis in its ancestry used a reference-form format. The embedding split reason (tag 39044) and its reference-form counterpart are separate registry entries with separate tags (Appendix~\ref{app:reason-formats}); a type admits whichever it intends its holders to be able to compress, and a token already minted under the embedding form cannot be converted.
	\item[Merges keep their roots] Folding collapses provenance \emph{depth} to a single proof, but each independent lineage flowing into a merge contributes its own issuance root, and every root is verified in the clear. Breadth is therefore still paid for, in proportion to the number of distinct issuance events behind a token --- one for a token that has only ever been split, more for a heavily merged one. Shallow, narrow provenance remains preferable: issuing in fixed denominations and consolidating deliberately beats repeated splitting and merging.
\end{description}

\paragraph{Data minimization, not privacy.} A recipient of a compressed token does not receive the predicates, unlocking arguments or auxiliary data of the folded transitions --- including any ephemeral keys those transitions carried (Sec.~\ref{sec:private-transactions}) --- and, with certificates, does not receive the ancestor tokens at all. This is a reduction in what is disclosed, not a privacy guarantee: unless the proof system is zero-knowledge, no hiding property is claimed for $\pi_\mathsf{ch}$ or $\pi_\mathsf{lin}$; the inclusion proofs of time-dependent transitions expose those transitions' state identifiers; the issuance roots of a certificate are disclosed in full by construction; and every party that held the token earlier retains the raw history regardless. Applications MUST NOT rely on compression as a privacy mechanism; unlinkability is provided by the protocols of Sec.~\ref{sec:private-transactions}.

\paragraph{Open items (next revision).} (i)~Proof-system profile and concrete sizes for $\mathfrak{R}_\mathsf{ch}$, $\mathfrak{R}_\mathsf{in}$ and $\mathfrak{R}_\mathsf{lin}$ (recursion-friendly, with secp256k1 verification in-circuit); the break-even point of Sec.~\ref{sec:compression-folding} cannot be stated numerically until these are fixed. (ii)~CBOR encodings and semantic tags of $\mathcal{H}$, $\mathcal{K}$ and the evidence set. (iii)~In-relation budget accounting mirroring $\Lambda$, including the cost of nested certificate verification. (iv)~A formal statement of the transfer-verification step in-circuit, shared with the bridging relation (Appendix~\ref{app:bridging-relation}). (v)~The relation variant carrying per-transfer type checks, prerequisite to compressing pool tokens. (vi)~Should the aggregation layer later publish consistency proofs between arbitrary certified roots, anchors could be collapsed inside $\mathfrak{R}_\mathsf{in}$ and the anchor list would reduce to a single root unconditionally. (vii)~Reference form for the conversion reason (Appendix~\ref{app:reason-convert}) and the pool transition records (Appendix~\ref{app:autonomous-pools}), which embed tokens by value today. (viii)~Whether committing the mint reason in $D_\mathsf{mint}$ by hash, so that the reason bytes themselves become detachable, is worth the wire-format change: it would let tokens already minted under an embedding format be compressed retroactively, which reference form alone cannot do.


\section{Bridged Assets}\label{sec:bridged-assets}

\index{bridge}\index{bridged asset}
A fungible token may represent an asset held in custody on an \emph{external chain} (e.g.\ an account-based EVM chain). Bridging is bi-directional. \emph{Bridge-in} locks the external asset in a settlement contract (the \emph{vault}) and mints a Unicity token whose mint reason (Sec.~\ref{sec:mint-justification}) is a \emph{backing proof} binding the token to that lock. \emph{Bridge-out}, or \emph{return}, burns the Unicity token and releases the matching external asset. Both directions are realized without a trusted bridge operator or committee: bridge-in as a token-type specific mint-reason verifier that every recipient re-runs, and bridge-out as a succinct validity proof the vault verifies. This section specifies both; concrete data structures and algorithms are in Appendix~\ref{app:bridging}.

\subsection{Bridge-In: Lock and Mint}\label{sec:bridge-in}

To bring an asset in, the locker fixes the recipient's first-owner predicate $\predi'_0$ and a token salt, determining the token identifier $\mathsf{id} = H(\mathsf{salt},\alpha)$ (Sec.~\ref{sec:mint-tx}) and the recipient commitment $h_\mathsf{rcpt} = H(\mathsf{CBOR}(\predi'_0))$. The locker calls the vault on the external chain, which escrows the asset into pooled custody, assigns a monotone lock nonce $n$, and emits a \emph{lock event} committing to $\mathsf{id}$, $h_\mathsf{rcpt}$, and the locked amount. The locker then mints a Unicity token of type $\mathsf{ty}$ to $\predi'_0$ whose genesis carries a \emph{backing reason} that references the lock by $(\chi, a_\mathsf{V}, a_\mathsf{A}, n)$ (Appendix~\ref{app:bridging-lock}).

Minting is permissionless: the minter key is a public constant derived from $\mathsf{id}$ (Appendix~\ref{app:el-constants}), so a valid genesis signature conveys no authority by itself. Authority comes entirely from the backing reason, verified by every recipient as the token-type specific mint-reason check (Sec.~\ref{sec:mint-tx}, step~5). The verifier (Appendix~\ref{app:bridging-backing}) confirms that a \emph{final} lock with nonce $n$ exists at the configured vault and asset on the configured chain, and binds it to the genesis: the lock's committed identifier equals $\mathsf{id}$, its recipient commitment equals $h_\mathsf{rcpt}$, and its amount equals the genesis's declared value for $\mathsf{aid}$. The reason body carries only the lock locator and the trust anchors; every security-relevant value is read from the certified genesis and the lock event and validated cryptographically.

Bridge-in cannot be instantaneous. A reorganization of the external chain could undo the lock after the token is minted and in circulation, so a recipient must wait for the lock to be final on the external chain before treating the token as good. This finality wait is intrinsic to accepting a deposit from a chain with probabilistic finality. Confirming the lock requires reading external-chain state: the recipient does so either by querying an external-chain node, or by verifying an external-chain inclusion proof carried in the backing reason against a pinned external-chain anchor (Appendix~\ref{app:bridging-finality}). Either way each recipient is its own verifier, so bridge-in introduces no trusted bridge party; its only assumption is the external chain's own consensus.

The wait is enforced by each verifier for itself, not attached to the token as a global condition. In particular, the locker minting to a predicate it already controls needs no wait: it already knows whether its own deposit exists, so no reorganization can surprise it, and a wallet may show such a token to its own owner immediately. The wait binds the first party that did \emph{not} witness the lock --- typically the first recipient the token reaches after leaving the locker's own custody --- since only that party's own $\Call{LockFinal}{}$ check protects it from a lock later undone by a reorganization.

\paragraph{Security.}
\begin{description}
\item[No mint without a lock] The backing verifier accepts the genesis only if a matching final lock exists on the configured chain and asset; a token minted without a lock fails verification and is never accepted.
\item[No double mint] The genesis of a token with identifier $\mathsf{id}$ is recorded at a single state determined by $\mathsf{id}$ (Sec.~\ref{sec:mint-tx},~\ref{sec:request-validation}); since the lock commits to $\mathsf{id}$, one lock funds exactly one token and cannot be replayed for a second mint.
\item[No theft] Although anyone may construct the genesis, $h_\mathsf{rcpt}$ binds ownership to the predicate the locker named on the external chain, so only the intended recipient can spend the minted token.
\item[No value inflation] The declared genesis value for $\mathsf{aid}$ must equal the locked amount, so minted value never exceeds custody.
\item[No rogue contract] The chain, vault, and asset in the reason must equal the pinned configuration, so a genesis pointing at an unauthorized contract is rejected.
\item[No reorged lock] The lock must be final on the external chain, so a deposit that could still be reversed is not accepted.
\end{description}

\subsection{Bridge-Out: Setting}\label{sec:bridge-setting}

A Unicity burn is final the instant it is certified by the BFT Consensus layer and is verifiable offline by $\Call{VerifyToken}{}$ (Sec.~\ref{sec:token-verification}) against the trust base $\mathcal{T}$ alone: there is no source-finality wait, no validator node, and no external RPC query. The limitation is that the external vault is computationally weak --- re-running $\Call{VerifyToken}{}$ on-chain incurs cost which grows with token history. A \emph{succinct validity proof} (a SNARK, see Appendix~\ref{app:bridging-primitives}) compresses that token history-dependent check into a single verification of constant cost.

The vault holds pooled custody of one asset, has persistent storage, can verify a succinct proof for constant cost, and pins (i)~an allow-listed trust-base hash $h_\mathcal{T} = H(\mathcal{T})$, selecting \emph{which} Unicity Service instance is authoritative, and (ii)~an immutable configuration hash $h_\mathsf{cfg}$ committing the external chain identifier, the vault and asset addresses, the bridged token type $\mathsf{ty}$, the asset identifier $\mathsf{aid}$, and the protocol's domain separators (Appendix~\ref{app:bridging-config}). There is no trusted operator, committee, or challenge window: the vault releases funds only against a valid proof.

The return proof is structured in layers: a shared Unicity anchor authenticates historical transition leaves; token-lineage verification checks ownership and chain linkage; value/backing verification ties the burned value to a recorded source-chain lock; replay verification advances the spent-burn accumulator; and the settlement layer binds the public release leaves to the vault transfers. Only the final settlement layer touches source-chain state.

\subsection{Return Authorization}\label{sec:bridge-return-reason}

To return value, the holder forms a \emph{return reason} $\mathcal{R}$ and its canonical encoding $b_\mathcal{R}$. The holder then burns the token (Sec.~\ref{sec:burn-transaction}) with auxiliary data $b_\mathcal{R}$ and recipient predicate $\predi_\mathsf{burn}(H(b_\mathcal{R}))$. The reason commits to the external release: the recipient, a gross amount $v$ equal to the burned token's certified value for $\mathsf{aid}$, an optional relayer fee, a fee deadline, and the pinned configuration fields (Appendix~\ref{app:bridging-reason}). A fungible token might have been split (Sec.~\ref{sec:token-splitting}), causing fractional returns.

\subsection{Replay Prevention}\label{sec:bridge-replay}

Replay prevention is implemented via a \emph{nullifier accumulator}, whose root $A$ is stored on-chain by the vault: an authenticated set (implemented by the sparse Merkle tree of Sec.~\ref{sec:smt}, which already provides inclusion and non-inclusion certificates) of the burns already released. The \emph{nullifier} of a burn is derived from its certified leaf, whose state identifier the Unicity Service records at most once (Sec.~\ref{sec:request-validation}); it is therefore globally unique by the same mechanism that prevents double-spending. A release proves the nullifier is \emph{absent} from $A$ and inserts it, and the vault advances $A$. Consequently, the on-chain state necessary for replay prevention is \emph{constant} --- one root.

The nullifier accumulator can be deterministically rebuilt by anybody based on transaction history of the source blockchain.

\subsection{Validity Statement}\label{sec:bridge-statement}

For a batch of $B$ burns, the proof attests the conjunction of the following claims:

\begin{description}
\item[Anchor.] A single recent Unicity Certificate $UC^*$ certifies an SMT root $h^* = UC^*.IR.h$ under $\mathcal{T}$, and $H(\mathcal{T}) = h_\mathcal{T}$. Because the SMT is add-only (Sec.~\ref{sec:smt}), every state a token ever occupied remains provable under any later root, so one $UC^*$ anchors entire token histories. The proof verifies this BFT certificate \emph{once} per batch, instead of one certificate per transition.
\item[Finality.] Each burned token verifies by $\Call{VerifyToken}{}$, with every certified transaction's leaf shown included under the shared root $h^*$; in particular the final state is a burn whose auxiliary data is the encoded return reason and whose recipient predicate binds its hash. This anchored mode is restricted to predicates whose validation does not depend on the original Unicity request-validation time.
\item[Value and backing.] Each burned amount equals the token's certified value for $\mathsf{aid}$, which traces --- through split value-conservation (Sec.~\ref{sec:split-verification}) --- to a genesis whose backing proof references a lock the vault recorded at bridge-in.
\item[Destination.] Each $\mathcal{R}$ matches the pinned configuration and yields a public \emph{release leaf} (recipient, amount, fee).
\item[Replay.] Each nullifier is absent from the input accumulator root $A_\mathsf{old}$; inserting them yields $A_\mathsf{new}$.
\end{description}

The vault verifies the proof, checks $h_\mathsf{cfg}$ and that $h_\mathcal{T}$ is allow-listed, requires $A_\mathsf{old}$ to equal its stored root, confirms each referenced lock digest against its own bridge-in records, advances the root to $A_\mathsf{new}$, and pays each release leaf. No external query is made at return time: backing was committed locally when the asset was locked.

\subsection{Security}\label{sec:bridge-security}

\begin{description}
\item[Solvency.] Every bridged token in circulation is backed by an equal external lock (bridge-in), and split verification guarantees children never exceed their parent (Sec.~\ref{sec:split-verification}). Hence $\sum(\text{valid burns}) \le \sum(\text{locks})$, and valid releases can never drain custody below zero. Over-release would require a burn of an unbacked token, which the backing claim and the vault's lock-digest check exclude.
\item[No double release.] The nullifier is unique (single-spend, Sec.~\ref{sec:request-validation}); a release both proves its non-membership and inserts it, and the vault gates on $A_\mathsf{old}$ equal to its current root. A replayed proof is rejected because the root has advanced, and a freshly built one cannot prove non-membership of an inserted nullifier.
\item[Authenticity.] The proof embeds $\Call{VerifyToken}{}$ against the pinned $\mathcal{T}$, so a forged, malformed, or non-final burn is unrepresentable under proof-system soundness.
\item[No trusted parties.] The prover cannot alter the recipient or amount (fixed in the certified $\mathcal{R}$) nor fabricate a release; it can only stall, and any party holding the burned token can reproduce the proof.
\end{description}

\paragraph{Relation upgrades.} The verification key $\mathsf{vk}$ is immutable once a vault is deployed: this is what makes proof verification trustworthy, since no party --- including the deployer --- can silently swap in a different relation later. The consequence is that fixing a bug in the proving relation, or extending it, requires deploying a \emph{new} vault under a new $\mathsf{vk}$; it cannot be done in place. The old and new vaults share no state, so value locked under the superseded configuration must be returned under the old relation before, or independently of, adopting the new one. Appendix~\ref{app:bridging-upgrades} details the upgrade procedure.

The full data structures, the proving relation, the settlement procedure, and the batched proving mechanism are in Appendix~\ref{app:bridging}.

\section{Private Transactions}\label{sec:private-transactions}

In the transaction flow described above, Sec.~\ref{sec:transaction-flow}, the Unicity Service learns only the public key and signature (predicate and unlock data in general) of the token spending party; but it is not possible to associate transactions with tokens. Looking at a token it is possible to associate transactions if made by the same party using the same key. In order to achieve perfect privacy it is necessary to generate a fresh predicate $\predi'$ for every transaction. This requires generating and storing a fresh keypair per transaction, which may be impractical when the recipient's secure storage is limited, and forces the transaction sender to obtain recipient's key for every transaction, making the transacting protocol interactive.

This section presents protocols that allow the recipient to derive unlinkable predicates from a single persistent keypair, requiring no persistent state beyond the keypair itself. Also, this persistent keypair can be used as a persistent address (recipient's identifier).

The protocols below are implemented at the ``wallet'' level and need no support by the execution layer and Unicity Service. User can choose selectively wheter to make fully private transactions or not.

The privacy protocols produce a transaction-specific public key $\mathsf{pk}_{tx}$ that the sender embeds in the predicate $\predi' = \predi_\mathsf{sig}(\mathsf{pk}_{tx})$. An ephemeral public key $R$ is included in the auxiliary data $\auxd'$ of the transaction, enabling the recipient to reconstruct the corresponding private key $\mathsf{sk}_{tx}$ when spending.

The protocols below assume an elliptic curve group of order $n$ with generator $G$, and that the signature predicate $\predi_\mathsf{sig}$ uses a compatible scheme (e.g. ECDSA). The persistent keypair is $(\mathsf{sk}, \mathsf{pk})$ where $\mathsf{pk} = \mathsf{sk} \cdot G$.

\subsection{Interactive Protocol}\label{sec:private-interactive}

For each incoming transaction, the recipient generates an ephemeral blinding factor $r$ and derives a transaction-specific public key $\mathsf{pk}_{tx} = (\mathsf{sk} + r) \cdot G$. The protocol is shown in Figure~\ref{fig:private-interactive}.

The recipient sends $\predi_\mathsf{sig}(\mathsf{pk}_{tx})$ and the ephemeral public key $R$ to the sender, who includes $R$ in the auxiliary data $\auxd'$ of the transfer transaction. When spending the received token, the recipient reconstructs the blinding factor $r' = H(\mathsf{sk} \,\|\, R)$ from the persistent private key and $R$ (read from $\auxd'$), and computes the transaction-specific private key $\mathsf{sk}_{tx} = \mathsf{sk} + r' \bmod n$.

\subsection{Non-Interactive Protocol}\label{sec:private-non-interactive}

For applications where the recipient publishes a persistent public key $\mathsf{pk}$ as an address, the sender can derive unlinkable predicates without interaction using Diffie-Hellman key exchange inspired protocol, shown in Figure~\ref{fig:private-non-interactive}.

The key challenge is protecting against a malicious sender who might choose a predictable ephemeral key $r$ or leak it to compromise unlinkability. The construction addresses this by binding the blinding factor to both the shared secret and public transaction data.

\begin{figure}[!htb]
\centering
\fbox{
\begin{minipage}{0.95\textwidth}

\underline{Setup:} Recipient publishes persistent public key $\mathsf{pk} = \mathsf{sk} \cdot G$

\vspace{3mm}
\begin{tabular}{lcl}
\textbf{Sender} & & \textbf{Recipient} \\
\hline
\\[-2mm]
$r \stackrel{\$}{\gets} \mathbb{Z}_n^*$ & & \\
$R \gets r \cdot G$ & & \\
$s \gets H(r \cdot \mathsf{pk} \,\|\, R \,\|\, \sthash)$ & & \\
$\mathsf{pk}_{tx} \gets \mathsf{pk} + s \cdot G$ & & \\
$\predi' \gets \predi_\mathsf{sig}(\mathsf{pk}_{tx})$ & & \\
$\auxd' \gets \{\ldots, R\}$ & & \\
Create and certify $T$ & & \\
& $\xrightarrow{\hspace{0.6cm} \mathcal{L}\; \cup\; T^\mathsf{cert} \hspace{0.6cm}}$ & \\[3mm]
& & \textbf{if} $R = \mathcal{O}$ \textbf{then abort} \\
& & $s' \gets H(\mathsf{sk} \cdot R \,\|\, R \,\|\, \sthash)$ \\
& & \textbf{if} $\mathsf{pk} + s' \cdot G \neq \mathsf{pk}_{tx}$ \textbf{then abort} \\
& & $\mathsf{sk}_{tx} \gets \mathsf{sk} + s' \bmod n$ \\
& & Sign next transaction using $\mathsf{sk}_{tx}$ \\
\end{tabular}
\end{minipage}
}
\caption{Non-interactive protocol for generating unlinkable predicates.}
\label{fig:private-non-interactive}
\end{figure}

The sender generates an ephemeral keypair $(r, R = r \cdot G)$ and computes a Diffie-Hellman shared secret $r \cdot \mathsf{pk}$. The blinding factor is derived by hashing the shared secret together with $R$ and the current state hash $\sthash$:
$$s = H(r \cdot \mathsf{pk} \,\|\, R \,\|\, \sthash)$$

The transaction-specific public key is $\mathsf{pk}_{tx} = \mathsf{pk} + s \cdot G$, and $R$ is included in $\auxd'$. The sender sets $\predi' = \predi_\mathsf{sig}(\mathsf{pk}_{tx})$ in the transaction data. Upon receiving the transaction, the recipient:
\begin{enumerate}
\item Verifies $R \neq \mathcal{O}$ (not trivially insecure)
\item Computes the shared secret $\mathsf{sk} \cdot R = r \cdot \mathsf{pk}$ using the persistent private key
\item Derives $s' = H(\mathsf{sk} \cdot R \,\|\, R \,\|\, \sthash)$ and verifies $\mathsf{pk} + s' \cdot G = \mathsf{pk}_{tx}$
\item Computes $\mathsf{sk}_{tx} = \mathsf{sk} + s' \bmod n$
\end{enumerate}

Including both $R$ and $\sthash$ in the hash input ensures that:
\begin{itemize}
\item Even if the sender chooses a predictable $r$, the blinding factor $s$ remains unpredictable to external observers
\item The recipient can verify that the sender correctly computed $\mathsf{pk}_{tx}$ without learning $r$
\item Each transaction uses a unique blinding factor, since $\sthash$ is unique by construction (Sec.~\ref{sec:token-state}), preventing linkability even if the sender reuses the same $r$
\end{itemize}
